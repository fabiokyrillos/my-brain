## 0. First-principles review — what Phase 2F should *not* be

Two different documents currently claim to define Phase 2F, and this proposal recommends following **neither** as written.

**Claim A — `PHASE_2_PLAN.md` (2026-07, pre-2X):** "Retroactive history and finish": occurrence/date semantics, historical timeline placement, review invalidation, recurrence, plus a bucket of pagination/responsive/localization/closeout work.

**Claim B — `PHASE_2E_PRD.md` §22 (2026-07-25):** Semantic task retrieval — embeddings, pgvector, a new job type, backfill, invalidation, cost accounting — *conditional* on the measured baseline justifying it, plus the `2E-COMMAND-012` provenance closure (ADR-053) and the "is activity an entity?" decision.

Each planned capability was challenged against the questions the review demands. Verdicts:

| Candidate | Real problem today? | Verdict | Why |
|---|---|---|---|
| Semantic task retrieval (§22) | **Unproven** | **Defer — gate on evidence** | §22 itself is conditional ("should the measured baseline later justify"). The baseline is 14 hand-written scenarios measuring the scoring layer only, and the feature has been live for **hours** with zero real commands typed. Building an embedding pipeline, a new job type, a backfill fan-out and index tuning before a single week of real usage is the largest possible investment against the weakest possible evidence. What *is* owed now is the measurement that makes the gate real (see 2F.5). |
| `2E-COMMAND-012` provenance | **Yes — recorded residual risk** | **In scope, conditionally (see 2F.1)** | *(Revised, F2.)* Revision 1 justified this by citing ADR-053's naming of Phase 2F. That citation is void: ADR-053's stated reason was that "Phase 2F already has to widen that same table for task embeddings (PRD §22), which makes it the natural home for one migration that fixes both," and §2 of this proposal removes the embeddings widening. The placement is therefore re-argued on first-order grounds, or not at all. **First-order grounds:** it is the one requirement Phase 2E recorded as *not delivered*, its residual risk is written into four documents, and it is the only change in this phase that touches the AI path at all — so it is the only phase in the foreseeable roadmap where the highest-blast-radius shared function can be re-declared *alone*, with nothing else competing for the same deployment session's attention. That is a real property of 2F and it does not depend on §22. **What it is not:** load-bearing. If the 2F.1 dry-run gate (F3) does not pass, provenance drops out of Phase 2F entirely and the phase still delivers its thesis. This row is the only in-scope item with a stated drop-out condition, and that asymmetry is deliberate. |
| Write-path consolidation (PRD §5, §16.4, `TODO.md`) | **Yes — the largest standing contract violation** | **In scope — the centerpiece** | `authenticated` holds direct `insert/update/delete` on `public.tasks` and `public.reminders`. `persistTaskStatus` is a plain client UPDATE with no undo row, no expected-pre-state guard, no operation key; `createRecord` is a plain insert; reminder authoring is a plain insert. This violates the product's own acceptance bar ("unaudited mutations… cosmetic undo" are disqualifying) and `ENGINEERING_STANDARDS.md` ("sensitive mutations are never plain client writes"). Phase 2E keeps consistency *going forward*; the pre-existing rows need a one-off reconciliation decision. This belongs with write-path consolidation because both close the same door. |
| Recurrence | No evidence of need | **Defer** | No recurrence model exists, no user has asked for one, and the product has one user. A large domain-model investment with zero demand signal. |
| Retroactive occurrence placement + review invalidation | Premature | **Defer** | Review *generation* itself is known-defective (`TODO.md` M11: fabricated similarity scores, server-local time, Portuguese-only prompts). Building invalidation semantics on top of a broken generator is inverted priority. Fix reviews first, in a phase that owns them. |
| Multi-target commands | No | **Defer** | Explicitly refused with its own reason code today; no usage data on how often users hit the refusal. Measure first (2F.5 makes the refusal rate visible). |
| "Activity" as a distinct entity | No | **Decide no, by ADR, in 2F** | Phase 2E's "activity = a task created by command" has produced zero observed problems. Inventing an entity type, table, RLS policy and projection surface for a distinction no user has needed would be pure speculation. Close the question §22 leaves open with a recorded decision and a named reopening condition (evidence from real usage), not with silence. |
| Split/merge (`2C-STRUCTURE-004`, issue #8) | Blocked on product definition | **Stay deferred** | Unchanged: no field mapping or UX exists to build against. |
| Rate limiting / spend caps (C1), error sink (H7), cron dead-man's switch (H8), retention purges (M6) | Yes, but a different phase's job | **Explicitly next phase (2G)** | These are real and C1 is the recorded blocker for *public production*. They are operational-readiness work with no coupling to the task-write domain, and folding them in would make 2F a grab bag. Recommendation: Phase 2G "Operational Readiness" immediately after 2F, scoped from the existing hardening backlog. If any 2F slice slips, 2G's C1 item may be pulled forward — it is independent. |
| Mobile/localization/accessibility "finish" (Claim A's bucket) | Continuous obligation | **Not a phase** | These are Definition-of-Done items on every slice (and Phase 2E held that bar — 12/12 journeys, both locales, both form factors). A "finish" phase for them institutionalizes the idea that other phases may skip them. |

**Conclusion of the review:** Phase 2F as currently envisioned in either document should not be built. The best next phase is smaller, cheaper and lower-risk than both: finish the trust model the product already promises, close the one recorded Phase 2E debt, and build the measurement that lets Phase 2G+ decisions be made on evidence instead of taste.

One bookkeeping consequence: `PHASE_2_PLAN.md`'s Phase 2F heading and `TODO.md` line 28 describe Claim A and are now stale. An ADR should record the re-scoping so the phase letters stop pointing at two different plans.

## 1. Executive summary

**Objective.** Make the Phase 2E mutation contract the *only* way a task changes, persist AI provenance on the ledger, reconcile the pre-existing reminder inconsistency, and replace the scoring-layer match baseline with an end-to-end measured one — so that the semantic-retrieval decision §22 defers is made on real data.

**Business value.**
- The product's core promise — every mutation audited, reversible, explainable — becomes *true*, not "true for Phase 2E's mutations only" (the §16.4 residual risk, closed).
- A bad AI command becomes attributable to the exact prompt/strategy version that produced it, by a **deterministic join on an identity both rows already carry** — not by timestamp proximity (ADR-053's residual risk, closed). *(Revised, F1: Revision 1 said "by reading a column", which was false — the column would have sat on a row with no join key to the operation. See §3 "AI interaction".)*
- Future phases get one write path to extend instead of two to keep in sync — the single largest maintenance-cost reduction available in the codebase today.
- The roadmap's most expensive open question (embeddings) gets an evidence gate instead of a vibe.

**Why Phase 2F should exist at all.** Because Phase 2E shipped a second, better task-write contract beside the old one, and every month the two coexist is a month in which the Work surface's buttons silently bypass audit-actor, undo, idempotency and reminder consistency. The window where consolidation is cheap — contract fresh, team context hot, zero production data pressure — is now.

## 2. Scope

**In scope**
1. AI provenance persisted on the usage ledger, **and made joinable to the operation it explains** (`2E-COMMAND-012`, ADR-053 discharge). Two parts, both inside one migration: (a) prompt and strategy version recorded on the ledger row the command parse already writes; (b) that row's existing, unused `source_type`/`source_id` pair populated — `'task_command'` and the command's operation key — so the row names the command attempt it belongs to. *(Revised, F1. Part (b) is what makes part (a) discharge the requirement; without it the versions sit on a row nothing can join to. It costs one literal in the same allowlist the same migration already re-declares, and no new column, table or index.)*
2. Task write-path consolidation: `persistTaskStatus` (Work-surface status buttons) and `createRecord`'s task branch migrated onto the validated mutation/creation contract; direct `insert/update/delete` on `public.tasks` revoked from `authenticated` afterward.
3. Reminder write-path decision and reconciliation: reminder authoring (`createReminder`) moved behind a validated path or an explicitly recorded exception; a one-off reconciliation of `scheduled` reminders orphaned on terminal/null-due tasks; direct DML on `public.reminders` narrowed to what the decision leaves necessary.
4. Measured matching: an end-to-end match corpus executed against the deployed contract (now possible — deployment exists), re-baselining `2E-MATCH-018` at its honest scope; plus a minimal internal reader over the command funnel events (M18, minimal form) so refusal/ambiguity/no-match rates are observable from real usage.
5. Decision ADRs: activity remains a task (with reopening condition); semantic retrieval gated on named evidence thresholds; phase-letter reconciliation for the old Claim A scope.
6. Small enablers already named in the backlog that de-risk this phase's own SQL work: the plpgsql grammar-trap guard (`TODO.md`, Slice 2E.4 discovery) before any new function body is written.

**Out of scope**
- Any embedding, vector, `pg_trgm`, or semantic infrastructure; the `source_type` literal **`'task'`** (that literal means "this spend embedded a task row" and ships with the phase that ships embeddings, not speculatively). *(Clarified, F1: the literal 2F adds is `'task_command'`, which classifies a command **parse attempt** and names an operation key, not a task. `202607250055:15-20` declined `'task'` because "at parse time the command has no persisted row of any kind — no task is selected yet, by construction". That reasoning is untouched and still correct: 2F does not claim a task. It claims the operation key minted at [`actions.ts:672`](../../../src/features/task-commands/actions.ts#L672) before the parse — an identity that already exists at ledger-write time. The two literals are independent and neither pre-empts the other.)*
- Recurrence, retroactive occurrence placement, review invalidation, review-generation repair.
- Multi-target commands; new command verbs; any taxonomy change.
- Rate limiting, spend caps, error sink, cron dead-man's switch, retention purges (→ Phase 2G).
- Split/merge (issue #8); Google OAuth; integrations; chat streaming; `daily-cycle`/`agent` decomposition.

**Deferred (named, with owner)**
- Semantic retrieval → next phase that passes the 2F.5 evidence gate.
- Operational readiness backlog → Phase 2G.
- Old "retroactive history" scope → a future phase after review generation is repaired.

**Explicit non-goals**
- No big-bang rewrite of `operations/` or `tasks/` features; UI behaviour of the Work surface is preserved, not redesigned.
- No new user-facing capability is the point of this phase. 2F is allowed to ship near-invisible.
- No backfill of provenance onto historical ledger rows (mirrors the ADR-046 precedent: forward-only).

## 3. Architecture

**Domain changes.** None at the entity level. Tasks, reminders, operations, ledger rows keep their shapes. What changes is *authority*: after 2F, the only routes to a task write are (a) the Phase 2E mutation/creation RPCs, (b) the Phase 2C candidate-materialization RPCs, (c) `service_role` workers, and (d) triggers/heartbeat — never a client-role table write.

**Ownership model.** Unchanged: non-null `user_id`, forced RLS, composite-FK relationship proofs. Grants *narrow* (revocations only); nothing widens, `anon` continues to hold nothing.

**Command lifecycle.** Unchanged for the console. The consolidation question is whether surface buttons (complete / wait / resume / reopen; manual create) become **thin mounts of the existing command contract** or get a **thin sibling RPC sharing the private primitives**. Reuse remains the default, but *(revised, F4)* Revision 1's stated mechanism for it was wrong and is withdrawn.

**Withdrawn:** "The Work projection already carries `updated_at`, so a surface click can synthesize a full envelope … expected pre-state from the rendered row." That is refuted by the contract. `apply_task_command` rejects any `p_pre_state` that does not carry **exactly nineteen keys** (`202607260059:876`) and requires four of them to be arrays with matching lengths (`:922-927`); the shape is [`TaskPreState`](../../../src/features/task-commands/matching.ts#L61-L81) — twelve scalars plus seven relation arrays. The Work projection selects thirteen columns and performs no relation joins ([`work-projection.ts:120`](../../../src/features/daily-cycle/work-projection.ts#L120)), so `completed_at`, `cancelled_at`, `created_at` and all seven relation arrays — **ten of nineteen keys** — are simply not there. Revision 1 also omitted `p_observed_before` from its envelope list entirely; it is a required, ISO-pattern-validated argument (`202607260059:858-862`) that is hashed into the fingerprint and that no rendered row can honestly supply, because its meaning is *the instant the database resolved the pre-state* ([`matching.ts:99`](../../../src/features/task-commands/matching.ts#L99)).

**Replacement mechanism, and it introduces nothing.** A surface click reads its pre-state the same way the console does: by calling the existing `public.list_task_command_candidates`. Its only required argument is `p_eligible_statuses`; `p_title_query` and the five other parameters are all defaulted (`202607260059:2518-2524`). The rendered row supplies the eligible statuses (from the taxonomy, for the clicked action) and the exact title as the query; the returned candidate whose `taskId` matches the clicked row is the witness — full nineteen-key pre-state, server-derived `observed_before`, already camel-cased by [`matching.ts`](../../../src/features/task-commands/matching.ts). The surface then walks the same preview → apply path the console walks, entering below the parse step. **Zero new RPCs, zero migrations, zero new query shapes, and no change to `list_task_command_candidates`** — which matters, because that function's "amendment window is closed by exhaustion" (`202607260059:2505-2508`) and any argument change would cost a `_v2`.

Two consequences worth stating plainly. First, this reads pre-state at **click** time rather than render time, which is strictly more correct than what Revision 1 described and removes the stale-witness-by-default problem F7 identifies. Second, if the task's title changed since render, the exact-title query returns nothing and the click refuses with the refresh affordance — the designed behaviour for stale state, reached one step earlier.

**The residual question, which is now a test and not an architecture decision:** whether an exact-title query reliably returns the target row within `p_limit` (default 25) given the prefilter tiering — an exact title match is tier 0 ([`matching.ts`](../../../src/features/task-commands/matching.ts)), so it should rank first, but "should" is not evidence. This is answerable by Vitest against the existing normalizer plus one pgTAP case, both cheap, and it is a gate on 2F.2 rather than on approving this phase. If it fails, the sibling-RPC fallback is unaffected and still available.

The fallback (sibling RPC over shared `private.` helpers) is acceptable only if the 2F.2 gate demonstrates concrete friction the above does not remove; a **third contract that shares nothing is prohibited** — that is the failure mode this phase exists to end.

**AI interaction.** None added. Surface buttons never touch a model; they enter the contract *below* the parse step. The model contract, prompts and schemas are untouched.

*(Revised, F1.)* **Where provenance lands, and how it reaches the operation.** The two version columns go on the ledger row the parse already writes ([`actions.ts:703-708`](../../../src/features/task-commands/actions.ts#L703-L708)). Revision 1 stopped there, and that was the defect: today that row is written with `source_type` and `source_id` both null — necessarily, because the parse precedes matching and no task exists yet — so nothing joins it to the operation that eventually results. Adding columns to an unjoinable row does not close ADR-053's residual risk; it renames the weak join from *(created_at ↔ deploy history)* to *(created_at ↔ ledger row)*.

The fix is already sitting in the schema. `ai_usage_events` has `source_type text` and `source_id uuid` (`202607160015:66-67`), both unused on this path, and `source_id` carries **no foreign key** — it is a correlation column, not a reference. The command's operation key is minted as a UUID at [`actions.ts:672`](../../../src/features/task-commands/actions.ts#L672), *before* the parse and therefore before the ledger write, and `apply_task_command` later stores it on the operation as `'taskcmd-v1:' || btrim(key)`. So the parse writes `source_type = 'task_command'`, `source_id = <that uuid>`, and the join from an operation to the prompt version that produced it is deterministic and owner-scoped, with no timestamps in it.

Two honest properties of this choice, stated rather than discovered later. **It is a correlation, not a foreign key:** a parse that is refused, abandoned or never applied leaves a ledger row whose `source_id` names no operation. That is correct and in fact desirable — provenance for refused proposals is exactly what a "why did the model produce this" investigation needs — but it means the column must never be read as a guarantee that an operation exists. **The allowlist moves in both places or neither:** `source_type` is validated by a table CHECK (`202607170018:8-9`) *and* independently re-validated inside the function body (`202607250055:127`), and `202607250055:12-13` records why they must be widened in the same migration ("the CHECK and the RPC guard disagreeing is a failure mode that surfaces only in production"). Since 2F.1 re-declares that function anyway, the literal costs one line in each of two places inside a migration that already exists — which is the whole reason F1 is resolvable without new infrastructure.

**Undo implications.** Consolidated surface writes gain real undo: operation rows recorded task-scoped, compensated by the already-registered Phase 2E handlers (reuse follows automatically if `apply_task_command` is reused). The fail-closed handler registry means a new `action_type` cannot be introduced unregistered. Undo surfacing reuses the existing history/undo affordances; no new undo UI is designed in this phase.

**Event generation / analytics impact.** No new event names are expected. If routing buttons through the command contract argues for a `commandOrigin` value such as `direct`, that is a bounded-vocabulary widening decided in 2F.2 — and per the M5 backlog note, the first new analytics addition is the moment to decide the catalog-table question rather than re-pasting three allowlists. Decide it then; do not pre-build it.

**Permissions / security.** The headline: closing PRD §16.4's residual risk. After 2F.4, a compromised or buggy client session cannot mutate a task or reminder except through validated, audited, rate-limitable RPCs. All new/changed functions follow the standing rules (SECURITY DEFINER only where forced, `search_path = ''`, caller validation, least-privilege grants). The confirmation-by-grants mechanism (ADR-047) is untouched.

**Coupling with previous phases.** 2F deliberately couples *into* Phase 2E's contract (that is its purpose) and touches Phase 2C only at the edges (materialization RPCs already validated; unaffected). One standing hazard inherited from 2E: tests that grep an RPC's migration text break when `create or replace` moves the authoritative body to a newer file — every slice that re-declares a function must move its text-pinned assertions in the same commit (recorded lesson, `STATE.md` Slice 2E.5 notes).

## 4. Database (conceptual only)

- **Expected migrations:** on the order of three to five, additive-first, each with the established post-deploy `DO`-block assertions. (1) Ledger provenance and its join: two nullable text columns on `ai_usage_events`, the `source_type` allowlist widened by the single literal `'task_command'` **in the table CHECK and the function body together**, and a re-declared `record_ai_usage` accepting the two new arguments **with defaults** — defaults are what let every existing ten-argument caller (including the Deno worker) keep resolving unchanged after the drop-and-recreate; the drop and the recreate must share one transaction so no window exists where the function is absent or ambiguous, and the `revoke`/`grant` pair (`202607250055:177-179`) must be re-issued inside it, because dropping a function drops its grants. *(Revised, F1: the allowlist widening is new to Revision 2 and is what makes this migration discharge the requirement rather than decorate it.)* (2) Reminder reconciliation: a one-off, idempotent, audited data correction over `scheduled` reminders, predicate to be fixed by the census (§14) — with the alternative (accept and document the firing) presented to the owner as an explicit choice before writing it. (3) Grant revocations on `tasks` (and `reminders` per the 2F.3 decision) as their **own late migration**, deployed separately.
- **RPC additions: zero.** *(Revised, F4.)* Revision 1 said "ideally zero" while recommending a mechanism that in fact required either a new read RPC or a widened Work projection. The replacement mechanism in §3 requires neither: it calls `list_task_command_candidates` as it exists today, with arguments it already defaults. The sibling-RPC fallback would still add exactly one, sharing private helpers, and is unchanged.
- **RPC removals:** none. No versioned RPC retires in this phase (ADR-037 lifecycle applies if 2F.2 finds one with no remaining caller).
- **RPC signature changes:** exactly one, `record_ai_usage`, in 2F.1 and nothing else in that slice. `list_task_command_candidates` is explicitly **not** touched: its "amendment window is closed by exhaustion" (`202607260059:2505-2508`) and any argument change would cost a `_v2` — a cost this phase has no reason to pay.
- **Indexes:** none anticipated; no new query shapes are introduced. *(This claim now holds. Under Revision 1's refuted mechanism it did not: widening the Work projection to nineteen fields would have added three relation joins to every rendered Work row, which is a new query shape with an index question attached. §3's replacement adds one call to an existing, already-indexed function on the click path only.)*
- **RLS impact:** none. Policies unchanged; only grants narrow.
- **`record_ai_usage` blast radius, named:** its signature is pinned by two `::regprocedure` casts, a `has_function` type array, hand-written generated types and the worker. All pins move in the same commit as the migration; CI's database job is the executable proof, exactly as ADR-053 anticipated.

## 5. Frontend (conceptual only)

- **New UX:** essentially none — deliberately. The Work surface keeps its buttons; the visible changes are honest ones: declared, localized error states from the closed vocabulary instead of a generic failure string; refusal rendered when the row is stale (the expected-pre-state guard) with a refresh affordance; undo availability on actions that previously had none.
- **Workflow changes:** manual task creation keeps its current form; it submits into the validated creation path. Manual reminder creation follows the 2F.3 decision.
- **Confirmation changes:** none. Surface buttons cover non-destructive transitions only; cancellation remains exclusively on the command console's confirmed path.
- **Error handling:** the `2E_*` mapping already localized for the console is reused; nothing throws out of a Server Action (standing rule).
- **Accessibility:** no new dialog or widget classes; existing focus/ARIA patterns and the jsdom-assertable gates apply to any touched component.
- **Localization:** all touched copy goes through typed feature `copy.ts` modules (ADR-036 mechanism); both locales, tested exhaustively per the outcome-vocabulary pattern.

## 6. Backend

- **Services affected:** `operations/actions.ts` (both write sites), `agent/actions.ts` (reminder authoring), `features/task-commands/` (payload builder reused, not forked). Workers untouched — this phase deploys no Edge Function change.
- **Execution flow:** button → Server Action → `buildApplyPayload`-equivalent shared builder → existing RPC → existing audit/undo/reminder-consistency machinery. One builder, per the convergence rule that `confirmation.ts` already follows.
- **API impact:** none externally; PostgREST surface changes only by the `record_ai_usage` re-declaration (compatible for existing callers via defaults).
- **Background jobs:** none added. No new queue consumers, no cron changes.
- **Validation:** every new boundary Zod-parsed; taxonomy remains the single source for eligible transitions (a button for an ineligible transition is not rendered *and* is refused server-side).
- **Idempotency:** client-minted operation keys per interaction, DB-enforced uniqueness — replay of a double-click returns the original outcome, per the existing contract.
- **Retries:** keyed on the declared failure policy, never the outcome (standing rule); no blind retry added anywhere.
- **Rollback strategy:** per slice, "stop routing": the old code paths are removed only in the same PR that proves the new routing green, and grants are revoked only after a full deployment's soak with the smokes executed. Re-granting is the trivial, tested rollback for 2F.4; no applied migration is ever reverted (standing posture).

## 7. AI

- **Prompt changes:** none. **Interpretation changes:** none. **Structured output:** unchanged. **Determinism:** unchanged — this phase adds no model call anywhere.
- **Provenance:** the parse's ledger row gains the prompt and strategy versions as data; the constants and their pinning tests already exist. This *strengthens* safety review of future prompt changes (a bad-command report joins to a version, not a deploy timestamp).
- **Confidence handling:** unchanged; the matching policy, thresholds and bands are not touched. The measured re-baseline (2F.5) is a measurement of the existing policy, not a change to it — any weight change would move `TASK_MATCH_POLICY_VERSION` and come to the pinned assertion, exactly as designed.

## 8. Analytics

- **New events:** none planned. **Modified:** possibly one bounded property-vocabulary widening (`commandOrigin`) if 2F.2 routes buttons through the command contract *and* chooses to report them; decided there, with the M5 catalog question decided at the same moment. **Removed:** none.
- **Dashboards:** none exist (M18's "17 events, zero readers"). 2F.5 ships the *minimal* reader — internal, owner-scoped, content-free aggregates over the command funnel (proposal rate, one-step rate, ambiguity rate, refusal reasons, no-match-to-creation rate). Its purpose is the §22 gate, not a BI surface; scope is capped at read-only aggregates of already-emitted events.
- **Telemetry / privacy:** unchanged posture — content-free events only, task content never in payloads, append-only ledger written through the documented RPCs.

## 9. Testing strategy

The organizing lesson is Phase 2E's sharpest: **a verifier that has never run is a claim, not a gate** (eight defects in three never-executed scripts, one assertion green while testing nothing). Every 2F gate is therefore designed to *execute against the real contract* before it is counted:

- **Unit (Vitest):** the shared payload builder, action-eligibility rendering, copy exhaustiveness over touched vocabularies, and — per ADR-052's pattern — a mirror test holding every `.mjs` contract-reader to the real imported constants by exact equality. No validation script may restate a contract it can read.
- **Integration:** Server Actions exercised through the dispatcher path end-to-end in jsdom, including refusal, stale, replay and undo renderings.
- **pgTAP:** re-declared `record_ai_usage` proven by catalog (signature, defaults, grants) *and* by behaviour (row written with and without the new arguments); grant revocations asserted positively (the revoked role provably cannot write) and the existing suites that pin current grants updated in the same commit; the reminder reconciliation proven idempotent and scoped (a healthy reminder is untouched — asserted, not assumed).
- **Playwright:** the Work-surface journeys (complete/wait/resume/reopen/create, plus undo and a stale-row refusal) on desktop and mobile, both locales; CI keeps the credential-free tier, the authenticated tier runs at deployment per house practice.
- **Remote validation:** each slice's smoke is written to run against the deployed contract and is **executed in the same session as its deployment** — never merged as "will run later". Smokes read vocabularies from source (ADR-052), create disposable fixtures, fail closed on cleanup, and must not race the interpretation drain (they create no entries; the known 2C/2D drain-race items stay separately tracked).
- **Deployment validation:** post-deploy `DO` blocks per migration; parity re-check before and after; the 2F.4 revocation deployment additionally runs the *full* existing remote suite, because revocation is the one change whose failure mode is "an unrelated surface stopped writing".
- **Rollback validation:** the 2F.4 re-grant script is tested against a disposable environment before the revocation deploys — the rollback itself must be an executed artifact, not a paragraph.

## 10. Deployment strategy

- **Rollout order:** strictly slice order (below); each slice merges and deploys independently, additive before revoking, provenance first (it is self-contained and discharges the recorded debt early).
- **Feature flags:** none needed. Consolidation swaps the implementation behind unchanged UI; the "flag" is the PR boundary. The one gated step is grant revocation, which is its own deployment.
- **Migration safety:** additive chain, single-transaction drop-and-recreate for the ledger function, reconciliation migration idempotent and re-runnable, revocations last and alone. PostgREST schema-cache behaviour after function re-declaration is verified in the deployment session (the PGRST205 lesson from the cleanup verifier).
- **Rollback plan:** per slice: route back (code revert) for 2F.2/2F.3; re-grant for 2F.4; nothing else requires one. No applied migration reverted, ever.
- **Observability:** deployment sessions record parity before/after, smoke exit codes, and journey counts in `STATE.md` — the Phase 2E discipline, kept.
- **Production validation:** the measured re-baseline (2F.5) doubles as the deepest post-deploy validation: it exercises match → preview → apply → undo against the deployed database with disposable fixtures.

## 11. Risk assessment (ranked)

1. **Contract-shape mistake in 2F.2 (architectural, highest).** Forcing surface actions through the command envelope could prove awkward, tempting a shortcut that becomes a third half-contract. Mitigation: a written design gate before code (reuse vs. sibling decided on demonstrated friction, both sharing the same private primitives), plus an architecture test forbidding any new module from writing `tasks` outside the contract.
2. **Revocation blast radius — and it includes the gate itself (migration/operational).** *(Revised, F5.)* Revision 1 called this "a forgotten writer". It is not: three known writers are the verification instruments 2F.4 proposes to verify itself with. [`remote-phase-2e-smoke.mjs:144`](../../../scripts/remote-phase-2e-smoke.mjs#L144) seeds tasks through the **authenticated** owner client — that is the aggregate smoke named as 2F.4's own acceptance gate. [`remote-supabase-smoke.mjs:258`](../../../scripts/remote-supabase-smoke.mjs#L258) and `:286` seed a task and a **reminder** the same way. And [`remote-editable-candidate-confirmation-smoke.mjs:797`](../../../scripts/remote-editable-candidate-confirmation-smoke.mjs#L797) inserts a task as a *second owner* — the repository's only executable proof that **RLS**, rather than a grant, denies a cross-tenant task write. Mitigation, in this order and not another: the §14 sweep is executed and published **before 2F.2 starts**, not before 2F.4; every fixture writer is re-seeded through the `service_role` client the same scripts already construct (`remote-phase-2e-smoke.mjs:52`, and [`remote-product-events-smoke.mjs:165`](../../../scripts/remote-product-events-smoke.mjs#L165) already seeds this way, so the pattern is precedent rather than invention); the re-fixtured suite is **green before the revocation migration is written**; revocation then ships last, alone, with a re-grant tested against a disposable environment first. The revocation *mechanism* itself is well precedented and is not the risk — `202607170016:196-244` already revokes `insert, update, delete` from `authenticated` on eight tables.
   **The evidence trade, recorded rather than discovered.** After revocation, a cross-tenant write through `authenticated` is refused by the grant before RLS is consulted, so the cross-owner insert assertion would still pass while proving nothing. Phase 2F therefore accepts, explicitly, that table-level RLS write-denial on `tasks` stops being provable through the `authenticated` role, and replaces that evidence with two things it can execute: cross-tenant denial asserted at the **RPC boundary** (`apply_task_command` against another owner's task raises `P0002`), which is the trust boundary that actually exists after 2F; and a pgTAP **catalog** assertion that the RLS policies on `tasks` still exist and are still forced. This trade is written into `SECURITY.md` in 2F.4, not left implied. It is a real reduction in one kind of evidence, and §11's "net security delta is strictly positive" is amended accordingly: the delta is positive on posture and negative on one class of proof, and both halves are now stated.
3. **`record_ai_usage` re-declaration — gated on an executed dry run (migration).** *(Revised, F3.)* Shared by every AI path; six-plus pinned artifacts move in lockstep. Revision 1 argued that ADR-053 had judged this too risky only *for a closeout slice*, and that as an opening slice it was "routine". That reads ADR-053 more favourably than ADR-053 reads. Its rejection has two independent legs (`DECISIONS.md:587`, `:589`): blast radius — "six-plus files that must move in lockstep, **verifiable only through CI**" — and closeout timing. Revision 1 answered the second and asserted the first away; and the mitigation it offered ("CI database job plus an executed remote smoke") is the same evidence ADR-053 already had in view when it wrote "verifiable only through CI". No new fact had appeared between the ADR and the proposal, both dated 2026-07-28. **Resolution: stop arguing and produce the missing fact.** 2F.1's provenance migration may not be written until a dry run has been *executed* against a disposable hosted project: the drop-and-recreate applied in one transaction, all six pins moved (`phase_2e_task_command_ai_usage.sql`'s two `::regprocedure` casts, `ai_usage_rls.sql`'s `has_function` type array, the generated types, and both Deno worker entrypoints), the grants re-issued and re-asserted, PostgREST's schema cache observed to settle, and one real call made from the worker path afterwards. The dry run's transcript merges as an artifact *before* the migration. If it does not pass, provenance leaves Phase 2F under the §0 drop-out condition. This is §9's own standard — "a verifier that has never run is a claim, not a gate" — applied to the change this phase is most tempted to exempt from it.
4. **Reminder reconciliation over-deletes (data).** A one-off correction that cancels a reminder a user wanted. Mitigation: audited, scoped by explicit predicate, preceded by a counted dry-run read presented to the owner, and reversible in the ordinary sense (reminders are re-creatable; the correction records what it cancelled).
5. **Text-pinned test drift (maintainability, recurring).** Re-declaring functions moves grep-pinned assertions; Phase 2E paid this twice. Mitigation: known hazard named in each slice's checklist; the plpgsql grammar guard ships before new bodies are written.
6. **Measurement scope creep (2F.5).** A "minimal reader" grows into a dashboard. Mitigation: scope stated as aggregates over existing events, no new storage, no new events; anything more is Phase 2G+.
7. **Security regression risk: low.** Nothing widens. The phase's net security delta is strictly positive (grants narrow, provenance improves audit).

## 12. Slice planning

**2F.1 — Ledger provenance and SQL guardrails.** *Objective:* discharge `2E-COMMAND-012`; land the plpgsql grammar-trap guard; record the decision ADRs (activity, semantic-retrieval gate, phase-letter reconciliation, and — new in Revision 2 — one superseding ADR-053's *reasoning* while preserving its decision, since its amortization premise no longer holds). *Rationale:* self-contained, and the guard protects every later slice's SQL. *Dependencies:* **the executed dry run of §11 risk 3, merged as an artifact, is a hard gate on writing the migration.** *Complexity:* Medium-small once the dry run exists; the dry run itself is the cost. *Acceptance (revised, F1/F3):* the dry-run transcript is in the repository and green; provenance columns populated for a real parse on the deployed project; **that same parse's ledger row carries `source_type = 'task_command'` and `source_id` equal to the operation key, and a join from the resulting `undo_operations` row back to the prompt version is demonstrated by an executed query in the deployment session** — a provenance column that cannot be joined does not count as delivered; the `source_type` allowlist proven widened in both the table CHECK and the function body; grants re-asserted after the drop-and-recreate; every signature pin updated and green; guard demonstrably catches the two known grammar traps; ADRs merged. *Deployment impact:* one migration; no behaviour change. *Rollback:* none needed (additive, nullable). *Drop-out:* if the dry run fails, this slice's provenance half leaves the phase; the guard and the ADRs stay.

## 13. Adversarial review of this proposal

Attacks attempted against the proposal, and what they changed:

- **"You are assuming the command envelope fits button clicks."** Partly conceded. The claim rests on `updated_at` being available (verified) and on operation-key minting patterns existing (verified in capture) — but *not* yet on demonstrated ergonomics of expected-pre-state for a twelve-column witness synthesized from a projection row that carries fewer columns than the preview does. That is a real unknown; it is why 2F.2 has an explicit design gate with a sanctioned fallback, and why §14 lists it as the top pre-code validation. The prohibition on a shared-nothing third contract is the non-negotiable, not the specific mechanism.
- **"Provenance-first is ceremony; nobody is debugging bad commands yet."** Rejected. It is first because it is *small, independent and already promised* (ADR-053 names Phase 2F), and because doing the scary-labelled change early, alone, with full CI evidence is precisely how to make it boring. Deferring it again would be the second consecutive phase to carry the same recorded risk.
- **"Reconciliation could be skipped — the rows will heal as 2E transitions touch them."** Rejected as default, but the alternative is explicitly offered to the owner in 2F.3: the do-nothing option means the heartbeat keeps firing reminders for cancelled/completed work — a user-visible wrongness with a known census query. Choosing it must be a recorded decision, not an omission.
- **"The measurement slice is a Trojan dashboard."** Conceded as a risk; scope hardened: no new events, no new storage, aggregates only, and the §22 gate ADR is the deliverable that matters — the reader exists to feed it.
- **"Deferring C1 (spend caps) is irresponsible for a product calling OpenAI."** Considered seriously. Held: the interim mitigations recorded at the hardening review stand, the environment is single-user with disposable data, and 2F adds *zero* new AI spend paths. The commitment made instead: Phase 2G is named, C1 is its first item, and 2F's closeout explicitly re-raises it rather than letting it age silently. If public signup opens before 2G, C1 jumps the queue.
- **"Grant revocation will break the smokes/e2e fixtures you forgot."** The strongest attack; answered structurally rather than confidently: the §14 sweep is a *gate* on starting 2F.2, revocation is sequenced last and alone, and the full remote suite runs in the revocation session. The proposal was revised to test the re-grant rollback *before* the revocation deploys.
- **"Replay/idempotency: a button click retried across a day reuses a stale witness."** True and acceptable: the contract's answer is a refusal with a refresh affordance, which is the designed behaviour for stale state — not a defect. Noted in 2F.2's acceptance so the refusal is rendered, not swallowed.
- **"Two definitions of Phase 2F is a paperwork problem you are over-rotating on."** Rejected: an agent-driven repo where `TODO.md` line 28 contradicts the phase you are executing is exactly how a future session builds the wrong thing. One ADR and two line edits are cheap insurance; they land in 2F.1 and 2F.6.

Revisions made after this review: rollback-tested-before-revocation added to 2F.4/§10; measurement scope capped harder; the reuse-vs-sibling decision reframed from a recommendation into a gated decision with the third-contract prohibition as the invariant; C1 escalation condition named.

## 14. Final recommendation

**Adopt Phase 2F as "One Write Path": 2F.1 provenance + guardrails → 2F.2 surface mutation convergence → 2F.3 creation/reminder convergence + reconciliation → 2F.4 revocation → 2F.5 measured matching (parallelizable) → 2F.6 closeout.** Remove semantic retrieval, recurrence, retroactive history, review invalidation, multi-target commands and the activity entity from Phase 2F entirely; the first two get named evidence gates, the rest get named future homes. Name Phase 2G "Operational Readiness" with C1 first.

**Implementation order:** exactly the slice order; 2F.5 may run concurrently from day one since it depends only on the already-deployed contract.

**Biggest unknowns (revised in Revision 2):**
1. ~~Envelope ergonomics for surface actions — can a projection row honestly supply the expected-pre-state witness?~~ **Resolved, and against Revision 1** (F4). It cannot: ten of nineteen required keys are absent from the Work projection, and `p_observed_before` has no honest render-time source. This was never an unknown — it was measurable from the migration and the projection query. What replaces it is a narrow, testable question, not an architectural one: does an exact-title query return the clicked task within `p_limit` for each action's eligible-status set? That is 2F.2's pre-code gate.
2. The complete writer inventory for `tasks`/`reminders` across `src/`, `scripts/`, `e2e/`, and any pgTAP fixture that relies on `authenticated` DML. **Partially resolved and re-prioritized** (F5): four writers are already named in §11 risk 2, three of them are 2F.4's own verification instruments, and one is the only executable proof of cross-tenant RLS. The sweep is now a gate on **2F.2**, not on 2F.4, because its result can change more than one slice's plan.
3. Whether defaulted parameters on the re-declared ledger function truly leave every existing named-argument caller (app + worker + smokes) untouched. **Escalated from an unknown to a required artifact** (F3): no longer "provable in CI before merge" but *proved by an executed dry run against a disposable hosted project before the migration is written*.
4. The orphaned-reminder census: how many rows the reconciliation would touch (a read, not a migration). **Unchanged, and still blocking 2F.3's migration** — see F9 in §15's carry-forward list, which additionally requires the census to distinguish reminders whose task is terminal, whose task has null `due_at`, and which have no task at all.
5. The reminder-authoring product decision: consolidate behind a validated path, or record a scoped exception. **Unchanged, owner-facing.**

**Validate before writing a single line:** execute the writer sweep (2) and the reminder census (4); execute the ledger dry run (3) if provenance is to stay in the phase; run 2F.2's exact-title gate; get the owner's decision on (5) and on the reconciliation-vs-accept choice; approve this scope so the PRD can be written against it. Only then write the Phase 2F PRD in the house format — requirement families, epics, per-slice acceptance, and gates that are designed to be *executed*, because the single sharpest lesson this repository has produced is that a gate that has never run is a claim, not a check.
