# `2H-RATE` ceilings — owner decision request (gate G-2H.5)

- **Status:** **AWAITING OWNER SIGNATURE. G-2H.5 is RED and slice 2H.3 cannot begin.**
- **Purpose:** the PRD's §14 value sheet leaves two ceilings deliberately blank. This document gives the owner what is needed to choose them, and **nothing here is written into the PRD or into any implementation until the owner signs.**
- **Rule this document obeys:** no ceiling is invented. Every option below is derived from a measured figure, an existing enforced ceiling, or a provider constraint — and where a figure is unknown, it says so rather than estimating.

---

## 1. Read this first: the surfaces are already partly bounded

`2H-RATE` does **not** arrive at an unprotected surface. SH.6 shipped and deployed per-user infrastructure quotas (`202608050076`, ceilings owner-signed under ADR-077, stored as runtime parameters in `private.quota_ceilings` and changeable by `UPDATE`, never a migration).

| Already enforced today | Value | Bounds |
| --- | --- | --- |
| `entries_per_day` | **300** / user / UTC day | capture, and therefore the `interpret_entry` fan-out |
| `live_jobs_per_user` | **50** concurrent `pending`/`running`/`failed` | total queued work per user |
| `drain_claims_per_owner_per_tick` | **5** | one user cannot occupy the whole drain |
| `attachments_per_day` | **50** / user / UTC day | upload volume |
| `storage_bytes_per_user` | **500 MiB** | upload total size |
| `storage_objects_per_user` | **200** | upload total count |
| attachments per entry | **5** | upload fan-out |
| Max file size | **25 MiB** | single upload |
| AI input bounds (`AI_INPUT_BOUNDS`) | capture/chat **12 000** chars, memory **4 000**, file text **100 000** | how much text reaches a model per call |

**The honest consequence:** a *daily* AI ceiling is largely redundant with `entries_per_day = 300`, and a *daily* upload ceiling is redundant with `attachments_per_day = 50`. **C1's gap is not daily volume — it is rate.** Nothing today stops a user from spending their entire daily allowance in ten seconds, which is what exhausts provider concurrency, inflates cost spikes and makes the service unavailable for everyone else.

**So both ceilings below are specified per hour, not per day, and their job is burst control.** If the owner would rather set daily ceilings, the correct answer is to *change the SH.6 parameters* — no new mechanism is needed, and `2H-RATE` should be reduced accordingly.

## 2. Scope questions the owner must settle alongside the numbers

The ceiling means nothing without these. Proposed answers are marked; each is a decision, not a default.

| Question | Proposed answer | Why |
| --- | --- | --- |
| **Which actions consume an AI slot?** | Every call that reaches a provider: capture interpretation, entry reprocessing, chat turns, task-command parse/preview, memory proposals, file analysis, and **embeddings when generated by a user-initiated action**. | The limiter protects the provider boundary; a call that reaches the provider consumes the resource regardless of which feature made it |
| **Which actions consume an upload slot?** | One slot per accepted upload request, counted **before** the storage write. | SH-QUOTA-004's refusal already precedes the write; the limiter matches so a refused upload leaves no object |
| **Do retries consume a new slot?** | **Worker retries: no. User-initiated retries: yes.** | A bounded backoff retry is the system's own recovery, and charging it turns one failure into a lockout. A user pressing "reprocess" is new demand |
| **Do background jobs consume a slot?** | **Yes, against the job's owner** — but the drain's own `drain_claims_per_owner_per_tick = 5` is the primary bound, and the limiter must not double-refuse work the drain already admitted. | Otherwise the biggest provider consumer in the product is exempt from the control meant to bound provider consumption |
| **Fail-open or fail-closed?** | **Fail-closed** (`2H-RATE-005`, already a declared requirement). | A limiter that admits traffic when its state is unreadable removes itself exactly under load |
| **Is the window fixed or sliding?** | **Sliding**, over the SH.5 throttle mechanism. | A fixed hourly window permits a double burst across the boundary — 2× the ceiling in two minutes |
| **Who is exempt?** | **Nobody, including the owner.** | A control the owner is exempt from is a control nobody has tested (the lesson from the always-passing CAPTCHA test key) |

## 3. AI operations per user — three options

Anchor: `entries_per_day = 300` is the enforced daily bound. Observed real usage is **effectively zero** — the funnel is measured and empty, and the hosted `jobs` table holds **4 jobs total, the newest 2026-08-02**. There is no usage distribution to fit a curve to, and this document will not pretend otherwise.

| | **Option A — Conservative** *(recommended default)* | **Option B — Generous** | **Option C — Strict** |
| --- | --- | --- | --- |
| **Ceiling** | **60** AI operations / user / **rolling hour** | 150 / user / rolling hour | 30 / user / rolling hour |
| **Relationship to `entries_per_day`** | 5 hours of sustained use to exhaust the 300/day allowance | exhausts the daily allowance in 2 hours | 10 hours to exhaust |
| **Normal use** | A heavy session — 20 captures, 20 chat turns, 20 command previews in one hour — passes. Very hard to hit by hand | Anything a human does by hand passes | A determined power hour (a long chat plus bulk capture) could touch it |
| **Abuse** | A script is refused within ~1 minute of sustained hammering | A script gets 150 provider calls per hour per account; with BYOK the user pays, but the product's concurrency and reputation are still consumed | Refuses a script almost immediately |
| **Cost of being wrong** | Low both ways | **A limiter that never fires is not a control** — the C1 finding would remain open in substance while appearing closed | Real users hit it, and a false refusal on a personal-agent product is a trust failure |
| **Consequence if chosen** | `2H-RATE-004`'s concurrency proof uses 60 as `M`; refusal copy needs a "try again shortly" register in both locales | Same, with `M = 150` | Same, plus the refusal copy must be genuinely apologetic, because it *will* be seen |

**Why A is the conservative default:** it is the only one of the three that both (a) cannot plausibly be reached by a person using the product as intended, and (b) demonstrably fires against a script. It bounds burst without re-litigating the daily allowance the owner already signed.

## 4. Upload operations per user — three options

Anchor: `attachments_per_day = 50`, 25 MiB per file, 500 MiB total. Uploads are far more expensive per operation than AI calls (bytes, storage, a `process_attachment` job, then an AI call on the extracted text) and far rarer in normal use.

| | **Option A — Conservative** *(recommended default)* | **Option B — Generous** | **Option C — Strict** |
| --- | --- | --- | --- |
| **Ceiling** | **20** uploads / user / **rolling hour** | 50 / user / rolling hour (the whole daily allowance in one hour) | 10 / user / rolling hour |
| **Normal use** | Uploading a batch of documents in a sitting passes; 20 files/hour is already atypical | Any human batch passes | A genuine bulk import session is refused partway |
| **Abuse** | Bounds the byte-rate a single account can drive at ~500 MiB/hour worst case — equal to the entire per-user storage quota, so the storage ceiling binds first | Permits the full daily allowance as one burst, which is precisely the burst C1 describes | Strong burst protection at real cost to a legitimate import |
| **Interaction with storage quota** | `storage_bytes_per_user = 500 MiB` binds before this in the worst case, so this ceiling's real job is bounding **job fan-out and AI follow-on**, not bytes | Same, but the fan-out is 2.5× | Same |
| **Cost of being wrong** | Low | The upload path is the most resource-expensive surface in the product; a generous burst ceiling here is the least defensible of the six options | Bulk import — a plausible real workflow — becomes painful |

**Why A is the conservative default:** it leaves the storage quota as the binding constraint on bytes (where it belongs) while bounding the job-and-AI fan-out that one upload burst can trigger.

## 5. Provider and platform constraints — stated with their confidence

| Constraint | Status | Note |
| --- | --- | --- |
| OpenAI per-key rate limits (RPM/TPM) | **NOT READ. Unknown.** | Under BYOK each user supplies their own key, so the applicable limit is **per user's own account tier** and is not knowable from this repository. This is a genuine gap and is not estimated here |
| Supabase Edge Function concurrency | **NOT READ** for the current plan | Bounds how many `process-jobs` invocations run at once; `drain_claims_per_owner_per_tick = 5` is the app-side bound already in place |
| GoTrue provider limits | **Read and recorded** under SH-THROTTLE-005 | The auth surface only; it does not bound AI or upload |
| Postgres connection limits | Not a binding constraint at this scale | 4 jobs total to date |

**The BYOK consequence, stated plainly:** because the user pays, an AI rate limit is **not a spend control** — `2H-RATE-006` already forbids it becoming one. Its purpose is availability, fairness across users, and bounding this product's own reputation with providers. If the owner's goal were cost, this is the wrong mechanism and the honest answer would be that BYOK already solved it.
