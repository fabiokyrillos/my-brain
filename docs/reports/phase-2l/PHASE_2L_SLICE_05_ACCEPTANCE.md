## 1. Telemetry — the phase declared nothing, and that is the finding

`product_events.event_name` and every property enum are **database
constraints**. A new event name costs a migration; OD-2L-2 option A signed the
phase's single allocation away and slice 2L.3 let it lapse. So Phase 2L reports
through the vocabulary already deployed:

| What | Event | Properties |
|---|---|---|
| quick edit, and each applied bulk item | `task_command_applied` | `commandOrigin: work`, a closed outcome, `applyRoute`, `replayed`, policy version |
| undo from a Work surface | `task_command_undone` | `commandOrigin: work`, a closed `undoResult`, policy version |

`undoWorkOperation` gained the second emission in this slice. **Nothing else
changed**: no name, no property, no builder.

**`failed` has no member of its own** in the deployed `undoResult` enum. It maps
to `refused`, which is what the router's own refusals report and is true of what
happened — rather than a new value the CHECK would reject.

### Selection and bulk preview are `not-built-by-rule`

Neither has an admitting name. Declaring `work_selection_changed` would produce a
producer the deployed CHECK rejects — **a vocabulary that is declared and
unwritable, which is exactly what cost `202608080087` and `202608090089`**.
Inventing it to satisfy `2L-METRICS-005` would trade that requirement against
`2L-METRICS-003`, and buy a third correction.

The refusal is **mechanical**: `phase-2l-telemetry-guard.test.ts` asserts that no
such name is declared and that no Phase 2L migration exists to make room for one.

### What the guard asserts, by name

- both events are in the application vocabulary **and** appear in the migration
  chain, so they can actually be written;
- both are emitted from the Work surfaces, so neither is a producer with no
  writer;
- the two Work-only modules emit **nothing** outside them, and the Work undo
  function emits exactly one event — scoped that way because
  `task-commands/actions.ts` is shared with the console and legitimately carries
  that surface's whole vocabulary;
- no builder produces a `title`, `note`, `description`, name, query or free-text
  property;
- **no emitter imports the sensitivity derivation at all** (`2L-PRIVACY-008`);
- no Work path constructs a provider, records usage or requests a rate-limit slot.

`scripts/generate-phase-2l-traceability.mjs` extracts the 82 declared
requirements from the PRD and the classification of each from the six slice
records, and it emits nothing at all unless every one of the following holds:

- every declared requirement is classified **exactly once**;
- no classification exists for a requirement the PRD does not declare;
- every citation is long enough to resolve;
- every `partial` and `undelivered` names a remainder **and** a destination;
- every `not-built-by-rule` names an ADR or a signed decision;
- **no migration exists for this phase** — the budget is reconciled by looking,
  not by restating;
- no row contradicts a signed decision: a matrix claiming a fourth view, a stored
  classification, a sensitivity column, a gesture or a spent migration is a
  refusal, not a row.

`phase-2l-traceability.test.ts` proves the refusals **by mutating a copy of the
repository** — an unclassified requirement, a duplicate id, an unresolvable
citation, a partial with no remainder, and a row that contradicts a signed
decision — because a generator whose refusals have never fired is a generator
nobody has tested.

Added after an independent review found that two rows were classified `partial`

### 6.1 `2L-CLOSE-004` — executed, read-only

`2L-CLOSE-004` requires the phase to state, **from a live reading rather than
from a filename**, whether hosted parity moved. The original close reported it
from the migration chain and called itself `partial` for exactly that reason.

The reading was executed:

```
npx supabase migration list --linked
```

| Check | Result |
|---|---|
| Rows returned | **89** |
| Rows where `Local` ≠ `Remote` | **0** |
| Local-only (a migration not applied remotely) | **0** |
| Remote-only (a migration not in the repository) | **0** |
| Head | **`202608090089`** |

**Nothing was written.** No migration was applied, nothing was deployed, no
fixture was created, and the command is read-only by construction. The signup
rollout gate is unchanged and was not touched.

Parity is therefore stated from a live reading, and `2L-CLOSE-004` is **built**.

### 6.2 `2L-BULK-011` — the missing proof was executed, so the row is `built`

The original row read `partial` with the remainder *"none in behaviour"*, which
is not a remainder. A `partial` that has nothing outstanding is a classification
being used to preserve a count, and the traceability vocabulary has no room for
one — so the generator now **refuses** it (§6.3).

Re-assessed against the requirement's own text, one claim turned out to be
argued rather than proved: that `ineligible` is **unreachable** for an id the
caller does not own. That is the only place a differentiable existence signal
could have hidden. It is now driven as two runs over the same id — present in
the owner-scoped resolution it yields `ineligible`, absent from it the same id
yields `unresolvable` — with a third test proving no refusal carries task
content whatever its cause.

With that executed, nothing in behaviour, proof or decision is outstanding, and
the row is **built**. **No remainder was invented to preserve the previous
count.**

### 6.3 The generator now refuses a vacuous partial

`partial` and `undelivered` already had to name a remainder. They now also have
to name a **real** one: the generator refuses a row whose remainder is "none",
says no behaviour or proof is pending, or points only at a record that is
already complete.

The refusal is proved by a fixture that plants exactly that row, executes the
generator, asserts it fails, restores a valid classification and asserts it
passes — and the existing refusals are re-asserted in the same run, so the new
rule cannot have been bought by weakening an old one.

### 6.4 What this correction did not do

No functional code, no UX change, no migration, no deployment, no database, RLS,
grant, policy or Auth change, no signup or rollout change, no `2M-*` requirement
or artifact, and **no A13 retarget**. One test file gained three cases; every
other change is a document, the generator, or the guard.
