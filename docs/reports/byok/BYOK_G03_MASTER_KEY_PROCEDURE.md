# BYOK G-0.3 — master-key generation and distribution procedure

**Pre-code gate G-0.3** of [`BYOK_IMPLEMENTATION_PLAN.md`](../../BYOK_IMPLEMENTATION_PLAN.md):
*"The written procedure, and four distinct keys provisioned (production, preview, test,
local), none in the repository."*

**Status (2026-08-01): the procedure is written; `local` and `test` are provisioned and
verified; `preview` and `production` are deferred to the point of use by owner decision.**
§5 is the record as of 2026-07-31 and is left standing; **§7 supersedes its `local` and
`test` rows**. The deferral is `ADR-069` / Amendment A-1 of the implementation plan.

---

## 1. What is being provisioned

Two secrets per environment, four environments, **eight distinct values**. No value is
ever shared between environments — that is what makes the environment separation
`BYOK-MASTER` requires real rather than nominal.

| Variable | Purpose | Shape |
| --- | --- | --- |
| `BYOK_MASTER_KEY` | AES-256-GCM key that wraps every user credential | 32 random bytes, base64 |
| `BYOK_FINGERPRINT_PEPPER` | HMAC-SHA256 pepper for credential fingerprints | 32 random bytes, base64 |

**The pepper is separate from the master key on purpose.** A fingerprint exists so the
product can say "this is the key ending 4f2a" and detect a re-paste without decrypting.
Deriving it from the master key would mean one compromise yields both the ability to
decrypt and the ability to correlate fingerprints across users.

---

## 2. Generation

Run once per environment, per variable. Nothing is written to disk by this command.

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

**Requirements the value must meet**, all enforced by `decodeMasterKey` at startup:

- valid base64;
- decodes to exactly 32 bytes;
- present. An absent or malformed value **fails the process to start** and never falls
  back — a process that boots without a usable key would accept credential writes it can
  never read back, and the owner would discover that at the moment they most needed the
  key.

---

## 3. Distribution, per environment

| Environment | Where the value lives | Who provisions it |
| --- | --- | --- |
| **local** | `.env.local`, git-ignored | the developer |
| **test** | `.env.test.local`, git-ignored; CI sets it as a job-level env var | the developer / CI config |
| **preview** | the hosting platform's preview environment secrets, **and** the Supabase Edge Function secrets for the preview project | **owner** |
| **production** | the hosting platform's production environment secrets, **and** the Supabase Edge Function secrets for the production project | **owner** |

**Both runtimes need the value in both places.** The Next.js application reads
`process.env.BYOK_MASTER_KEY`; the Edge Function reads `Deno.env.get("BYOK_MASTER_KEY")`.
Setting it in one and not the other yields an application that can encrypt and a worker
that cannot decrypt — which surfaces as every background job failing on a credential that
is provably correct.

Edge Function secrets are set with:

```bash
supabase secrets set BYOK_MASTER_KEY=... BYOK_FINGERPRINT_PEPPER=... --project-ref <ref>
```

**Never** with `--linked` against a project you have not confirmed, and never from shell
history that persists.

---

## 4. Rules

1. **No value enters the repository.** Not in a migration, not in a function body, not in
   `.env.example`, not in a comment, not in a test fixture. `.env.example` gains both
   names with **empty** values only. A CI chain-scan (BYOK.1 task 1.8) asserts this.
2. **No value is logged.** Not at startup, not on failure, not truncated, not
   fingerprinted into a log line.
3. **Environments never share a value.** A preview key that also opens production makes
   every preview deployment a production credential store.
4. **Rotation is a two-key window, not a swap.** `key_version` exists so an old key can
   decrypt while a new one encrypts. BYOK.6 owns the runbook; this gate only requires that
   the values be distinct and separately replaceable.
5. **Losing the master key loses every credential.** That is the design, not a defect: the
   ciphertext is useless without it. BYOK.6's recovery drill is executed against a
   disposable project precisely so this is demonstrated rather than assumed.

| preview | — | — | **BLOCKED — owner action** |
| production | — | — | **BLOCKED — owner action** |

### Why this loop did not generate the local and test values

It could have, and deliberately did not. Writing a real 32-byte key into `.env.local` on
this machine would put live key material into an environment the loop also commits from —
and the one rule this gate exists to enforce is that **no value enters the repository**.
The generation command is one line (§2) and the developer runs it once. The code does not
depend on the value existing until BYOK.1's tests run, and those tests generate their own
ephemeral keys, as `scripts/byok-crypto-interop.mjs` already does.

### Why preview and production are blocked

Provisioning them means writing secrets into the hosting platform's secret store and into
the Supabase Edge Function secrets for two projects. That is an **administrative control
this loop cannot reach without extracting or exposing credentials**, which is one of the
initiative's stated stop conditions.

**This does not block BYOK.1 or BYOK.2.** Those slices are schema, crypto and RPC work,
tested against ephemeral keys. What preview and production gate is **deployment** of the
credential system — which is Phase 2H's concern, not BYOK.1's.

Authorized by `BYOK-GATE-DEC-2` / Amendment A-1.1. Four values generated:
`crypto.randomBytes(32)`, base64-encoded, one `BYOK_MASTER_KEY` and one
`BYOK_FINGERPRINT_PEPPER` per environment.

### Pre-conditions, proven before any value was written

lands the permanent chain-scan in the repository and in CI, where it cannot read a
developer's `.env.local` and therefore asserts the complementary property: that the two
variable names appear with **empty** values in `.env.example` and that no high-entropy
32-byte-shaped literal appears in any migration, function body or source file. The two
scans check the same rule from the two sides available to them.

`preview` and `production`. Deferred to the point of use by Amendment A-1.2, with the

## 8. A third secret — `BYOK_RATE_LIMIT_PEPPER` (2026-08-01)

`ADR-070` adds `credential_validation_attempts.ip_hash`, an `HMAC-SHA256` over a
canonicalized IP. Its key is a **third independent secret**, and §1's "two secrets per
environment, four environments, eight distinct values" becomes **three secrets per
environment, four environments, twelve distinct values**. §1's table is otherwise unchanged
and this row is added to it:

| Variable | Purpose | Shape |
| --- | --- | --- |
| `BYOK_RATE_LIMIT_PEPPER` | HMAC-SHA256 key for the validation-throttle IP hash | 32 random bytes, base64 |

### Why a third rather than reusing either existing one

The same argument §1 already makes for keeping the fingerprint pepper separate from the
master key, applied once more — and it is **strongest** here. The rate-limit pepper is the
most widely handled of the three: it is touched on every validation attempt, including
failed and throttled ones, which is exactly the traffic an attacker generates. Coupling
that to the ability to decrypt credentials would be the worst pairing available.

Three secrets, three capabilities, and no single compromise that yields two.

### Executed provisioning — `local` and `test`

Same procedure, same evidence rule, same five pre-conditions re-verified before writing
(both files git-ignored, neither tracked, no script printing the name — at generation time
it appeared only in the three governing documents that name it and never value it — no
shell tracing, no persistent history). Generation, writing and verification again happened
**inside one Node process**, so no value crossed a command line.

**The generator refuses to overwrite an existing value.** Rotating `BYOK_MASTER_KEY` by
accident would invalidate every ciphertext already sealed under it, so the script adds the
new name and leaves the other two alone.
