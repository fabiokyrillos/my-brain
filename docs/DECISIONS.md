# Architecture Decision Record

Last updated: 2026-07-29

This file is append-only for accepted architectural decisions. Amend a decision by adding a new ADR that supersedes it; do not silently rewrite project history.

## ADR-001 — Supabase as the application backend

- **Date:** 2026-07-16
- **Status:** Accepted
- **Context:** The product needs authentication, relational persistence, file storage, row-level authorization, server-side functions, and scheduled database operations.
- **Problem:** Building and operating independent services for every backend concern would slow the pre-MVP and duplicate infrastructure.
- **Alternatives considered:** Custom Node.js API with managed PostgreSQL; Firebase; Supabase.
- **Decision:** Use Supabase Auth, PostgreSQL, Storage, RLS, RPCs, and Edge Functions as the backend substrate while keeping application/domain behavior in explicit server actions, SQL functions, and AI service modules.
- **Reason:** It provides the required primitives with a small operational footprint and preserves PostgreSQL portability.
- **Consequences:** Schema and policies are production code; migrations and pgTAP validation are mandatory. Supabase must not become a substitute for domain boundaries or ownership validation.

## ADR-002 — PostgreSQL and pgvector for semantic memory

- **Date:** 2026-07-16
- **Status:** Accepted
- **Context:** The personal knowledge system must store structured entities and retrieve semantically related content.
- **Problem:** A separate vector database would introduce synchronization, tenancy, and operational complexity during the pre-MVP.
- **Alternatives considered:** Dedicated vector database; external search service; PostgreSQL with `pgvector`.
- **Decision:** Store embeddings in PostgreSQL using `pgvector`, with HNSW indexes and user-scoped RLS.
- **Reason:** It keeps relational and semantic data transactionally close and uses the existing Supabase platform.
- **Consequences:** Embedding dimensions/model changes require migrations; vector queries must retain tenant filters and be measured before scale-up.

## ADR-003 — Event-oriented heartbeat with scheduled evaluation

- **Date:** 2026-07-16
- **Status:** Accepted
- **Context:** The agent should proactively surface meaningful items without becoming noisy.
- **Problem:** Pure polling or unconditional daily digests ignore user state, quiet hours, cooldowns, and relevance.
- **Alternatives considered:** Fixed cron notifications; application-only polling; database-evaluated heartbeat events.
- **Decision:** Evaluate candidate events in database functions, persist heartbeat runs/notifications, and invoke evaluation through a scheduled worker.
- **Reason:** Database-side evaluation can enforce idempotency and preference-aware limits near the data.
- **Consequences:** Timezone, locale, locking, per-user failure isolation, retry, and delayed-delivery semantics must be explicit. Sprint 1.5 hardens these guarantees before expanding heartbeat scope.

## ADR-004 — Row-level security as the tenant boundary

- **Date:** 2026-07-16
- **Status:** Accepted; hardening completed in Sprint 1.5 (see ADR-014)
- **Context:** Every user-owned record must remain isolated even if client/server queries are incorrect.
- **Problem:** Application-only filters are insufficient as a security boundary.
- **Alternatives considered:** Service-role-only backend access; shared tables with application filters; user-scoped RLS.
- **Decision:** Force RLS on owned tables and authorize rows using `auth.uid()`, with relationship ownership enforced through composite constraints or validated RPCs.
- **Reason:** Defense in depth and database-enforced tenant isolation.
- **Consequences:** Generic CRUD policies are not acceptable for append-only or domain-controlled tables. Policies, grants, RPC security, and cross-user denial require pgTAP coverage.

## ADR-005 — Typed AI provider, routing, and immutable usage ledger

- **Date:** 2026-07-16
- **Status:** Accepted; deployed and verified in Sprint 1.5 (see ADR-014)
- **Context:** Different AI operations need different quality/cost profiles and every provider call must be explainable.
- **Problem:** A single hard-coded model hides operational cost and makes future model changes risky.
- **Alternatives considered:** One global model environment variable; model choice in every call site; central typed routing and pricing catalog.
- **Decision:** Route typed AI operations through a central model profile, calculate costs in integer micro-dollars, and record immutable per-call usage events tied to user and operation.
- **Reason:** Central routing avoids drift and makes costs auditable without floating-point errors.
- **Consequences:** Provider usage must be recorded immediately after a successful provider response, even if downstream persistence fails. Pricing migrations and behavioral cost tests are release gates.

## ADR-006 — Durable AI jobs through a database queue and Edge Function

- **Date:** 2026-07-16
- **Status:** Accepted; operational hardening pending
- **Context:** Attachment processing and other expensive AI work must not block request/response flows.
- **Problem:** In-request processing is fragile and cannot safely retry.
- **Alternatives considered:** Synchronous server actions; external queue; PostgreSQL queue plus Supabase Edge Function.
- **Decision:** Persist owned jobs in PostgreSQL and process them through the authenticated `process-jobs` Edge Function.
- **Reason:** It reuses the platform while making asynchronous state observable.
- **Consequences:** The function must authenticate every request manually when JWT verification is disabled at the platform layer. Job leases, stale-job recovery, retry/backoff, and scheduled invocation remain required operational safeguards.

## ADR-007 — Permanent project-state documentation

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** Agent conversations can be lost and must never be the source of truth.
- **Problem:** A future maintainer cannot safely resume work if status, decisions, changes, and backlog exist only in conversation history.
- **Alternatives considered:** Rely on Git history and implementation plans; maintain a single status document; maintain four purpose-specific living documents.
- **Decision:** Maintain `STATE.md`, `DECISIONS.md`, `CHANGELOG.md`, and `TODO.md` at every completed feature or phase.
- **Reason:** Together they separate current truth, architectural rationale, historical changes, and future work.
- **Consequences:** A feature/phase is not complete until all four files accurately reflect it. Documentation changes belong in the same commit as the completed work whenever practical.

## ADR-008 — Sprint 1.5 is a foundation gate, not a feature phase

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** The Phase 1 review found critical correctness, authorization, navigation, background-processing, and verification gaps.
- **Problem:** Continuing the roadmap would compound risk and make later behavior depend on unstable foundations.
- **Alternatives considered:** Continue directly to Phase 2; fix only security blockers; run a dedicated hardening sprint.
- **Decision:** Complete Sprint 1.5 in the fixed order: permanent documentation, critical fixes, AI routing/cost completion, full quality gate, final documentation and report.
- **Reason:** It reduces compounding risk without restarting architecture or expanding scope.
- **Consequences:** No new product capability is accepted in this sprint. Deferred improvements must be explicit in `TODO.md` and the closing report.

## ADR-009 — Explicit PKCE continuations and local credential policy

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** Signup and recovery relied on implicit Supabase defaults; recovery targeted a missing page and authenticated auth routes were redirected away from reset.
- **Problem:** The application could send a recovery email without providing a complete, safe password-update journey, while raw provider errors and a visible unconfigured Google action created unreliable authentication behavior.
- **Alternatives considered:** Keep Supabase defaults; implement client-fragment recovery; use explicit server-side PKCE callback continuations with validated forms.
- **Decision:** Use explicit same-locale callback URLs and allowlisted continuations, validate credentials with Zod, require a 12-character mixed password plus confirmation, update the password only in an authenticated recovery session, then sign out and require a fresh login. Hide Google OAuth until its provider is configured and verified.
- **Reason:** The server-side PKCE flow matches the SSR architecture, prevents open redirects, gives deterministic errors, and avoids presenting an integration that cannot succeed.
- **Consequences:** Supabase redirect allowlists must include the callback URLs in each environment. Changing the password policy later requires coordinated UI/schema/test updates. Google OAuth returns only through a future ADR and end-to-end proof.

## ADR-010 — Mobile primary navigation with accessible overflow

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** The desktop rail exposed the application areas, but the mobile bar rendered only the first four entries and quick capture.
- **Problem:** Most authenticated destinations were not visibly reachable on mobile without a direct URL.
- **Alternatives considered:** Put all links in the bottom bar; replace the bar with a drawer; keep four primary links and expose the remaining destinations in a native overflow menu.
- **Decision:** Preserve Home, Today, Inbox, Tasks, and quick capture as the persistent mobile controls, then expose every remaining destination in a localized native `details/summary` overflow menu.
- **Reason:** It keeps the frequent actions stable, uses keyboard-accessible browser semantics, and makes the complete information architecture reachable without crowding the viewport.
- **Consequences:** New authenticated destinations must be classified as primary or overflow and added to the mobile navigation regression test. The overflow must retain 44-pixel touch targets and remain within the viewport.

## ADR-011 — Least-privilege RLS plus database-enforced relationship ownership

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** Owner-only CRUD policies protected table rows but still allowed direct mutation of domain-controlled history and relationships could reference another user's guessed entity ID.
- **Problem:** Checking only the relationship row's `user_id` does not prove ownership of every referenced entity, and mutable audit/worker records weaken invariants.
- **Alternatives considered:** Application-only validation; policy subqueries on every relationship; composite ownership FKs plus validated triggers/RPCs.
- **Decision:** Revoke unneeded direct mutations, route domain writes through validated security-definer RPCs/service workers, enforce concrete relationships with `(user_id, id)` FKs, and validate polymorphic targets with ownership triggers.
- **Reason:** The database remains authoritative even when a client or server action is bypassed, while legitimate direct user commands retain only the grants they need.
- **Consequences:** New owned entity tables need a composite ownership key before they can participate in relationships. New domain-controlled writes require an explicit RPC/worker and denial coverage.

## ADR-012 — Lossless, user-local heartbeat evaluation

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** The previous wrapper created notifications before applying caps, used database dates in dedupe keys, and could discard over-cap work or stop a batch on one user failure.
- **Problem:** Proactivity cannot lose reminders, repeat around local midnight, ignore locale, or allow concurrent evaluation for one user.
- **Alternatives considered:** Keep post-processing caps; move heartbeat to the application worker; replace the SQL evaluator with a single candidate-first function.
- **Decision:** Select/rank candidates before insertion, use local day boundaries and localized destinations, enforce a rolling task cooldown, lock per user, keep over-cap items pending, sanitize failure records, and isolate batch failures.
- **Reason:** Candidate-first SQL preserves deterministic, auditable behavior near the source data without adding another scheduler.
- **Consequences:** Heartbeat candidate types remain intentionally narrow. Any new signal must define priority, cooldown, dedupe, quiet-hour, locale, and cap semantics before release.

## ADR-013 — Append-only AI ledger with database-side complete aggregation

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** Client-side aggregation was capped at 5,000 rows and provider usage could be recorded only after later domain persistence succeeded.
- **Problem:** Successful paid calls could disappear from local cost history, and totals would become incomplete as the ledger grew.
- **Alternatives considered:** Paginate and aggregate every ledger row in Next.js; maintain mutable rollup tables; aggregate the immutable ledger in a caller-RLS database function.
- **Decision:** Record every successful provider call immediately, snapshot its applicable price in an append-only/idempotent ledger, and compute complete totals/breakdowns with `get_ai_cost_summary` under the caller's forced RLS.
- **Reason:** This preserves accounting evidence, removes API row ceilings, and avoids mutable rollup drift at pre-MVP scale.
- **Consequences:** The price catalog must be versioned via new migrations, unknown models remain explicitly unpriced, and OpenAI billing remains the reconciliation authority.

## ADR-014 — Reproducible linked-environment release gate

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** Sprint 1.5 needed to prove authentication, RLS, ownership, heartbeat, AI accounting, dashboard rendering, and the deployed worker against the linked Supabase project without persisting privileged credentials.
- **Problem:** Local-only tests miss hosted configuration and deployment drift, while manual credential copying is fragile and risks secret leakage. Hosted Auth email quotas also make repeated delivery tests nondeterministic.
- **Alternatives considered:** Keep online validation manual; store remote test secrets in `.env.local`; use linked CLI credentials at runtime with disposable data and explicit provider-limit handling.
- **Decision:** Retrieve linked project credentials only in process through the authenticated Supabase CLI, run disposable remote smoke and online Playwright suites, delete test users/files automatically, and classify hosted email throttling as a stable localized error. Exercise provider email delivery once per matrix and keep custom SMTP as a pre-production dependency.
- **Reason:** The gate remains reproducible and secret-safe while distinguishing product regressions from external delivery quotas.
- **Consequences:** `npm run test:remote` and `npm run test:e2e:online` require an authenticated, linked Supabase CLI session. Signup delivery may be explicitly skipped when the hosted quota is exhausted, but validation, error UX, recovery token exchange, protected password update, fresh login, RLS, ownership, heartbeat, cost aggregation, dashboard, and worker execution remain mandatory. CI must later receive equivalent short-lived credentials and custom SMTP coverage.

## ADR-015 — Mandatory permanent engineering standards

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** Phase 2 expands trusted interpretation, automation, and user-controlled actions across frontend, AI, jobs, and database boundaries.
- **Problem:** A feature checklist alone cannot prevent drift toward client-side authority, mutable evidence, unleased jobs, unvalidated model output, false controls, or unverified completion.
- **Alternatives considered:** Keep standards implicit in reviews; copy a checklist into each phase plan; adopt one permanent mandatory engineering contract.
- **Decision:** Adopt `ENGINEERING_STANDARDS.md` as the permanent minimum for all new code and every existing file changed after 2026-07-17. Temporary or architectural deviations must be documented with risk and a removal condition.
- **Reason:** A stable contract makes trust, ownership, test evidence, job safety, UI truthfulness, and repository hygiene enforceable across sessions and contributors.
- **Consequences:** A slice is not complete until applicable standards and permanent documentation gates pass. Existing out-of-scope debt is tracked in `TODO.md`; blocking correctness/security debt is fixed in the active slice.

## ADR-016 — Reconcile Phase 2 and harden the existing queue incrementally

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** The pre-MVP already implemented large parts of the original capture, task, chat, embedding, heartbeat, file, and AI-cost roadmap, while reliable job leasing and several correction/trust workflows remain incomplete.
- **Problem:** Replaying the original roadmap would duplicate working behavior, while expanding asynchronous processing on the current queue could strand jobs in `running` or allow stale workers to overwrite recovery.
- **Alternatives considered:** Rebuild Phase 2 from the original roadmap; replace `jobs` with a generic external orchestration platform; keep attachment-only claim logic; harden the shared `jobs` core and retain attachment processing as its first real consumer.
- **Decision:** Follow the reconciled slices in `PHASE_2_PLAN.md`. Start with additive leased queue semantics, atomic recovery, bounded retry/exhaustion, stale-worker protection, and minimal observability, without introducing a new queue service or a generic orchestration framework.
- **Reason:** This preserves proven architecture, fixes the highest compounding risk first, and provides exactly the reliability required by current and near-term Phase 2 processing.
- **Consequences:** Migration `019` must remain compatible with the deployed worker during rollout. Later slices extend existing domain models and must not recreate complete features or bypass the leased job contract.

## ADR-017 — Database-owned leased job transitions

- **Date:** 2026-07-17
- **Status:** Accepted
- **Context:** The attachment worker previously claimed with a row lock but then completed or failed jobs through direct service-role updates. A crashed or delayed worker could leave `running` forever or overwrite recovery.
- **Problem:** Worker identity, lease expiry, retry eligibility, terminal exhaustion, and stale-worker rejection must remain correct across concurrent Edge Function instances and partial failures.
- **Alternatives considered:** Keep transitions in Edge Function code; add only `locked_at`; introduce an external queue; make PostgreSQL RPCs own the complete leased state machine.
- **Decision:** PostgreSQL is authoritative for claim, completion, failure, backoff, exhaustion, reaping, and metrics. `process-jobs` receives a unique identity, uses a bounded lease/timeout, and can change terminal state only through RPCs that match its active unexpired lease.
- **Reason:** Atomic database transitions preserve concurrency and recovery invariants without adding a platform, and they are independently testable through pgTAP and disposable remote smoke.
- **Consequences:** Expired workers cannot commit job state. The per-minute reaper converts expired work to recoverable `failed` or terminal `exhausted`. Current failed attachment retry remains an authenticated owning-user action after `next_attempt_at`; an unattended consumer requires a separate concrete workflow and review.

## ADR-018 — Immutable interpretation snapshots with an owned current pointer

- **Date:** 2026-07-17
- **Status:** Accepted; deployed and remotely verified in Phase 2B
- **Context:** Users must correct AI interpretations, inspect why each element was trusted, undo mistakes, and retry interpretation without losing the original or rewriting evidence.
- **Problem:** Updating a latest interpretation row or maintaining an `is_current` flag would mutate historical evidence. Model confidence alone cannot authorize entity links or derived actions, and concurrent correction/reprocessing needs explicit ownership and idempotency.
- **Alternatives considered:** Mutable latest interpretation; an `is_current` flag on every revision; separate editable and snapshot tables; a new generic reprocessing worker; append-only snapshots selected by an owned entry pointer.
- **Decision:** Keep `entry_interpretations` immutable and append-only. Select the active version through `entries.current_interpretation_id`; make PostgreSQL RPCs own locking, expected-version checks, operation-key idempotency, complete-link ownership, lifecycle updates, audit, and compensating undo. Calculate trust and entity ranking deterministically in typed domain modules, persist bounded per-element evidence, and use a synchronous expiring reprocessing lease around the single shared extraction pipeline.
- **Reason:** This preserves an auditable history, makes concurrency and tenant boundaries database-enforced, reports missing evidence instead of inventing confidence, and avoids duplicating the provider/prompt or introducing infrastructure without a detached consumer.
- **Consequences:** Corrections and undo add rows rather than replacing them. The current pointer is mutable but can reference only an owned interpretation of the same entry. Reprocessing is bounded and synchronous until a concrete detached workflow justifies moving it behind the existing leased queue. Phase 2C must consume this trust/revision boundary rather than create a parallel task workflow.

## ADR-019 — Private, allowlisted product-behavior ledger

- **Date:** 2026-07-17
- **Status:** Accepted; deployed and remotely verified in Phase 2X Slice 2X.2
- **Context:** Product convergence needs measurable evidence about the daily cycle, but existing audit, job, and AI-cost records have different purposes, payloads, and retention needs.
- **Problem:** Reusing domain audit, technical jobs, or AI accounting for funnel analysis would leak internal lifecycle details into UX decisions and encourage collection of personal content or raw errors.
- **Alternatives considered:** Query existing ledgers; send open-ended analytics payloads from the browser; add a third-party analytics platform; use one private, bounded PostgreSQL ledger with dedicated RPCs.
- **Decision:** Add `product_events` as a private, RLS-forced ledger with exactly 17 allowlisted event names and event-specific bounded properties. The table accepts only validated security-definer RPC writes: one derives the authenticated owner and one is restricted to service-role workers. Events are idempotent per owner/key, synthetic traffic is marked, subject IDs must be owned, and the TypeScript server boundary is server-only and best effort.
- **Reason:** The product can measure behavioral friction without making telemetry a domain source of truth, exposing cross-user data, or collecting content that is unnecessary for UX funnel analysis.
- **Consequences:** `product_events` must remain distinct from `audit_logs`, `jobs`, and `ai_usage_events`; new names/properties require coordinated TypeScript, SQL, tests, and documentation. No UI emitter or dashboard belongs to this slice. Retention is capped at 180 days and requires an explicit purge operation before the pilot.

## ADR-020 — Durable entry capture before asynchronous cutover

- **Date:** 2026-07-17
- **Status:** Accepted; deployed in Phase 2X Slice 2X.3
- **Context:** Phase 2B capture and reprocessing remain synchronous, while the existing leased `jobs` queue already provides proven ownership, retry, stale-worker, and recovery semantics for attachments. The product needs a safe asynchronous cutover without changing current user behavior before the entry worker is ready.
- **Problem:** Creating an entry and a future interpretation request in separate operations risks a saved entry with no work, a job without an owned entry, duplicate retries, payloads that retain personal content, or an Edge Function/UI cutover before execution is proven.
- **Alternatives considered:** Move the current UI immediately to a detached worker; add a generic queue platform; let clients insert arbitrary entry jobs; add only worker code and defer persistence contracts; use additive, atomic database RPCs on the existing queue.
- **Decision:** Migration `025` keeps the current UI path intact and adds atomic `capture_entry_async` plus idempotent `enqueue_entry_reprocessing`. Initial jobs contain only `entry_id` and `mode`; reprocessing adds an operation key. Service-role-only claims validate type, payload, ownership, eligibility, attempts, lease and `SKIP LOCKED`, while existing attachment wrappers and generic completion/failure/reaper transitions remain unchanged.
- **Reason:** The database becomes the durable handoff boundary before any UI or worker cutover, preserving RLS, auditability, idempotency, and fail-closed behavior without duplicating the queue or starting an unverified asynchronous flow.
- **Consequences:** No entry job is dispatched in Slice 2X.3, and no current Server Action, route, UI, Edge Function, or projection consumer changes. Slice 2X.4 must add the worker/dispatch against these contracts; Slice 2X.5 may then switch capture only after end-to-end proof. The historical Product Projections implementation remains reusable prework, not the official database Slice 2X.3.

## ADR-021 — Service-role interpretation access and a Deno-native entry worker

- **Date:** 2026-07-17
- **Status:** Accepted; deployed in Phase 2X Slice 2X.4
- **Context:** Slice 2X.3 durably persists `interpret_entry` jobs, but the RPCs an unattended worker would need to actually run interpretation (`begin_entry_interpretation`, `fail_entry_interpretation`, `persist_entry_interpretation`, `begin_entry_reprocessing`, `persist_reprocessed_entry_interpretation`, `fail_entry_reprocessing`) all derive the acting user from `auth.uid()`, which is null for a service-role caller with no end-user session. Separately, the synchronous extraction pipeline (`src/lib/ai/openai-provider.ts`, `src/features/interpretations/interpret-entry.ts`) is Node/Next.js-only: `openai-provider.ts` starts with `import "server-only"`, whose Node-resolved default export unconditionally throws (verified directly against `node_modules/server-only/index.js`) outside a bundler that recognizes the `react-server` export condition, so it cannot be imported from the Deno Edge Function runtime. The project also has no deployed, publicly reachable Next.js server (Vercel is deliberately deferred), so a worker cannot be a Next.js route; the only currently deployed, network-reachable, unattended-triggerable compute is a Supabase Edge Function, and the only proven scheduled-automation mechanism in this project (`pg_cron`) has so far only ever called plain SQL functions, never made an outbound HTTP call.
- **Problem:** How to run AI extraction and persistence for `interpret_entry` jobs without a user session, without duplicating the entity-resolution/trust-scoring domain logic (a direct violation of the "no duplicated logic" standard), and without an existing mechanism for turning `pg_cron` ticks into unattended Edge Function invocations.
- **Alternatives considered:** Mint a per-user JWT in the worker to impersonate the owner through the existing `auth.uid()`-based RPCs (adds a new signing secret and a materially larger security surface for a routine internal call); reimplement the full entity-resolution/trust pipeline in Deno (violates the no-duplication standard and risks silent behavioral drift from the synchronous path); run the worker inside the Next.js app and have `pg_cron` call it (no deployed public Next.js server exists); extend the six RPCs with a `service_role`-gated optional parameter, and reuse the pure algorithmic modules by direct file copy into `supabase/functions/_shared/`, keeping only the unavoidable Node-only piece (the OpenAI HTTP call itself, already precedented by `attachment.ts`) duplicated in Deno.
- **Decision:** Migration `026` extends `begin_entry_interpretation`, `fail_entry_interpretation`, `persist_entry_interpretation`, `begin_entry_reprocessing`, `persist_reprocessed_entry_interpretation`, and `fail_entry_reprocessing` with an optional trailing `p_service_user_id` parameter, honored only when `auth.role() = 'service_role'`; each function is dropped and recreated under its original name (the same pattern migration `019` used for `claim_attachment_job`) so there is exactly one overload and no call-signature ambiguity for the unchanged `auth.uid()` path. `src/features/interpretations/entity-resolution.ts`, `trust-builders.ts`, and `trust-policy.ts` have zero Node/Next.js-specific imports in their Node form, so their logic is reused verbatim (only relative-import extensions were adapted for Deno's resolver) as `supabase/functions/_shared/*.ts`. The OpenAI Responses/embeddings calls, system prompt, JSON schema, and `EXTRACTION_STRATEGY_VERSION`/`EXTRACTION_PROMPT_VERSION` constants are duplicated into `supabase/functions/process-jobs/entry.ts`, matching `openai-provider.ts` byte-for-byte where it matters and calling the exact same persistence RPCs as the synchronous path, so persistence, audit, and the AI usage ledger stay identical regardless of which runtime produced them. `process-jobs/index.ts` is reduced to auth/routing; `attachment.ts` is the unmodified attachment behavior extracted verbatim; `dispatch.ts` is a fail-closed type router plus the unattended drain loop (`interpret_entry` only — attachments keep their existing explicit per-upload invocation, since no "claim next" RPC exists for them and adding one is out of scope). Unattended scheduling uses `pg_net` (newly enabled) and a per-minute `pg_cron` job that calls `process-jobs` in `dispatch` mode, authenticated by a dedicated `x-dispatch-secret` Edge Function secret; the target URL and that same secret also live in Supabase Vault by name so the cron body never embeds a literal value, and the query is guarded by `where exists (...)` so a tick before secrets are provisioned is a safe no-op.
- **Reason:** This keeps exactly one implementation of the trust/entity-resolution domain logic (genuinely shared source, not a parallel reimplementation), keeps the database as the single persistence authority regardless of caller runtime, avoids inventing a JWT-impersonation mechanism for a routine internal call, and works within the project's actual deployed topology (Edge Functions plus `pg_cron`/`pg_net`, no public Next.js server) instead of assuming infrastructure that does not exist yet.
- **Consequences:** `entity-resolution.ts`, `trust-builders.ts`, and `trust-policy.ts` now have a Node copy and a Deno copy that must be kept in sync by hand until/unless a shared package is introduced; each Deno copy says so at the top of the file. `openai-provider.ts`'s prompt/schema/version constants are similarly mirrored in `entry.ts` and must be updated together. The six extended RPCs are a superset of their Slice 2B contract — additive and non-breaking — but any future change to their `auth.uid()` behavior must also update the `p_service_user_id` branch. Attachments remain without an unattended consumer, consistent with `TODO.md`'s existing stance that one should only be added when a concrete workflow needs it.

## ADR-022 — Trigger-based enforcement instead of a CHECK-constraint privilege that broke authenticated inserts

- **Date:** 2026-07-17
- **Status:** Accepted; deployed in Phase 2X Slice 2X.4 (fixing a Slice 2X.3 regression)
- **Context:** While verifying Slice 2X.4's required attachment regression smoke, `scripts/remote-job-reliability-smoke.mjs` failed with `permission denied for function is_valid_entry_interpretation_job_payload` on a plain authenticated insert of a `process_attachment` job — the same operation `src/features/agent/actions.ts` performs on every real file upload. Migration `025` (Slice 2X.3) added the `jobs` CHECK constraint `type <> 'interpret_entry' OR private.is_valid_entry_interpretation_job_payload(payload)` and then revoked `EXECUTE` on that private helper from every role, including `authenticated` and `service_role` (confirmed against the live grants: only the migration-owning role retained it).
- **Problem:** PostgreSQL checks a referenced function's ACL when the executor initializes the expression tree for a CHECK constraint, not only when the branch that calls it is actually evaluated at runtime. So even though the `OR`'s left operand (`type <> 'interpret_entry'`) is true for a `process_attachment` row and the value of the right operand is never needed, the executor still had to initialize a `FuncExpr` node for it, which requires the inserting role to have `EXECUTE` on that function. Because only `postgres` had that grant, every authenticated insert into `jobs` — regardless of `type` — failed. This broke real file uploads from the moment migration `025` shipped, undetected because the one smoke test that performs a direct authenticated insert (`remote-job-reliability-smoke.mjs`) was not re-run after `025`.
- **Alternatives considered:** Grant `EXECUTE` on the private validator to `authenticated` and `service_role` (works, but broadens a function whose name and `private` schema explicitly signal it should never be callable directly, weakening the original intent for no real benefit); rewrite the validator as an inlinable plain SQL function (does not reliably avoid the ACL check and is a larger, riskier rewrite of validation logic that must stay byte-identical); move enforcement to a `BEFORE INSERT OR UPDATE` trigger, gated by a `WHEN` clause so it only fires for `interpret_entry` rows, backed by a `SECURITY DEFINER` trigger function.
- **Decision:** Migration `027` drops `jobs_interpret_entry_payload_check` and replaces it with trigger `jobs_interpret_entry_payload_trigger` (`before insert or update ... when (new.type = 'interpret_entry')`) calling `SECURITY DEFINER` function `private.enforce_entry_interpretation_job_payload()`, which raises `errcode = '23514'` (matching the committed pgTAP contract) when `private.is_valid_entry_interpretation_job_payload` returns false. The private validator's own grants are untouched — still revoked from every role.
- **Reason:** Trigger firing is authorized by ordinary table `INSERT`/`UPDATE` privilege, which `authenticated` and `service_role` already have on `jobs`; it does not require the writing role to hold `EXECUTE` on the trigger function or on any function that function calls internally, because the `SECURITY DEFINER` trigger function itself supplies the elevated privilege needed to call the private validator. This restores the constraint's original enforcement with zero privilege broadened anywhere, and the `WHEN` clause means the validator is invoked only for the row type it was written for, exactly matching the original constraint's intent.
- **Consequences:** `jobs` no longer has a named CHECK constraint for `interpret_entry` payload shape; the same guarantee is now expressed as a trigger, which existing and future documentation/tests should reference by trigger name rather than constraint name. Any future job-payload validation added the same way should default to this trigger pattern rather than a CHECK constraint that calls a privately-scoped function.

## ADR-023 — Async capture cutover using `after()`, a generalized entry retry, and removal of the now-unreachable synchronous pipeline

- **Date:** 2026-07-17
- **Status:** Accepted; deployed in Phase 2X Slice 2X.5
- **Context:** Slices 2X.3–2X.4 built and remotely proved a durable `capture_entry_async`/`enqueue_entry_reprocessing` contract and a deployed, automatically-dispatched entry-interpretation worker, but no Server Action, route, or UI had switched to it — `captureEntry` and `reprocessEntry` still called the synchronous Node extraction pipeline (`src/features/interpretations/interpret-entry.ts`) directly and `captureEntry` still redirected only after interpretation finished or failed. This slice is the vertical cut: the user must save and continue immediately, while a nudge to the worker and best-effort product analytics still need to happen without adding latency to the response, and a real gap opens once capture is async — an entry whose initial interpretation job fails or is exhausted has no manual retry path yet, unlike attachments' existing `retryAttachmentJob`.
- **Problem:** How to return a `CaptureReceipt` the instant the atomic RPC settles while still (a) nudging the deployed worker so the user does not wait up to a minute for the next `pg_cron` dispatch tick, (b) recording best-effort product events, and (c) giving entries a retry path equivalent in spirit to attachments' — all without blocking the Action's response, without inventing a new secret/authorization surface, and without leaving a dead synchronous extraction pipeline behind that a future change could mistake for a live code path.
- **Alternatives considered:** For the nudge/analytics: await them inline before returning (adds real latency to every capture for a pure optimization); fire them without awaiting and let the request/response cycle race their completion (unsupported outside a long-lived server process and explicitly warned against by the Next.js runtime, which may tear down in-flight unawaited work once the response is sent); use Next.js's `after()` API, which the platform guarantees will run to completion after the response is flushed. For entry retry: build a parallel `interpret_entry`-only retry Action from scratch; extend `retryAttachmentJob` itself to branch on job type (couples an unrelated, working, already-tested attachment path to new entry logic); add a new `retryProcessingJob` Action in `src/features/agent/actions.ts` that mirrors `retryAttachmentJob`'s eligibility checks but branches on the entry queue's actual recovery mechanics. For the dead code: leave `interpret-entry.ts` in the tree as unreachable production code; delete it now that nothing calls it.
- **Decision:** `captureEntry` and `reprocessEntry` call `capture_entry_async`/`enqueue_entry_reprocessing` and return as soon as that RPC (plus one lightweight indexed lookup for lifecycle/job state) settles. The worker nudge (`kickEntryInterpretationWorker`, `src/lib/jobs/entry-worker.ts` — reuses the existing authenticated `{ jobId }` Bearer-token contract, no new secret) and the `capture_save_succeeded`/`capture_save_failed`/`capture_processing_enqueued` product events are scheduled inside `after()`, with every internal error swallowed since the scheduled `pg_cron` drain is the correctness backstop, not the nudge. `agent/actions.ts` gains `retryProcessingJob(entryId, locale)`: for a `failed` job whose backoff has elapsed, it only kicks the worker (the job itself is still eligible for automatic dispatch); for an `exhausted` job, it calls `enqueue_entry_reprocessing` with a fresh operation key (an exhausted job is never re-claimed, so only a new job unblocks it), then kicks that new job. `retryAttachmentJob` is untouched. `interpret-entry.ts` and its two now-superseded ordering assertions in `src/lib/ai/usage-order.test.ts` are deleted; `entity-resolution.ts`, `trust-builders.ts`, and `trust-policy.ts` are kept exactly as they are — ADR-021 documents them as the canonical Node source the Deno `_shared/` copies must be kept in sync with, and that relationship does not change just because their orchestrator caller is gone.
- **Reason:** `after()` is the platform-sanctioned mechanism for exactly this shape of work (documented as safe for Server Functions, including calling back into the same request-scoped Supabase client) and keeps the capture Action's own latency bounded by the atomic RPC alone. Branching the entry retry on the queue's own recovery semantics (automatic dispatch for `failed`, a fresh job for `exhausted`) reuses `enqueue_entry_reprocessing` instead of reinventing recovery, and keeping it a separate Action from `retryAttachmentJob` means neither path can regress the other. Deleting `interpret-entry.ts` prevents a future reader from mistaking inert code for the live extraction path, while leaving the three ADR-021 modules alone avoids resolving that ADR's documented Node/Deno drift risk as an incidental side effect of an unrelated slice.
- **Consequences:** A capture or reprocess request's latency no longer includes any AI call; the worker nudge and analytics are best-effort and may occasionally under- or over-count on network retries, which is acceptable for product telemetry. `retryProcessingJob` has no UI consumer yet — it is wired up by the Needs-Attention slices (2X.10/2X.11), consistent with this project's existing pattern of landing a server-side capability ahead of the UI slice that consumes it. `entity-resolution.ts`'s Node copy now has zero non-test production callers (only the Deno `_shared/` copy is exercised in production), a fact future readers should know before assuming it is dead code.

## ADR-024 — Candidate provenance bound to the current interpretation, not the entry

- **Date:** 2026-07-18
- **Status:** Accepted; deployed in Phase 2X Slice 2X.7
- **Context:** A task candidate was identified only by `(source_entry_id, candidate_index)`. Once an entry has more than one interpretation (a correction or a reprocess), `candidate_index` numbering restarts at 0 for the new version, but nothing recorded which interpretation actually produced a given candidate or a given confirmed task. The old unique constraint on `(source_entry_id, candidate_index)` governed every confirmation regardless of interpretation, so a legitimately different candidate at the same index in a newer version could silently fail to materialize against `ON CONFLICT DO NOTHING`, and the existing `confirm_entry_tasks` RPC picked "the latest version by `order by version desc`" rather than the interpretation the UI actually had open, with no check that the two still matched.
- **Problem:** How to guarantee, at the database layer, that a confirmed task always traces to the exact interpretation version the UI displayed when the user confirmed it — surviving later corrections without resurrecting stale candidates or blocking legitimate new ones at the same index — without a client-side comparison of IDs, versions, or candidate arrays (which cannot be trusted or kept correct as the UI evolves).
- **Alternatives considered:** Keep `(source_entry_id, candidate_index)` as the sole identity and have the client resend the full candidate content for the server to fuzzy-match against (fragile, and pushes a trust decision onto data the server should own); version-stamp `task_candidates` itself and diff arrays server-side per request (expensive, and still doesn't answer "was this exact task already created for this exact version"); add `source_interpretation_id`/`operation_key` to `tasks`, make uniqueness interpretation-scoped instead of entry-scoped, and require the caller to declare the interpretation ID it believes is current, checked against `entries.current_interpretation_id` inside the same transaction that locks the entry row.
- **Decision:** Migration `028` adds `entry_interpretations.is_record_only` (persisted at creation/correction/reprocess/undo instead of existing only as a transient input to the computed `status`), `tasks.source_interpretation_id` (FK-composite-proven `(user_id, id)` against `entry_interpretations`) and `tasks.operation_key`, and replaces the old entry-wide unique constraint with two partial unique indexes: one preserving legacy behavior when `source_interpretation_id is null`, one authoritative per `(source_interpretation_id, candidate_index)`. New RPC `confirm_entry_task_candidates(entry_id, expected_interpretation_id, candidate_indexes, operation_key)` locks the entry row, rejects immediately if `entries.current_interpretation_id <> expected_interpretation_id`, rejects outright if the current interpretation is `is_record_only`, and is idempotent per `operation_key`. Backfill for existing tasks is conservative: only entries that have ever had exactly one interpretation get `source_interpretation_id` set; anything with a correction/reprocess history keeps `null` rather than a guessed value. `confirm_entry_tasks` is preserved for compatibility (no new consumer) with only its `ON CONFLICT` target adjusted to the new legacy partial index.
- **Reason:** Locking the entry row and re-reading `current_interpretation_id` inside the same transaction is the only way to make "is this candidate still current" a server-verified fact rather than a client assertion — it is exactly the pattern `correct_entry_interpretation`'s `expected_version` check already established, reused instead of inventing a second concurrency idiom. Making the new unique index interpretation-scoped rather than entry-scoped fixes the actual coherence bug (a same-index candidate in a newer version was previously unconfirmable), while the legacy entry-scoped index kept behind a `source_interpretation_id is null` predicate means `confirm_entry_tasks` needed no behavior change for its (absent) callers. Persisting `is_record_only` rather than deriving it made it possible to check "is the current version actionable at all" without re-deriving policy from `element_policy`/`pending_questions`, which was never a reliable proxy for that specific fact.
- **Consequences:** `ActionableCandidateView`/`InterpretationReviewView` (`src/features/daily-cycle/contracts.ts`, prework from Slice 2X.1) still have no consumer — Slice 2X.8 is responsible for wiring `/inbox/{entryId}` onto a dedicated projection instead of the current broad Phase 2B revision page, which for this slice was adapted just enough (`isRecordOnly`, `unavailableCandidateIndexes`) to stop offering an unconfirmable or already-confirmed candidate. Any future work on candidate confirmation must go through `confirm_entry_task_candidates`, not `confirm_entry_tasks`; the latter stays only until an explicitly approved cleanup slice removes it.

## ADR-025 — SECURITY DEFINER for task confirmation, and avoiding SQLSTATE 40001 in RPC-raised conflicts

- **Date:** 2026-07-18
- **Status:** Accepted; deployed in Phase 2X Slice 2X.7. One consequence (Phase 2B's `correct_entry_interpretation`) is explicitly deferred — see Consequences.
- **Context:** While building `confirm_entry_task_candidates` for Slice 2X.7, `scripts/remote-daily-cycle-smoke.mjs` was written to exercise it as a real signed-in `authenticated` user against the linked project — not against `service_role`, not against pgTAP's typically-superuser test session. That run surfaced two things no prior verification of this feature (mocked Vitest, pgTAP, or manual review) had caught, because none of them exercised a `SECURITY INVOKER` function under real `authenticated` grants end to end.
- **Problem, part one (grants):** `confirm_entry_tasks` (Slice "domain relationships", pre-Phase 2X) and the first draft of `confirm_entry_task_candidates` were `SECURITY INVOKER`. Both take `SELECT ... FOR UPDATE` on an `entry_interpretations` row — which requires `UPDATE` privilege even though nothing is written — and `authenticated` has no `UPDATE` grant there, deliberately, since interpretations are immutable and trigger-protected. Both also `INSERT` into `undo_operations` and `audit_logs`, append-only tables `authenticated` likewise has no `INSERT` grant on; every other RPC in this schema that writes to them (`persist_entry_interpretation`, `correct_entry_interpretation`, `undo_operation`, and so on) is `SECURITY DEFINER` for exactly this reason. The practical effect: `confirm_entry_tasks` has never successfully run for a real authenticated user since it was written — task confirmation, the feature this entire slice exists to make trustworthy, was unconditionally broken (`permission denied`) the whole time, invisible because nothing had called it as anything other than a superuser-equivalent role.
- **Problem, part two (40001 hangs):** The first version of `confirm_entry_task_candidates` signaled "the interpretation the UI declared as current no longer is" with `errcode = '40001'` (`serialization_failure`), deliberately mirroring `correct_entry_interpretation`'s existing `p_expected_version` conflict convention so the two optimistic-concurrency signals would read the same way to a caller. The smoke script's very first call down that path hung for the full client timeout instead of returning quickly. `pg_stat_activity`, sampled mid-hang, showed the backend had already finished and gone `idle` — the SQL itself executed in well under a second. Bypassing this repo's code entirely with a raw `fetch()` against the project's REST endpoint reproduced the same multi-second-plus hang on a deliberately wrong `p_expected_version` sent to the **already-shipped** `correct_entry_interpretation`, with no application code involved on either side. Re-running the existing `remote-entry-processing-smoke.mjs` in full (which raises `P0002` and `55P03` from real `SECURITY DEFINER` RPCs several times) completed normally and quickly in the same session, isolating the hang specifically to SQLSTATE 40001, not to raised exceptions in general.
- **Alternatives considered (grants):** Grant `UPDATE`/`INSERT` on the affected tables to `authenticated` directly (defeats the entire reason those grants are withheld — `authenticated` would then be able to write audit/undo/interpretation rows outside any RPC's validation); keep `SECURITY INVOKER` and drop the `entry_interpretations` lock while routing the `undo_operations`/`audit_logs` writes through a small dedicated `SECURITY DEFINER` helper (adds a second function and an extra round trip for no benefit over making the whole RPC `SECURITY DEFINER`, the pattern already used everywhere else this exact problem occurs in this schema).
- **Alternatives considered (40001):** Keep 40001 and treat the hang as an environment quirk to route around at the client/Action layer with a request-level timeout and manual retry (masks the platform behavior instead of fixing the signal, and would still leave `correct_entry_interpretation`'s equivalent path hanging for real users); pick an entirely new, unused SQLSTATE for this one condition (adds a code the rest of the schema has no precedent for); reuse `55P03` (`lock_not_available`), the SQLSTATE `begin_entry_reprocessing` already raises for "this entry is already being reprocessed" and which the smoke suite had just proven fast and correct in the same session.
- **Decision:** `confirm_entry_tasks` and `confirm_entry_task_candidates` are both `SECURITY DEFINER`, keeping the same manual `current_user_id := auth.uid()` plus `where user_id = current_user_id` ownership filtering already used by every other `SECURITY DEFINER` RPC here; `confirm_entry_tasks` additionally gained the explicit `grant execute ... to authenticated` / `revoke all ... from public, anon` pair every other RPC in this schema already has (it had none before — reachable, harmlessly, by `anon`, since the function also rejects a null `auth.uid()`). The unnecessary `FOR UPDATE` on `entry_interpretations` is removed from both functions rather than kept and merely tolerated under the new security context: interpretations never change after creation, and the `entries` row lock both functions already take serializes them against a concurrent correction/reprocess on its own. `confirm_entry_task_candidates` signals a stale interpretation with `55P03` instead of `40001`.
- **Reason:** SECURITY DEFINER with manual ownership filtering is this schema's one established pattern for RPCs that must write to owner-scoped-but-not-directly-writable tables; introducing a second pattern for the same problem would be exactly the kind of unnecessary abstraction this project's engineering standards warn against. Avoiding 40001 for a condition this project's UI must actually recover from (reload and retry) is a hard requirement once a live gateway is confirmed to hang on it — a conflict a real user cannot get a response for is materially worse than one they see and can act on.
- **Consequences:** Any future RPC in this schema that needs to signal "the resource the caller expected is no longer current" should default to `55P03`, not `40001`, until Supabase's platform behavior here is understood or changes. `correct_entry_interpretation`'s own `40001` raise (Phase 2B, already shipped, used by `src/features/interpretations/actions.ts`'s existing conflict handling) was **not** changed by this slice — it is out of scope for a 2X.7 file list that does not include `interpretations/actions.ts` or a migration touching that function's signature, and changing an already-shipped Action contract is its own unit of work with its own tests and Playwright coverage. It is left as an explicit, urgent, separately-tracked defect (`SECURITY.md`, `TODO.md`): today, a real user who triggers that specific version conflict has their correction request hang for a full gateway timeout instead of seeing "reload and try again." Whether the root cause is Supabase's connection pooler, PostgREST's own exception handling, or a project-specific configuration was not determined and needs its own investigation before the fix (almost certainly the same `55P03`-style substitution, but potentially also a client-side bounded timeout) is designed. **Resolved by ADR-026.**

## ADR-026 — `correct_entry_interpretation`'s version-conflict path adopts `55P03`, closing the ADR-025 follow-up

- **Date:** 2026-07-18
- **Status:** Accepted; deployed via migration `202607180029`.
- **Context:** ADR-025 documented, but deliberately did not fix, that `correct_entry_interpretation` (Phase 2B, already shipped) signals its optimistic-concurrency conflict with SQLSTATE `40001`, and that raising `40001` from any RPC on the linked project hangs the request until the platform gateway times out instead of returning an error. That defect predates Phase 2X entirely and was left as an urgent, separately-tracked follow-up because fixing it was outside Slice 2X.7's file list.
- **Problem:** How to eliminate the gateway hang for a real, already-shipped user flow (correcting an interpretation after a stale reload) without weakening the optimistic-concurrency check itself, changing its signature, or touching any other RPC or Slice 2X.8 work.
- **Alternatives considered:** Route around the hang at the client with a request-level timeout and manual retry (masks the platform behavior instead of fixing the signal, and still leaves the raw RPC call itself hanging for any other caller); pick an unused SQLSTATE (adds a code with no precedent in this schema); reuse `55P03` (`lock_not_available`), matching the exact substitution ADR-025 already made for `confirm_entry_task_candidates` and already validated fast/correct in production by `begin_entry_reprocessing`.
- **Decision:** Migration `202607180029` redefines `correct_entry_interpretation` with `create or replace function` under its unchanged signature `(uuid, integer, jsonb, text, text)`. The only behavioral change is the single `raise exception 'Interpretation changed; reload before saving'` on version mismatch, which now uses `errcode = '55P03'` instead of `'40001'`. Every other line — ownership checks, the idempotent-replay short-circuit, patch/entity-link validation, the insert/update/audit/undo writes, and the `is_record_only` persistence added by migration `028` — is copied verbatim from the interpretation's prior authoritative body. `src/features/interpretations/actions.ts`'s `correctInterpretation` conflict detection (`error.code === "40001"`) is updated to `error.code === "55P03"`; the existing message-content fallback regex is unchanged. The migration's own post-deploy verification checks the literal `errcode = '40001'` / `errcode = '55P03'` assignment strings in `pg_get_functiondef()`'s output, not an arbitrary numeric substring, so it cannot be defeated (or falsely tripped, as a first draft of this migration discovered when its own inline comment happened to contain the digits `40001`) by unrelated text elsewhere in the function body.
- **Reason:** `55P03` is no longer just "the pattern to default to" per ADR-025's consequences — it is now the actual fix for the specific already-shipped path ADR-025 named as the reason a future RPC should prefer it. Keeping the signature, validation, and every non-conflict behavior byte-for-byte identical means this is strictly a SQLSTATE substitution, not a contract change, so no caller other than the one `error.code` check needs to change.
- **Consequences:** `correct_entry_interpretation` no longer raises `40001` anywhere. The remaining `40001` raise in `undo_operation` (`'Cannot undo after a newer interpretation revision'`) is a distinct, separate optimistic-concurrency signal on a different action; it was not in this hotfix's scope (a single-RPC fix, not a sweep of every `40001` in the schema) and remains an explicit, separately-trackable risk — see `SECURITY.md`. The authenticated remote smoke (`scripts/remote-interpretation-revisions-smoke.mjs`, extended by this hotfix) now asserts a bounded elapsed time and the `55P03` code around the existing concurrent-correction race, which is the actual evidence this ADR relies on rather than reasoning about the SQL alone.

## ADR-027 — SQL-side lifecycle precedence for `list_needs_attention`, and a candidate-index name-collision hotfix found by the real remote smoke

- **Date:** 2026-07-18
- **Status:** Accepted; deployed in Phase 2X Slice 2X.10 via migrations `030` and `031` (`031` applied in the same session, before either was committed).
- **Context:** Slice 2X.10 needed a "Precisa de você" query that returns only entries currently requiring one of the five supported actions, paginated deterministically, without an unbounded per-user scan (XG-025). The canonical decision logic already exists as `resolveDailyCycleLifecycle` in `src/features/daily-cycle/lifecycle.ts`, and the project's default instinct (reinforced by explicit instruction for this slice) is to reuse that single source of truth rather than invent a second definition of "needs attention."
- **Problem:** `resolveDailyCycleLifecycle` is TypeScript running in the request/server process; it cannot be called from a Postgres function, and Inbox's existing approach — compute lifecycle for a fixed page of entries already fetched, in any order — does not generalize to "find every entry across a user's entire history that currently qualifies," which is exactly what a filtered, paginated queue requires. Filtering in application code would mean scanning every owned entry per request to find qualifying rows, which grows unbounded with a user's total entry count regardless of how small their actual backlog is.
- **Alternatives considered:** Filter in TypeScript by loading every owned entry per request and running the existing mapper (violates XG-025, cost grows with total history not actual backlog); add a materialized/persisted `needs_attention` table kept in sync by triggers (a new source of truth the plan explicitly forbids, and a synchronization-drift risk of its own); reimplement the same five-reason precedence directly in SQL, restricted to a bounded candidate set of entries whose raw state could plausibly qualify, verified against the same scenario matrix `lifecycle.test.ts` already covers.
- **Decision:** Migration `030` adds `list_needs_attention` (`SECURITY DEFINER`, `set search_path = ''`, owner-scoped via `auth.uid()`) as a SQL function whose `CASE` expression is deliberately ordered to match `resolveDailyCycleLifecycle`'s branches one for one (fail-closed unknown state, terminal/exhausted, active-job organizing, interpreting/reprocessing, `recoverable_error`, `awaiting_review`/`partially_processed`, `completed` sub-branches, `saved`+completed-job fallback), fed by a bounded `candidate_entries` union restricted to entries whose raw status/interpretation/question/job shape could plausibly qualify — not every entry the user has ever captured. `supabase/tests/needs_attention_projection.sql` exercises the same scenario matrix `lifecycle.test.ts` already covers, as the practical substitute for a shared code path across the TypeScript/SQL boundary. While proving this behavior against the linked project with `scripts/remote-daily-cycle-smoke.mjs` (not just pgTAP or mocked Vitest), a real defect surfaced: the `has_unconfirmed_candidate` check named its `generate_series` output `candidate_index` — identical to `tasks.candidate_index` — so the unqualified reference inside the correlated `tasks` subquery resolved against the innermost scope (`tasks` itself) instead of the outer loop variable, making the comparison a tautology. Confirming one of two current candidates incorrectly removed the entry from the queue entirely instead of leaving it listed until the remaining candidate was resolved. Migration `031` (`create or replace function`, identical signature/grants/index) fixes this by renaming the alias to the two-part form `candidate_slot(idx)`, referenced explicitly as `candidate_slot.idx`, which cannot collide with any table's own column name.
- **Reason:** Reimplementing the precedence in SQL is the only way to satisfy both "reuse the one definition of needs-attention" (in intent and rules, not literal shared code — the two are kept in sync by mirrored branch order and a matching test matrix, since no shared runtime exists across the TypeScript/Postgres boundary) and "no unbounded scan" (XG-025) simultaneously; the bounded candidate set keeps cost proportional to a user's actual unresolved backlog rather than their total history. `55P03`-style precedent from ADR-025/ADR-026 was not needed here since this RPC raises no conflicts — it is read-only. The name-collision fix specifically illustrates why this slice's real remote smoke (exercising the actual RPC against real captured/interpreted/confirmed state) is required validation, not an optional nicety: no pgTAP fixture that hand-inserts task rows in isolation, and no TypeScript unit test of `attention-projection.ts`'s hydration logic, exercises this exact SQL correlation path.
- **Consequences:** Any future SQL function that loops over `generate_series` and correlates against a table with a same-named column must use a qualified/two-part alias, not a bare column-shaped name, to avoid the same silent shadowing. `list_needs_attention` has no UI consumer yet — Slice 2X.11 is responsible for Home/Caixa wiring. `supabase/tests/needs_attention_projection.sql` includes a dedicated regression case (confirm one of two candidates, assert the entry remains listed, confirm the second, assert it resolves) so this exact class of defect cannot silently reappear.

## ADR-029 — Daily funnel emission follows domain ownership and confirmed interaction semantics

- **Status:** Accepted (2026-07-19).
- **Context:** Migration `024` already supplied a private, allowlisted, owner-scoped and idempotent product-event ledger, but the 17 approved daily-funnel events needed precise emission owners. Putting everything in React effects would count render/hydration/prefetch instead of product meaning and would trust the browser with outcome truth; putting views in Server Components would claim visibility that never occurred; coupling event writes transactionally to unrelated domain mutations would let telemetry availability break the product; random keys on retried Actions/workers would overcount outcomes.
- **Alternatives considered:** a generic client analytics SDK accepting arbitrary names; server-rendered view events; synchronous/fail-closed telemetry inside each domain mutation; a new event queue or migration; random idempotency for every call; one emitter per render.
- **Decision:** Browser-only intent/view/open semantics use a closed set of small client exports that build exact allowlisted payloads, confirm views with `IntersectionObserver`, deduplicate logical views per tab session and call the existing authenticated Action. Successful outcomes remain owned by the existing Server Action and emit only after the mutation succeeds. Entry-worker outcomes emit through `record_product_event_for_user` only after the completion/failure RPC persists, with the owner and entry subject loaded server-side. Domain/worker replay keys are deterministic UUIDs derived from the existing operation/job-attempt scope; meaningful new interactions use new UUIDs. Analytics remains a separate fail-open effect and never becomes lifecycle truth.
- **Reason:** This maps each event to the layer that can truthfully observe it, preserves actor/subject validation and content-free allowlists, prevents common duplicate sources, and keeps product correctness independent of telemetry.
- **Consequences:** New browser events must be added to the finite contract and a targeted export, never passed as arbitrary names. View semantics require confirmed visibility and a documented session key. Domain outcome events require a durable success point and deterministic replay scope. The ledger/RPC remain unchanged; rollback removes emitters only. No dashboard, aggregation service, migration, remote deployment or Slice 2X.16 projection work follows from this decision.

## ADR-030 — Phase 2X closes on deployed source parity and separates provider-email evidence

- **Date:** 2026-07-19
- **Status:** Accepted; `process-jobs` v13 deployed and Phase 2X closed by Slice 2X.18.
- **Context:** Slice 2X.15 intentionally committed worker product-event instrumentation without deploying it. Phase 2X could not close while local worker behavior differed from the linked runtime, while no aggregate remote gate existed, or while provider-dependent Auth failures were summarized together with the core product matrix.

## ADR-033 — Phase 2D resolves pending questions through a versioned, audited, undoable transition and reuses the existing reinterpretation path

- **Date:** 2026-07-23
- **Status:** Accepted for Phase 2D planning; implementation not started. Approved 2026-07-23 with two adjustments folded in: suggested answers are deterministic by default (no AI schema change), and all resolution kinds use one long-lived versioned RPC family. No branch, migration, RPC, deployment, push, or PR is authorized by this ADR.
- **Context:** Phase 2C closed through Slice 2C.6 with immutable interpretations, versioned `SECURITY DEFINER` confirmation RPCs, canonical replay fingerprints, an `entry_task_candidate_resolutions` disposition ledger, audit/undo, and a fail-open product-event ledger. Pending questions (`public.pending_questions`) already exist, are normalized from the immutable interpretation by trigger, and carry dormant `snoozed`/`dismissed` statuses and `snoozed_until`. But the current `answerPendingQuestion` is a plain owner-scoped `UPDATE` to `status='answered'` with no RPC, audit, undo, or effect — the roadmap's Gap #5 ("question answers stop at storage instead of completing a traceable domain transition"). Reinterpretation infrastructure (`correct_entry_interpretation`, `enqueue_entry_reprocessing`, the deployed worker, `undo_operation`) is already owner-scoped and audited; `undo_operation`'s own `40001` conflict path is an unresolved residual (`2C-UNDO-004`). Phase 2D is the next official roadmap phase (`PHASE_2_PLAN.md` §7).
- **Problem:** Let a user answer, defer, dismiss, or mark-not-relevant a pending question as an auditable, reversible transition; preview a question's source and effect; optionally apply exactly one bounded consequence (reinterpretation) that visibly improves the Brain; and resolve questions from Chat and the queue — without a second draft source of truth, without editing the immutable interpretation, without a new interpretation engine, and without letting question/answer content become model instructions or analytics content.
- **Alternatives considered:** keep the plain `UPDATE` and add audit/undo around it in the Server Action (rejected: not atomic, not database-owned, not replay-safe); add a `question_drafts`/answer-draft table (rejected: a second source of truth, matching the Phase 2C anti-pattern); build a new interpretation/answer engine or queue for reinterpretation (rejected: duplicates the deployed worker/dispatch); let an answer drive an arbitrary action agent (rejected: unbounded security surface); make `not_relevant` a new `status` value (deferred: forces a `CHECK` migration; default is a resolution-evidence kind over `dismissed`); separate `answer_*` and `resolve_*` RPC families (rejected: two contracts to version and keep in sync where one discriminated family suffices); extend the AI extraction schema for suggested answers up front (rejected as the default: a provider/worker-touching change before deterministic generation is proven insufficient); an LLM-timed proactive surfacing (rejected: non-deterministic nagging); a single versioned `SECURITY DEFINER` resolution RPC family reusing the Phase 2C fingerprint/audit/undo patterns with reinterpretation via the existing path and deterministic suggestions (**chosen**).
- **Decision:** (1) Resolution *state* lives on `pending_questions`; *evidence* lives on append-only `audit_logs`/`undo_operations` (plus a narrow resolution-kind field only if lifecycle needs it); no draft table. (2) Every resolution flows through **one long-lived versioned `SECURITY DEFINER` RPC family**, `resolve_pending_question_vN`, with a closed discriminated `p_resolution` (2D.1 `answer`; 2D.2 adds `deferred`/`dismissed`/`not_relevant`; 2D.4 adds an optional `consequence`), `set search_path = ''`, `auth.uid()` identity, owner lock, a current-interpretation (anti-stale) check, canonical replay fingerprint, and atomic state + audit + undo — the legacy answer path preserved until cutover, and a new version added only when the closed input shape must change. Separate answer/disposition RPC families are not created unless a future contract genuinely requires separation. (3) The permitted-consequence set is a closed enum (`none`, `reinterpret`); `reinterpret` reuses the deployed `enqueue_entry_reprocessing`/correction/worker/`undo_operation` path, never a new engine. (4) Suggested answers are generated **deterministically by default** from the question type and existing owned domain context (bounded, closed, never free-form model output), populate an editable answer, and never auto-apply; an additive, validated AI extraction-schema field is a later fallback only if deterministic suggestions prove insufficient. Source/effect previews are read-only. (5) Proactive surfacing is deterministic and reuses the heartbeat's quiet-hours/cap/cooldown/override discipline; no LLM decides timing and no new outbound channel is added. (6) Question/answer/interpretation content is untrusted data in Chat and prompts and never enters analytics. (7) The `undo_operation` `40001` residual (`2C-UNDO-004`) is a hard gate for Slice 2D.4 (reinterpretation undo): resolve to `55P03` (mirroring ADR-026) or prove safe before remote acceptance.
- **Reason:** Reusing the proven Phase 2C RPC/fingerprint/audit/undo and the deployed reinterpretation path closes the security/concurrency/replay gaps a client `UPDATE` cannot, avoids a second source of truth, and keeps rollback a UI/Action switch over an additive migration. One discriminated resolution family keeps a single contract to version and test. Deterministic suggestions avoid a provider/worker change until it is demonstrably needed. Keeping consequences a closed enum and previews non-mutating bounds the security surface; deterministic surfacing prevents nagging.
- **Consequences:** Phase 2D delivers in six ordered slices (2D.1 answer transition; 2D.2 dispositions; 2D.3 deterministic suggested answers + preview; 2D.4 permitted action/reinterpretation; 2D.5 chat/queue surfacing + cooldown; 2D.6 convergence/closeout), each additive and independently reviewable, per `PHASE_2D_PRD.md` and `PHASE_2D_IMPLEMENTATION_PLAN.md`. Slice 2D.3 adds no AI schema/worker change by default; any later `suggestedAnswers` schema field is additive, validated, and separately authorized. Slice 2D.4 cannot ship remotely until the `40001` residual is resolved or proven safe. No implementation, migration, deployment, worker, secret, schedule, push, or PR is authorized by this ADR.

## ADR-035 — `undo_operation` becomes a thin router over registered per-operation handlers

- **Date:** 2026-07-25
- **Status:** Accepted; implemented on branch `codex/pre-2e-foundation-hardening` (migration `202607250052`).
- **Context:** Because migrations are append-only, every slice that added an undoable operation re-created the entire `undo_operation` body. Ten migrations had done so by the end of Phase 2D, the current definition being 414 lines (`202607230050:593-1006`) dispatching eight `action_type` values through a flat `if/return` chain. The same defect class shipped twice: `pg_catalog.greatest(` cannot resolve under `search_path = ''` because `greatest` is a SQL special form, not a `pg_catalog` function; `202607220042` fixed it and `202607220044` re-pasted the pre-fix version, forcing `202607220045`. Migration `202607220040` is 2,368 lines because one bug had to be fixed in five function bodies. Phase 2E (natural-language task updates) adds undoable operations; the architecture review names this the single true pre-2E blocker (H2).
- **Problem:** Stop requiring a ~470-line re-paste of critical compensation logic per new undoable operation, without changing any observable behaviour of a `SECURITY DEFINER` RPC that three Server Actions, eleven pgTAP suites, six remote smokes and one e2e journey depend on — and without weakening ownership, RLS, replay safety, concurrency, immutable history, audit semantics or compensation semantics.
- **Alternatives considered:** keep the monolith and rely on review discipline (rejected: the recurrence rate is measured, not hypothetical); a `case` statement routing to statically-named handlers (rejected as the sole mechanism: adding an operation would still edit the router, so the router would still be re-pasted, just shorter); one `SECURITY DEFINER` handler per operation (rejected: handlers take the owner as a parameter, so an accidental future grant would become a cross-tenant write — invoker handlers fail closed on table grants instead); passing the locked `undo_operations` row into handlers as a composite parameter (rejected in favour of primitive `(uuid, uuid)`: it keeps `to_regprocedure` assertions trivial and avoids relying on composite `EXECUTE ... USING` behaviour that could not be tested locally, at the cost of one indexed re-read inside the same transaction); a CHECK constraint to bind `action_type` to the registry (rejected: `202607170027` proved a CHECK referencing a revoked function breaks every writer, because CHECK expressions are evaluated with the caller's privileges); a foreign key from `public.undo_operations.action_type` to the registry (rejected after being written: an FK to a table in the unexposed `private` schema is metadata the Supabase type generator reads, so it could perturb `src/lib/supabase/database.types.ts` in a way this repository cannot verify without first applying the migration — Docker is unavailable locally and the linked project does not yet have these migrations; a trigger gives the identical guarantee and `pg_trigger` metadata never reaches generated types, which follows the `202607170027` precedent of replacing a constraint with a trigger — there for an ACL/plan-initialization reason rather than a type-generation one, but the same substitution); dynamic dispatch from a private, fully-revoked registry table with `format('%I')` quoting (**chosen**).
- **Decision:** (1) `public.undo_operation(uuid)` keeps its exact signature, `security definer`, `set search_path = ''`, grants, shared preamble in its existing order (auth `42501` → owner lock `for update` on `undo_operations` → `P0002` not found → replay short-circuit on `status = 'undone'` → status validation → expiry), and per-branch return shapes. It owns nothing operation-specific. (2) Each family's compensation body moves **verbatim** into a private handler (`private.undo_resolve_pending_question_v1`, `…_v2_v3`, `private.undo_confirm_entry_tasks`, `private.undo_correct_entry_interpretation`) — every statement, the lock order, every SQLSTATE, every `detail` code and every return shape byte-identical, the only edit inside the compensation being `current_user_id` → `p_user_id`. Each handler additionally gains a three-statement preamble with no monolith analogue: a re-`select` of the row the router already locked, a `P0002` guard, and the ownership guard described in (3). (3) Handlers are `security invoker` with `execute` revoked from `public`, `anon`, `authenticated` and `service_role`, and each refuses an `action_type` it does not own. (4) `private.undo_operation_handlers` maps `action_type` → handler, and a `before insert or update of action_type` trigger on `public.undo_operations` refuses to record an operation whose `action_type` is unregistered, so an operation cannot exist without a handler to reverse it. (5) `private.undo_operation_definition_bundle()` exposes the router plus every registered handler as one text blob, and the pre-existing fail-closed source assertions (no `errcode = '40001'`, `55P03` present, no `pg_catalog.greatest(`) are re-pointed at it so they neither pass vacuously nor need updating when handlers are added. (6) Adding a Phase 2E undoable operation is one handler plus one registry row.
- **Reason:** The router/registry split removes the mechanical cause of a measured defect-recurrence rate while leaving every security and concurrency property byte-identical. Invoker handlers are strictly safer than definer ones here because they take the owner explicitly. The registration trigger converts "no operation silently falls through" from a code convention into a structural guarantee the database enforces on writers, and the definition bundle keeps the existing recurrence guards meaningful after the bodies move.
- **Consequences:** One new forward migration; no prior migration edited; no data migrated. The handlers run in the router's transaction, so a failed integrity check still rolls the whole undo back and leaves the row `available` — the property `phase_2c_slice_4` already asserts. Four pgTAP source-text assertions were re-pointed at the bundle and `supabase/tests/undo_operation_routing.sql` was added (19 assertions covering router posture, registry integrity, handler posture, the registration guarantee and the router's own fail-closed fallback). Rollback re-creates the monolith in a new migration and drops the registration trigger. The registry table is the first table in the `private` schema; it deliberately has no RLS, because forcing RLS would make the router's own lookup return zero rows.

## ADR-036 — Typed feature copy modules are the canonical localization mechanism; `next-intl` is removed

- **Date:** 2026-07-25
- **Status:** Accepted; implemented on branch `codex/pre-2e-foundation-hardening`.
- **Context:** Seven localization mechanisms coexisted: `src/i18n/messages.ts` (a hand-rolled typed record read by three shell files), typed feature copy modules with `satisfies` (`daily-cycle/copy.ts`, nine consumers), copy modules with only `as const`, action-local copy records, component-local copy records, 77 inline `{ "pt-BR": …, en: … }` literals across five files, and 180 `pt ? … : …` ternaries across 36 files. `ENGINEERING_STANDARDS.md:87` ("Do not scatter locale ternaries") was the most-violated line in the document. `next-intl@^4.13.2` was a declared dependency with **zero imports** anywhere in `src/` or any config, no `next-intl/plugin` wrap, no `i18n/request.ts`, no `[locale]/layout.tsx` — and `CLAUDE.md` described `messages.ts` as a "next-intl message catalog", which is false and is a plausible root cause of the fragmentation. - **Decision:** (1) The canonical mechanism is a typed feature copy module in the `daily-cycle/copy.ts` shape — explicit `type XCopy`, `satisfies Record<Locale, XCopy>`, and an accessor — so a missing key or a missing locale is a compile error. (2) `Locale`, `locales`, `isLocale` and `resolveLocale` come from `src/lib/preferences.ts`; the locale union is not redeclared. (6) New code uses only this mechanism; **no new localization mechanism may be introduced**; legacy mechanisms migrate opportunistically when a file is substantially touched, never in a big-bang pass. (7) `src/i18n/messages.ts` stays as-is for its three shell consumers and is not the canonical mechanism.
- **Reason:** The chosen mechanism already exists, already has the most consumers, and is the only one whose exhaustiveness the compiler can check. Locale-first resolution eliminates the defect class structurally rather than fixing 30 strings and waiting for the 31st. Removing an unused dependency removes both the maintenance surface and the false documentation that fed the fragmentation.
- **Consequences:** `chat/actions.ts` gains a typed copy record and its first tests ever (the slice had none); `operations/actions.ts` and `agent/actions.ts` gain typed copy records; `interpretations/actions.ts`'s three locale-parse-failure branches use `resolveLocale` with the file's existing `localized()` idiom rather than being rewritten, per the opportunistic-migration rule. `ENGINEERING_STANDARDS.md:87` gains the explicit rule, and `CLAUDE.md`'s false next-intl claim is corrected. 180 ternaries and 77 inline literals remain and are tracked in `TODO.md` as opportunistic work, not debt to be cleared in one pass. Two Vitest files that mock `@/lib/preferences` were updated to expose `resolveLocale`.

## ADR-037 — Versioned mutation RPCs get an explicit retirement policy, applied once on evidence

- **Date:** 2026-07-25
- **Status:** Accepted; implemented on branch `codex/pre-2e-foundation-hardening` (migration `202607250054`).
- **Context:** Ten mutation RPC generations across exactly two versioned families (`confirm_entry_task_candidates` unversioned + `_v2`–`_v6`; `resolve_pending_question_v1`–`_v3`) plus the Phase-1 `confirm_entry_tasks` were all executable by `authenticated`, with no `revoke ... from authenticated` anywhere in the 54-migration history. The application calls only `_v4`, `_v6` and `resolve_v3`. Retention is deliberate, but the cost is measured: migration `202607220040` is 2,368 lines because one bug had to be fixed in five bodies. Phase 2E starts its own `_vN` family. Architecture-review H3.
- **Problem:** Give versioned RPCs a lifecycle before Phase 2E creates more of them, without breaking a hidden consumer, a rollback path, or a retention claim a governing document has made — and without treating "superseded" as automatically meaning "safe to revoke".
- **Alternatives considered:** revoke all nine superseded versions now (rejected: `_v5` is an undo/replay dependency, GATE-03 claims the confirmation family remains callable, and `resolve_v1`/`_v2` retirement is explicitly deferred by PRD §21.7 and ADR-034 to a separately authorized step); a time-based rule alone, e.g. "revoke N days after supersession" (rejected: elapsed time is not evidence, and it would have retired versions a documented rollback claim still names); `drop function` rather than `revoke execute` (rejected: `undo_operations` rows still name the operations these functions recorded, and the audit trail must stay readable); deliver the policy with no revocation at all (rejected as insufficient: a policy never applied is indistinguishable from no policy, and one case does meet every criterion); policy plus exactly one evidence-backed revocation (**chosen**).
- **Decision:** (1) `docs/DATABASE.md` gains an eight-point policy covering when to version, the compatibility window, the evidence required before retirement, revoke-versus-drop, undo/replay independence, the generated-types consequence, the security posture every retained version must keep, and the documentation obligation. (2) Exactly one version is retired: `public.confirm_entry_tasks(uuid, integer[])` loses `execute` from `authenticated`. Evidence: no `.rpc` caller in `src/`, `supabase/functions/`, `scripts/` or `e2e/` and none has ever existed; no SQL caller; pgTAP references it only through `has_function` and a `prosecdef` check, both of which keep passing because the body is retained; GATE-03's retention claim names the `confirm_entry_task_candidates` family, not this unversioned Phase-1 function; and `202607180028` recorded that it had never worked for a real authenticated user before that migration fixed it, gaining no consumer afterwards. (3) The `resolve_pending_question_v1`/`_v2`/`_v3` deferral stands, untouched. (4) No function body is dropped. (5) `supabase/tests/rpc_version_retirement.sql` encodes the whole inventory as an executable contract: every retained version executable by `authenticated` and by neither `anon` nor `public`, every version `SECURITY DEFINER` with an explicit `search_path`, the retired one executable by no role while keeping its body and a `RETIRED` catalog comment, and the retired operation still routable by `undo_operation`.
- **Reason:** Evidence, not supersession, is what makes a revocation safe, and the evidence differs sharply between the two families. Revoking execute while keeping the body preserves both the audit trail and a one-line rollback. Encoding the inventory in pgTAP is what converts the policy from prose into something CI enforces — and it is now the only thing that can, because revoking a grant is a zero-diff change in the generated types and therefore invisible to every other gate.
- **Consequences:** Phase 2E's `_vN` family is born with a documented expiry and a test file that will fail if a retained version silently loses its grant or a retired one silently regains it. One-line rollback: `grant execute on function public.confirm_entry_tasks(uuid, integer[]) to authenticated;`. Nine versions remain granted, each for a written reason. The 2,368-line-fix problem is not solved by this ADR — it is reduced only as versions retire, and the pgTAP inventory is what makes future retirement decisions cheap to justify.

## ADR-038 — CI verifies the database and the worker, not only the mocked Node layer

- **Date:** 2026-07-25
- **Status:** Accepted; implemented on branch `codex/pre-2e-foundation-hardening`.
- **Context:** CI was exactly `npm ci → lint → typecheck → vitest → build`. Every Vitest suite mocks Supabase, so CI executed zero SQL, zero RLS policy, zero Playwright journey, zero Deno test and no `supabase db lint`. The 24-file pgTAP suite had **never executed as a suite in any environment** (Docker unavailable on the only workstation, documented repeatedly in `CHANGELOG.md`), and nothing checked that the migration chain still applied from an empty database. `eslint.config.mjs` ignores `supabase/functions/**` and `vitest.config.ts` includes only `src/**`, so the 592-line production worker had no static or behavioural gate at all. The project's own history shows this is where defects hide: the migration-030 alias tautology, the `SECURITY INVOKER` RPC that "had never worked for a real user", the `40001` gateway hang and a validator bound bug were all found only by executing SQL remotely. Architecture-review H1 and H10; `SECURITY.md` already listed "Teste pgTAP integral em CI com banco limpo" as required before production.
- **Problem:** Close the gate on the database and worker layers, fail closed, without production credentials, without calling real OpenAI, and without making every CI run depend on the shared linked project.
- **Alternatives considered:** run the remote smokes in CI (rejected: `scripts/linked-supabase.mjs` needs an authenticated session against the real project and the smokes create real Auth users — they stay manual or protected); install pgTAP through a migration (rejected: pgTAP is a test harness, not part of the product schema, and the linked project must not carry it — `supabase/seed.sql` runs only on local/CI `db reset`); one job doing everything (rejected: the Deno gate needs no Docker and should not wait on it); two Docker-backed jobs, one for the database and one for the journey (rejected: it pays the container start-up cost twice); relax `plan(N)` to `no_plan()` so the suite could not fail on count drift (rejected outright: the explicit plan is what catches a silently skipped assertion — the drift it exposed was a real bug); `--fail-on warning` on `db lint` (rejected: two long-standing `42804` warnings in `run_user_heartbeat` are recorded in `SECURITY.md` and unrelated to this work, so the gate would be red on arrival while `--fail-on error` still catches the defect class it exists for).
- **Decision:** (1) Three jobs in one `verify` workflow, so branch protection can require each: `app` (unchanged), `worker` (`deno check` on both deployed entrypoints, then `deno test supabase/functions/` with **no** `--allow-*` flags so the suite cannot reach a network), and `database` (local Supabase stack → `supabase db reset` → `supabase test db` → `supabase db lint --local --schema public,private --level warning --fail-on error` → production build → `e2e/foundation.spec.ts` on desktop and Pixel 7). (2) `supabase/seed.sql` installs pgTAP into `extensions` and puts `extensions` on the database `search_path`, local/CI only. (3) `playwright.config.ts` runs the production build under CI (`npm run start`, `reuseExistingServer: !CI`) instead of the dev server, so the journey proves the artifact that would ship. (4) Retries stay at zero: a flaky gate that retries is not a gate. (5) Remote smokes and the authenticated online journeys stay manual.
- **Reason:** These four commands cover exactly the layers the project's own defect history proves are unguarded, they need no secret, and `supabase db reset` is the only check that can prove the migration chain still applies from zero — which nothing did before. Excluding Studio, imgproxy and the edge runtime keeps the job inside a sane timeout while keeping the real API and Auth the journey needs. Three names `--help` advertises (`inbucket`, `analytics`, `functions`) are rejected by the CLI at runtime, and `vector` is left running because `[analytics]` cannot be excluded and consumes it. The lint is scoped to `public,private` because `seed.sql` installs pgTAP into `extensions`, whose 30 internal plpgsql_check findings would otherwise fail a gate that exists to check code this project owns.
- **Consequences:** Running the suite for the first time immediately found and fixed one real drift — `resolve_pending_question_v3.sql` declared `plan(34)` for 37 assertions, invisible for as long as the suite never ran. `deno check` also gives the worker its first static gate. Because Docker is unavailable on the development workstation, the database and journey jobs are first executed by CI on the pull request, not locally: that is named as evidence debt rather than claimed as local verification. The Deno job **was** executed locally (Deno 2.9.4 installed for the purpose): 28 tests pass and both entrypoints type-check. Two new pgTAP files were added by other workstreams in this initiative and are covered by the same gate.

## ADR-039 — A Phase 2E AI contract lives in an importable module, and 2E-COMMAND-010 parity means single declaration

- **Date:** 2026-07-25
- **Status:** Accepted; implemented in Slice 2E.1 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** PRD 2E-COMMAND-010 requires the command prompt, its response schema and their version constants to "exist once per runtime and be held identical by an automated parity test **in the shape of** `src/lib/ai/extraction-contract.test.ts`". That test compares two runtimes because it has to: `openai-provider.ts` begins `import "server-only"`, which throws outside a react-server bundler, so the Deno worker re-declares the extraction prompt and schema, and the only available guarantee is a byte-comparison performed by reading both files back as *text* (`extraction-contract.test.ts:15-33` extracts template literals with a regex). Command parsing has no worker counterpart: it runs synchronously in a Server Action, the PRD itself states "Phase 2E enqueues no jobs" (§13.14, 2E-OPERATIONS-004), and `supabase/functions/process-jobs/index.ts` routes exactly two job types, neither of them a command.
- **Problem:** Satisfy a requirement whose named mechanism — a cross-runtime comparison — has only one side, without either weakening the guarantee or manufacturing a second side to compare against.
- **Alternatives considered:** *Build a Deno command parser* so the comparison test has two runtimes (rejected: a production module with no consumer, which is precisely the speculative abstraction `ENGINEERING_STANDARDS.md` forbids and which the pre-2E hardening pass had just finished deleting — `resolveAIRoutes` and `retryProcessingJob` both went for this reason). *Put the prompt inside `openai-provider.ts`* mirroring the extraction precedent, and assert it by regex over source (rejected: it inherits a limitation that exists only because of `server-only`, and a regex over source cannot assert what a value *is*, only what its source text looks like). *Declare the contract twice inside Node* — once as the wire schema, once as the taxonomy — and hold them together by test, mirroring `extraction-parity.test.ts` (rejected: two declarations of the action vocabulary is the exact defect Epic 2E-H exists to converge away, and the PRD makes the taxonomy-as-data a requirement in its own right, 2E-COMMAND-004).
- **Decision:** (1) The prompt, the response schema, both version constants, the bounded-input classifier and the closed provider-error vocabulary live in `src/lib/ai/task-command-schema.ts`, which has no `server-only` import and is therefore importable by tests. (2) The schema derives its action enum from `@/features/task-commands/taxonomy` rather than restating it; the taxonomy is dependency-free pure data, so the import creates no cycle. (3) The 2E-COMMAND-010 guarantee is discharged as **single declaration asserted over the whole tree** — repo-wide counts for the prompt, the schema, both versions and the action list, a value-based check that the prompt's distinctive text appears in exactly one production file, and an explicit assertion that no file under `supabase/functions/` mentions the command contract or routes a `task_command` job. (4) `src/lib/ai` may import feature-owned domain vocabulary; the direction is recorded here so it is a decision rather than an accident.
- **Reason:** "Held identical" between one thing and nothing is vacuous; "declared once, and proven that no second declaration exists" is the same property stated in the form the situation actually has, and it is strictly stronger than the extraction test in one respect — the fencing and the no-task-row promise are asserted against the real exported value (an exact-equality assertion on the built user message), not against a regex match over source text. Keeping the contract out of the `server-only` module is what makes that possible, and it is a direction `docs/TODO.md` H4 already wanted for the extraction prompt.
- **Consequences:** The guarantee is weaker than a byte-comparison **the day a Deno consumer appears**. If Phase 2F adds one — a background command replay, an embedding-driven re-match — this ADR obliges converting the single-declaration test into the parity shape in the same change; the existing negative assertion over `supabase/functions/` is what will fail first and force the question. The line this ADR does *not* cross: `OpenAIProvider.parseTaskCommand` itself remains untestable by import, so its ordering, bounds and error classification are still asserted by source inspection (`task-command-contract.test.ts`). Slice 2E.1 narrowed that surface by extracting `classifyCommandText` into the importable module after a review found the provider reporting an empty command as `command_text_too_long` — a defect no test could reach — but the SDK call itself stays behind `server-only`, and a behavioural test of it needs an injectable client, which is deliberately not in this slice. The `task_command` `ai_usage_events` operation literal (migration `202607250055`) is **not** part of this ADR: widening a CHECK and its matching RPC guard is a routine additive migration, recorded in `CHANGELOG.md` and `DATABASE.md`.

## ADR-040 — The Phase 2E candidate query is `SECURITY DEFINER`, and no grant is widened to avoid it

- **Date:** 2026-07-25
- **Status:** Accepted; implemented in Slice 2E.2 on branch `codex/phase-2e-natural-language-task-updates`. Migration `202607250056` is **local only** and not applied to the linked project.
- **Context:** `public.list_task_command_candidates` is the read half of natural-language task matching. Every lexical decision it makes — exact title, phrase containment, token overlap, relation-name matching — is made by `public.normalize_entity_alias`, because 2E-MATCH-007 designates that function authoritative: it is the only `immutable` normalizer and therefore the only one usable in the ORDER BY that 2E-MATCH-003 requires before truncation. 2E-MATCH-001 asks for ownership enforced "by an explicit predicate **and** by RLS", which literally describes `security invoker`. Invoker was written first, and it cannot run: migration `202607170020:314` revokes EXECUTE on `normalize_entity_alias` from `public, anon, authenticated`, and the function carries a non-null `proconfig` (`search_path=""`), which stops the planner inlining it, so the ACL check reaches the caller. Every candidate query would raise `42501` for the only role that will ever call it. This is not a new situation: migration `202607170022` exists solely to work around the same revoke, and resolved it the same way.
- **Problem:** Run the authoritative normalizer from a query an `authenticated` user makes, without weakening a deliberate hardening decision taken in another slice, and without pretending the ownership story is unchanged.
- **Alternatives considered:** *Grant `authenticated` EXECUTE on `normalize_entity_alias`* (rejected: it would work — the function is a pure text transform that reads nothing — but 2E-OWNERSHIP-003 and PRD §14 say this phase widens no grant, and quietly reversing a hardening decision from another slice on the grounds that it is inconvenient here is not this slice's call to make; the revoke is also layered on a trigger wrapper, so reversing one half would leave an inconsistent posture). *Re-implement normalization in TypeScript for the query* (rejected outright: `normalizeEntityName` and `normalize_entity_alias` are **not** the same function — 2E-MATCH-008 characterizes three divergences across an eight-entry corpus, including one where the same word typed NFD becomes two tokens in SQL and one in TypeScript — so a row would qualify in SQL and score as unrelated in TypeScript, or worse, the reverse). *Inline the normalization expression into the candidate query* (rejected: the same defect in a quieter form, a second normalizer that drifts from the authoritative one with nothing holding them together). *A `security invoker` wrapper over a `definer` normalizer shim* (rejected: it adds a function to the trust surface to obtain exactly the privilege posture the direct `definer` has, with one more thing to audit).
- **Decision:** (1) `list_task_command_candidates` is `security definer` with `set search_path = ''`, following the `list_needs_attention` read-projection precedent and the `202607170022` workaround for this same revoke. (2) No grant is widened: `authenticated` gets EXECUTE on the new function only, and `public, anon` are revoked from it explicitly. (3) The cost is stated in the migration, in `SECURITY.md` and here rather than papered over — inside this function ownership rests on the `auth.uid()` predicate alone, because the definer owns the tables and RLS does not apply to it. (4) The three layers 2E-MATCH-001 asks for become the predicate in SQL, the owner filter in `rankTaskCandidates`, and a **raise** (never a filter) in `loadTaskCandidates`, because quietly dropping a foreign row would hide the failure of the only control there is. (5) Cross-owner denial is proven by execution in `supabase/tests/phase_2e_task_command_matching.sql` — symmetrically, in both directions, plus a null-caller case — rather than argued from role attributes.
- **Reason:** RLS was never available here; the choice was between `definer` and a function that raises `42501` for every real caller. Given that, the honest posture is to make the single remaining control explicit, test it by execution rather than by inspection, and record the residual. A test proving the other owner's identically-titled task is *absent* — not merely outranked — is stronger evidence than the role attribute it replaces.
- **Consequences:** If the `auth.uid()` predicate is ever removed or weakened, nothing else inside the function stops a cross-owner read; that is why the pgTAP cross-owner assertions are symmetric and why `SECURITY.md` names the regression explicitly. The function is exposed through PostgREST to any authenticated caller as soon as it is deployed, independently of whether application code calls it, so its argument bounds are enforced server-side rather than relying on the command schema's caps. **No index was created**: an expression index on `(user_id, normalize_entity_alias(title))` was written and removed, because index maintenance evaluates the expression as the *writing* role and `createRecord` inserts into `public.tasks` as `authenticated` (`src/features/operations/actions.ts:68`) — the same `42501`, on a live path, breaking task creation outright. It was also unusable: candidacy is a disjunction over lexical and relation signals, so the expression never sits in a sargable position. 2E-MATCH-007 designates this normalizer authoritative because it *is* index-expressible; it does not oblige a slice with nothing to index to add one.

## ADR-041 — One generated type is hand-maintained, and parity is proven three ways instead of by regeneration

- **Date:** 2026-07-25
- **Status:** Accepted; implemented in Slice 2E.2. Narrows the mechanism 2E-OPERATIONS-002 names, not its guarantee.
- **Context:** 2E-OPERATIONS-002 requires generated types to be regenerated whenever exposed schema changes, with parity "proven by content comparison, not asserted". `supabase gen types typescript` cannot run in either environment available to this phase: Docker is unavailable on the development workstation, and in CI the CLI refuses to start without an access token even when pointed at a local `--db-url` it never leaves. Satisfying the CLI offline required a credential-shaped literal in the workflow, which GitHub push protection rejected — correctly. Migration `202607250056` adds `list_task_command_candidates` with a 7-argument, 30-column signature that `database.types.ts` must describe for `candidates.ts` to type its RPC call at all.
- **Problem:** Add an exposed function to the generated types when the generator cannot be run, without either shipping an unverified hand-edit or blocking the slice on tooling that has no offline path.
- **Alternatives considered:** *Run the generator against the linked project* (rejected: it would emit types for a schema that does **not** contain this function, since `202607250056` is deliberately undeployed — the output would be wrong in the one way that matters). *Put the credential-shaped literal in the workflow* (rejected: push protection is correct, and defeating a secret scanner to satisfy a type generator is a trade nobody should make). *Type the RPC call as `any` or cast it* (rejected: `ENGINEERING_STANDARDS.md` forbids unjustified `any`, and the 30-column projection is exactly where a silent column reorder would be scored rather than caught). *Defer the whole slice until Docker is available* (rejected: the constraint is environmental and indefinite, and the guarantee is obtainable without the tool).
- **Decision:** (1) The `list_task_command_candidates` entry in `src/lib/supabase/database.types.ts` is **hand-written**, and that is stated wherever the file is discussed rather than left to look generated. (2) The parity guarantee is discharged by three independent checks, all green: the migration declares the signature; `database-types-parity.test.ts` compares the generated types against that declaration by content — names, ordering, optionality and type mapping; and `supabase/tests/phase_2e_task_command_matching.sql` pins both against `pg_proc.proargnames` and `pronargdefaults` from the **real catalog** in a from-zero CI database. (3) The whole-file regeneration check is **withdrawn**, recorded in `docs/TODO.md`, and is owed back the moment the generator has an offline path.
- **Reason:** The third check is what makes this sound, and it is stronger than regeneration would have been: regeneration proves the file matches whatever schema the generator was pointed at, whereas `proargnames` from `pg_proc` proves the file matches the schema the migration chain actually builds from empty. The first two checks are what fail fast, locally and without Docker; the third is what cannot be fooled by a shared mistake between the migration and the hand-edit.
- **Consequences:** A future column change to this function must update three places or one of the three checks reds — the intended cost, and cheaper than it sounds because `create or replace` cannot change a `RETURNS TABLE` shape anyway (`42P13`), so any such change is already a `_v2` under ADR-037. The claim "generated types were regenerated" is **not** made for this slice anywhere; `STATE.md`, `CHANGELOG.md` and the slice report all say hand-written. Nothing else in `database.types.ts` is hand-maintained, and this ADR is not a licence to extend the practice: it applies to one function, under a named tooling constraint, with a named path back.

## ADR-042 — Postgres owns the Phase 2E preview fingerprint; TypeScript never hashes

- **Date:** 2026-07-26
- **Status:** Accepted; implemented in Slice 2E.3 on branch `codex/phase-2e-natural-language-task-updates`. Migration `202607250057` is **local only** and not applied to the linked project.
- **Context:** 2E-PREVIEW-004 requires a preview to carry "a fingerprint over task identity, observed pre-state, canonical patch, policy version, owner and operation key", and 2E-IDEMPOTENCY-003 requires that fingerprint to be "stable under key reordering and insignificant whitespace". The value is not decorative: Slice 2E.4's mutation RPC has to derive the *same* value to recognize a replay (2E-UPDATE-006), and Slice 2E.5 has to bind a server-issued single-use confirmation token to it (2E-DESTRUCTIVE-002). Every one of the fourteen `request_fingerprint` values this repository already computes is computed in SQL (`202607190032:352`, `202607210036:498`, `202607220038:780`, `202607220039:763`, `202607220040:578,1226,2157`, `202607220041:1184`, `202607220044:1101`, `202607230046:124`, `202607230047:116`, `202607230048:210`, `202607230050:248`, `202607230051:211`).
- **Problem:** Produce one canonical request identity that both a Node preview and a Postgres RPC agree on, without creating a second cross-language canonical-serializer parity surface — the exact defect class 2E-MATCH-008 characterizes one slice earlier for the entity normalizer, where the two languages provably *cannot* be made to agree.
- **Alternatives considered:** *Hash in TypeScript and pass the digest to the RPC* (rejected: the RPC must be able to derive the value itself, or a client could bind a token to a fingerprint the server never computed — and the digest would then be an unverified client claim rather than an identity). *Hash in both and hold them equal by test* (rejected: they cannot be made equal. `jsonb` stores an object with its keys sorted **by length, then by bytes**, while `src/features/task-commands/schema.ts`'s `canonicalize` sorts with `Object.keys(value).sort()`, which is lexicographic by UTF-16 code unit; the two also disagree on separators and on how they render an instant. Making them agree means reimplementing jsonb's ordering rule in TypeScript and keeping it correct across Postgres versions — a parity surface with no upside, since only one of them ever needs to hash). *Pass the whole payload as text the caller serialized* (rejected: it moves canonicalization to the client, so 2E-IDEMPOTENCY-003 becomes a convention someone has to remember rather than a structural property). *Add the fingerprint to `202607250056`* (rejected on attribution and budget grounds: a separate function costs no `42P13` budget, and keeping it separate keeps `…056` identifiable as Slice 2E.2's artifact that Slice 2E.3 amended).
- **Decision:** (1) `public.task_command_fingerprint(uuid, uuid, text, jsonb, jsonb, text, text)` is the only place a Phase 2E fingerprint is computed. `src/features/task-commands/fingerprint.ts` owns the *payload* — which seven values, in which shape — and hashes nothing; no module in that directory may. (2) `jsonb_build_object` **is** the canonicalizer: jsonb sorts keys and discards whitespace before `::text` ever runs, so 2E-IDEMPOTENCY-003 holds structurally rather than by convention. (3) **No `timestamptz` argument and no bare timestamp inside the hashed jsonb.** `to_jsonb(timestamptz)` renders through the session's `TimeZone` GUC, which `set search_path = ''` does not pin, so the same logical payload would hash differently for two callers in two zones; instants arrive already rendered as text by the caller that read them. (4) The function is `immutable`, `strict` and deliberately **not** `security definer`: it reads no table, which is what makes 2E-PREVIEW-001 and 2E-PREVIEW-007 structurally true and why computing a fingerprint cannot re-read the task and reopen the TOCTOU window `observed_before` exists to close. `strict` mirrors `public.normalize_entity_alias` (`202607170020:97-102`) — a null input yields null rather than a plausible-looking hash of a hole. (5) **The fingerprint is identity, never authorization.** It is granted to `authenticated` and all seven inputs are values the caller already holds, so a client can derive it; 2E-DESTRUCTIVE-002's server-issued single-use token is a separate mechanism, and Slice 2E.5 must not accept a matching fingerprint as evidence of confirmation. (6) **Only `TASK_COMMAND_POLICY_VERSION` is hashed**, not `TASK_MATCH_POLICY_VERSION`. 2E-PREVIEW-004 says "policy version", singular, and the two answer different questions: the match policy decided *which* task this is about, which the fingerprint already binds by `taskId`, while the command policy decides what the patch is allowed to mean — which is what the preview asserts and what Slice 2E.4 applies. The match policy version travels in the preview DTO for provenance instead. (7) Output is 64 lowercase hex characters, already the shape `undo_operations_request_fingerprint_check` (`202607190032:20-27`) accepts, so Slice 2E.4 stores it with no new column and no new constraint. (8) The fingerprint is **replay identity and token binding, never a staleness gate**: staleness is a separate typed column-by-column comparison, because conflating them would force the RPC to re-render the locked row's timestamps as text byte-identically to what PostgREST emitted.
- **Reason:** A contract two runtimes must agree on byte-for-byte is only safe when exactly one runtime produces it. That is the same conclusion ADR-040 and 2E-MATCH-007 reached for the normalizer, for the same reason, and it is cheaper here because the value has no consumer that needs it before the RPC does. Everything else in the decision follows from removing the ways a digest can be right about the wrong thing: an unpinned timezone, a substituted null, a definer that could read a row, or a hash a client could present as proof of consent.
- **Consequences:** **Points (2), (3) and (6) are irreversible the moment Slice 2E.4 stores a fingerprint.** Changing the canonicalizer, the instant's representation, or the set of hashed inputs would invalidate every stored fingerprint and every unexpired confirmation token, and would do so **silently** — a replay would simply stop being recognized as one, with no error anywhere. That is why `supabase/tests/phase_2e_task_command_fingerprint.sql` asserts all four properties directly rather than trusting them, and why `TASK_COMMAND_POLICY_VERSION` moved to `2026-07-25.2` in the same slice that added `targetStatus` rather than later. Obtaining a fingerprint costs a database round trip that a TypeScript implementation would not, which is accepted: it is one `immutable` call with no table access, and the preview already needs a client for the candidate query. `fingerprint.ts` has **no production caller** in this slice — its consumers are Slices 2E.4/2E.5 — and its behaviour is proven through an injected client double; that is the same consumer-less-contract situation ADR-043 governs, resolved differently here because the *migration* is the artifact and a Postgres function with no caller is inert, whereas a React component with no caller is a maintenance liability. Finally, `202607230051:203` hashes a timestamptz-derived value and therefore carries the latent timezone bug point (3) avoids; this ADR does not fix that migration, and doing so would need its own change with its own replay analysis.

## ADR-043 — Phase 2E preview and disambiguation components are deferred to Slice 2E.7

- **Date:** 2026-07-26
- **Status:** Accepted; recorded in Slice 2E.3 on branch `codex/phase-2e-natural-language-task-updates`. Obliges Slice 2E.7 to own 2E-A11Y-001/002/003 in the Phase 2E traceability matrix.
- **Context:** Epic 2E-C's acceptance criteria (PRD §19.1) read: "Every `2E-DISAMBIG` and `2E-PREVIEW` requirement passes; previews are read-only, truthful about linked effects and the undo window, fingerprinted, and detect `no_change` and staleness; **the surfaces are keyboard operable and localized**; no mutation exists in this slice." Slice 2E.3 delivers the projections — `buildTaskCommandPreview` and `buildTaskDisambiguation`, both pure, both localized through a typed `copy.ts` — and delivers **no surface at all**: no component, no route, no Server Action.
- **Problem:** Decide whether to satisfy the keyboard-operability clause now by building components with no consumer, or to record the clause as deliberately unmet and move it to the slice that has one.
- **Alternatives considered:** *Build the components now* (rejected — see Reason). *Restructure the phase so Epic 2E-C carries the surface* (rejected: it would put a preview UI in front of a mutation that does not exist yet, so the only reachable dispositions would be `no_change`, `rejected_stale` and `refused`, and the Apply control the whole surface exists around could not be rendered honestly). *Weaken the clause in the PRD* (rejected: the PRD is approved and its acceptance criteria are not edited to match what a slice happened to do; the honest move is to record the deviation and name its owner).
- **Decision:** (1) Epic 2E-C's "the surfaces are keyboard operable and localized" clause is **deliberately not met by Slice 2E.3**, stated as such in the slice report §2, §12 and §13, in `STATE.md`, and in `CHANGELOG.md` — not quietly omitted. (2) The *localized* half **is** met: all Phase 2E copy is in `src/features/task-commands/copy.ts` per 2E-I18N-001 and ADR-036, covering all twelve 2E-UX-001 outcomes in both locales with no fallback, and dates render in the caller's timezone and locale per 2E-I18N-002. (3) **Slice 2E.7 owns 2E-A11Y-001, 2E-A11Y-002 and 2E-A11Y-003** in the traceability matrix, together with the Playwright desktop/mobile journeys in both locales that Epic 2E-G requires. (4) No React component, route or Server Action for the command surface is added before Slice 2E.7.
- **Reason:** Three independent reasons, any one of which would be sufficient. **The shape is not knowable yet:** Slice 2E.4 adds the Apply control and the undo affordance, 2E.5 adds a confirmation dialog with its own 2E-A11Y-004 semantics, and 2E.6 adds a creation offer — a surface built now would be rewritten three times, and each rewrite would re-open the accessibility assertions it had already passed. **Two of the three requirements are untestable today:** with no mutation there is no async action, so 2E-A11Y-002 ("focus moves predictably after an async action") has no action to move focus after, and 2E-A11Y-003 ("outcome changes are announced through a live region") has no outcome transition to announce. Asserting them against a static render would be a passing test that proves nothing, which is worse than an honestly deferred one. **The consumer-less-contract precedent is explicit in this repository:** the pre-2E hardening pass *removed* `retryProcessingJob` for exactly this reason — a generalized Action written in Slice 2X.5 for a UI that later shipped a different Action (`reprocessEntry`), leaving a maintained, tested, dead code path that had to be deleted rather than adopted. `ENGINEERING_STANDARDS.md` allows an extension point only for a real current consumer, and the same pass deleted `resolveAIRoutes` on the same grounds.
- **Consequences:** Epic 2E-C cannot be reported as fully met, and the Phase 2E traceability matrix must show 2E-A11Y-001/002/003 as **deferred with a named owner** rather than as met or as unmapped — the generator fails closed on inventory drift (PRD §19.2), so this is enforced rather than remembered. Slice 2E.7's scope grows accordingly: it inherits the whole command surface's keyboard operability, focus management and live-region announcement, across Chat and the task surfaces, on desktop and mobile, in both locales. The projections are exposed to a real risk this ADR accepts: a pure contract with no consumer can be *wrong in a way no test notices*, and this slice demonstrated exactly that — an adversarial review found the preview rendering a bare `"+1"` where a relation name belonged, a defect a component would have made visible immediately. The mitigation is that the projections' output is asserted by value in `preview.test.ts` and `disambiguation.test.ts` rather than by shape, and that the copy is keyed by declared unions so no rendered string can originate outside `copy.ts`. This ADR is scoped to Phase 2E's command surface; it is not a general licence to ship projections without consumers, and the obligation it creates on Slice 2E.7 is the price of using it.

## ADR-044 — Phase 2E's mutation RPC is unversioned, and the version lives in the request contract

- **Date:** 2026-07-26
- **Status:** Accepted; recorded in Slice 2E.4 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** PRD 2E-UPDATE-001 requires "one versioned `SECURITY DEFINER` RPC" for all Phase 2E task mutations, and 2E-UPDATE-018 requires the RPC to be "added to the versioned-RPC inventory and its retirement-policy test in the same change, so the ADR-037 CI check does not red". ADR-037's inventory is not a table or a function: it is prose plus a markdown table in `docs/DATABASE.md:99-125`, and an executable contract at `supabase/tests/rpc_version_retirement.sql` (`plan(24)`) which hardcodes the nine retained signatures across **four separate literal arrays** and asserts at lines 186-200 that no versioned public function exists outside the two inventoried families.
- **Problem:** Decide whether the first-generation mutation RPC is named `apply_task_command_v1` or `apply_task_command`.
- **Alternatives considered:** *Name it `_v1`* (rejected — see Reason). *Name it unversioned and leave `rpc_version_retirement.sql` untouched* (rejected: that file's `prosecdef` + `search_path=""` assertion iterates a hardcoded ten-element array, so a new definer function would never be checked by it, and the posture guarantee 2E-UPDATE-001 asks for would rest on this slice's own pgTAP file alone).
- **Decision:** (1) The function is `public.apply_task_command`, with no version suffix. (2) The **request contract** carries the version in two places that are already load-bearing: `TASK_COMMAND_POLICY_VERSION`, which is one of the seven inputs hashed into every `request_fingerprint`, and the `'taskcmd-v1:'` prefix namespacing every `undo_operations.operation_key`. (3) It is nonetheless **added to `rpc_version_retirement.sql`'s `prosecdef` + `search_path=""` array**, and to nowhere else in that file — it does not match `_v[0-9]+$`, so it neither joins nor forks an inventoried family. `plan(24)` is unchanged, because adding an element to a literal array is not an assertion. (4) No `docs/DATABASE.md` inventory row is added, because the inventory tracks *families that have forked*.
- **Reason:** ADR-037 §1 warrants a new version only when a closed input shape changes incompatibly, and there is no predecessor for this function to be incompatible with — the situation the policy was written for is `confirm_entry_task_candidates` reaching `_v6`. `list_task_command_candidates` and `task_command_fingerprint` set the unversioned precedent inside this same phase and required no edit to that test. A `_v1` suffix would have red-ed line 195 immediately and cost six coordinated edits — four literal arrays, a family-size count, a `_v2`-absence guard, a `plan()` bump and a docs row — to a test whose purpose is policing sprawl that has not happened. 2E-UPDATE-001's word "versioned" is satisfied by a contract that carries a version and can be superseded, which this one does: a future incompatible shape becomes `apply_task_command_v2`, at which point the family genuinely exists and the inventory genuinely applies.
- **Consequences:** The first incompatible change to this RPC's argument list creates the family the inventory expects and must add the row, the arrays and the guards then — the work is deferred, not avoided. Because the function returns a scalar `jsonb` rather than a `RETURNS TABLE`, `create or replace` can change its body and its result shape freely, which is exactly what lets Slice 2E.5 enable `cancel_task` and `restore_task` on the same function instead of introducing a second write path; that freedom is the reason the versioning question is less pressing here than it was for `202607250056`, whose column list is frozen by `42P13`. The risk accepted is that a reader looking for a version in the identifier will not find one, which the `comment on function` and this ADR mitigate.

## ADR-045 — `no_change` is decided before the idempotency reservation, so it can write nothing at all

- **Date:** 2026-07-26
- **Status:** Accepted; recorded in Slice 2E.4 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** PRD 2E-UPDATE-009: "`no_change` is detected at preview time and terminal there. The RPC carries the same check as defence in depth: should it observe an empty canonical delta — reachable only by replay or a concurrent write — it writes **no task update, no audit row and no undo row**, and returns `no_change`." Separately, 2E-UPDATE-007 requires the undo row to be inserted **before any task write**, following `confirm_entry_task_candidates_v6`, whose reservation at `202607220044:1108` is the first write in the function and precedes even its `55P03` gate.
- **Problem:** Those two requirements collide. If the reservation is the first write and the delta is evaluated after the row is locked, then a `no_change` observed under the lock has already written an `undo_operations` row — and a `return` cannot un-write it.
- **Alternatives considered:** *Delete the reservation on the `no_change` path* (rejected: `authenticated` holds no DELETE on `undo_operations`, so the definer function would be the only path that ever removes a reservation, and a deleted operation key is indistinguishable from one that never existed — which breaks replay for a client retrying the same request). *Raise instead of returning* (rejected: it rolls the reservation back correctly but makes `no_change` an error, and 2E-UPDATE-009 says "returns `no_change`", while `TASK_COMMAND_OUTCOMES` lists it as a first-class terminal outcome and PRD §11.1 says explicitly it "is a first-class terminal outcome, not a failure"). *Take the row lock before the reservation* (rejected: the replay branch must return the stored result **without** re-evaluating the staleness gate — `202607220044:1140-1158` returns before ever touching `public.entries`, deliberately — and locking first would make a legitimate retry receive `55P03` instead of its original answer, because `for update` re-reads the committed row).
- **Decision:** (1) The canonical delta is computed against the **caller-supplied** pre-state before the reservation, and an empty delta returns `no_change` immediately: no reservation, no lock, no fingerprint, no write of any kind. (2) An unlocked ownership probe runs **before** that return, so a task the caller does not own and a task that does not exist both yield `P0002 'Task not found'` and stay indistinguishable (2E-OWNERSHIP-002). (3) The post-lock delta check is retained as defence in depth but raises `P0001` + `2E_TRANSITION_INTEGRITY` rather than returning `no_change`, because by that point the staleness gate has already proven the claim equals the locked row.
- **Reason:** The claimed pre-state is unverified at the point of the early return, and that is acceptable **because the outcome writes nothing**. The worst case is a mis-informed answer to a caller who supplied a false pre-state about their own task — no row changes, no ledger entry, no audit trail, nothing another user can observe. 2E-UPDATE-009 itself makes the preview the authoritative place `no_change` is decided; the RPC's copy is explicitly "defence in depth", and defence in depth that writes a ledger row is not defence. The post-lock branch becomes genuinely unreachable rather than dead-by-accident: with the twelve-column staleness gate passing, the locked row and the claim are equal by construction, so an empty delta there is an invariant violation and should be reported as one.
- **Consequences:** `no_change` is the only outcome of this RPC that performs no read of the locked row, so it is also the only one that cannot report reminder or relation state observed under a lock — which is consistent, since it changes neither. The pgTAP suite asserts the whole declared return shape for `no_change` **and** that it creates zero `undo_operations` rows and zero `audit_logs` rows, pinned to literals. A caller wanting a verified `no_change` must obtain it from the preview, which is where 2E-UPDATE-009 puts it. Slice 2E.5's confirmation token must not be issued for a `no_change` preview, which `loadTaskCommandFingerprint` already enforces by returning null for every disposition other than `previewed` and `matched_requires_confirmation`.

## ADR-046 — The shared task audit trigger derives its actor from a transaction-local setting

- **Date:** 2026-07-26
- **Status:** Accepted; recorded in Slice 2E.4 on branch `codex/phase-2e-natural-language-task-updates`. First Phase 2E change to an object the existing product already uses.
- **Context:** PRD 2E-UPDATE-010 requires every applied change to record actor, source, reason, target and resulting state, and states the mechanism: "Because `audit_task_change` co-fires and hardcodes `actor='user'` on UPDATE, the phase makes that trigger derive its actor from a transaction-local setting the RPC sets, defaulting to `'user'` so `persistTaskStatus` behaviour is byte-identical; the same migration extends the trigger's watched columns to `title` and `description`, which it currently ignores entirely." 2E-PROVENANCE-003 requires an automatic action to be distinguishable from a user-initiated one "everywhere it is recorded, including in the shared audit trigger". A grep for `set_config`/`current_setting` across `supabase/migrations`, `src`, `supabase/functions` and `docs` returns **nothing** — the only uses in the repository are pgTAP fixtures setting `request.jwt.claims`.
- **Problem:** There is no precedent for the setting's name, its default, its scope, or what happens when it is absent — and `audit_task_change` fires on every `public.tasks` INSERT and UPDATE in the product, including `persistTaskStatus`, `createRecord` and `private.undo_confirm_entry_tasks`.
- **Alternatives considered:** *A new column on `public.tasks` carrying the actor* (rejected: it would need a value on every existing write path, and PRD §10.2 forbids a command setting `created_by`). *Read the actor from `auth.uid()` vs `service_role`* (rejected: it cannot distinguish a user's own command from a user's own undo, which is what 2E-DESTRUCTIVE-007 needs). *`current_setting(key)` without `missing_ok`* (rejected: it raises `42704` when unset, so every `public.tasks` UPDATE not routed through the RPC — a plain client edit, a pgTAP fixture, the heartbeat — would fail). *`is_local => false`* (rejected: on a PgBouncer-fronted Supabase connection the value would outlive the transaction and mis-attribute an unrelated later request). *Raise on an out-of-vocabulary value* (rejected: `audit_logs.actor` has a three-literal CHECK, so a bad value would raise `23514` from inside a trigger on an unrelated write — worse than a mis-attributed row).
- **Decision:** (1) The setting is `app.audit_actor`. (2) It is read as `coalesce(pg_catalog.current_setting('app.audit_actor', true), 'user')`, with `missing_ok = true`, and normalized through a `case` against `('user','agent','system')` that falls back to `'user'` rather than raising. (3) It is written with `pg_catalog.set_config(..., true)` — `is_local => true`, transaction-scoped. (4) **Only the UPDATE branch derives it.** The INSERT branch's existing `case when new.created_by = 'agent' then 'agent' else 'user' end` is untouched. (5) `public.apply_task_command` sets `'user'` explicitly; both undo handlers set `'system'`. (6) The trigger's watched-column predicate gains `title` and `description`, and both jsonb payloads gain those keys. (7) The trigger **definition** is not recreated and gains no `update of` column list.
- **Reason:** `app.` is the conventional custom-GUC prefix and cannot collide with the `request.*` namespace Supabase and PostgREST own. The default of `'user'` is mandated verbatim by 2E-UPDATE-010 so `persistTaskStatus` stays byte-identical, and `missing_ok` plus normalization are what make that true for every caller that does not know the setting exists. The INSERT branch is left alone because it answers a different question — who *authored* the task, not who performed *this* write — and because Slice 2E.6's creation RPC will set `created_by = 'agent'`, so that branch already reports `'agent'` for an agent-created task without any change. Splitting apply (`'user'`) from undo (`'system'`) is the part that earns the mechanism: the trigger row describes who performed the column write, which for an undo is the stored compensating operation executed by the system, while the handler's own `operation_undone` row records `actor = 'user'` and the reason "User executed the stored compensating operation" — who *asked*. Together they are strictly more informative than either alone, and they make 2E-DESTRUCTIVE-007's "user cancellation and undo-driven cancellation are distinguishable in audit" provable at the trigger layer in Slice 2E.5 without reopening this trigger again. No `update of` list is added because `create or replace function` deploys the watched-column change with zero trigger churn, whereas a column list would have to enumerate all seven watched columns and any future addition would silently stop auditing.
- **Consequences:** This is the first Phase 2E migration that is **not** inert on a dormant surface — it changes an object every existing task write already fires. The change is designed to be behaviourally neutral for existing callers (the actor defaults to what was hardcoded; the two new watched columns only add rows that were previously not written at all), and the evidence is the `database` job's green foundation journey on desktop and Pixel 7 plus pgTAP assertions that a plain client UPDATE still records `'user'` and does not raise. Rollback means re-pasting `202607160014`'s body in a further forward migration, not dropping anything. The shape of every future `task_updated` row changes: both jsonb objects now carry `'title'` and `'description'`, joining the existing quirk that `manual_priority` is written under the key `'priority'` — jsonb key names in this trigger have never been required to match column names. Extending the watched columns also closes the blind spot 2E-MATCH-006 declared: the audited-recency signal now has a historical row for a rename or an appended note, which it previously did not, so the matcher's recency evidence becomes truthful for Phase 2E's own writes from this migration forward — but **not retroactively**, and no backfill is attempted.

## ADR-047 — The destructive confirmation is a server-minted row, addressed by its own id, with no expiry

- **Date:** 2026-07-27
- **Status:** Accepted; recorded in Slice 2E.5 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** PRD 2E-DESTRUCTIVE-002 requires "a server-issued, single-use token bound to one preview fingerprint, owner and operation key", and states that "a client-derivable value is not confirmation evidence" — a sentence `202607250057:49-53` had already anticipated by recording that `task_command_fingerprint` is granted to `authenticated` and computed from values the caller already holds, so the digest alone can never be the evidence. 2E-UPDATE-001 requires **one** RPC for every Phase 2E task mutation, and ADR-044 records that `public.apply_task_command` returns a scalar `jsonb` so `create or replace` may change its body freely — but its **argument list** is not free: adding an eighth parameter creates a second function beside the first rather than replacing it.
- **Problem:** The apply RPC cannot accept a token as an argument, so decide what the token is, where it lives, how it is presented, and whether it expires.
- **Alternatives considered:** *An eighth argument* (rejected: it is a second apply RPC, which 2E-UPDATE-001 forbids and which would fork `database.types.ts`, the pgTAP signature pins and the parity test). *A token inside `p_patch` or `p_pre_state`* (rejected: both are hashed into the digest the token is bound to, which is circular, and both have closed key sets). *A separate secret column with its own format* (rejected: a second capability mechanism for a problem `public.undo_operation` already solves with a uuid primary key plus an ownership predicate). *An `expires_at` column* (rejected — see Reason).
- **Decision:** (1) `public.task_command_confirmations` is the ledger; its `id uuid` **is** the token. (2) **No role may INSERT, UPDATE or DELETE it**, including `service_role`; both writers are `SECURITY DEFINER` functions and `authenticated` holds `select` only, under forced RLS. (3) `public.issue_task_command_confirmation` takes the **same seven arguments** as the apply RPC and derives the binding digest itself through `public.task_command_fingerprint`; it never accepts one. (4) The apply RPC does not receive the token — it resolves the row by `(auth.uid(), btrim(p_operation_key))` and requires the stored digest to equal the one it derives, all as predicates of the single guarded `UPDATE` that consumes it. (5) **No expiry.**
- **Reason:** All three bindings 2E-DESTRUCTIVE-002 names are enforced, and none of them is a value a caller may assert — which is the property the requirement is actually about. The client presenting the token back would add nothing: a malicious client can call the issuing RPC itself either way, so what the protocol really guarantees is that confirmation is *server-mediated, payload-bound and single-use*, and that is exactly what the guarded UPDATE establishes. Making the grants, rather than the two functions, the place "server-issued" and "single-use" live is what stops a future third writer from quietly weakening either. Expiry is rejected on three grounds, the third decisive: §13.6 requires none; the digest binds the observed pre-state and the twelve-column staleness gate independently refuses any payload whose pre-state moved, so a stale confirmation is unusable rather than dangerous; and **2E-UX-001's outcome vocabulary is a closed list** that `copy.ts` and the exhaustiveness test run against, so an expired confirmation would have to either widen a closed contract or misreport itself as `refused`.
- **Consequences:** An abandoned confirmation lives forever, bound to a payload that a single subsequent edit to the task makes unappliable. `no_change` returns before the gate, so a command that turns out to be a no-op leaves its confirmation unspent — asserted, and harmless for the same reason. The consuming UPDATE sits **after** the replay branch and **inside** the mutating transaction: a replay therefore consumes nothing, and any raise after consumption rolls it back, so a lost `2E_TRANSITION_INTEGRITY` does not cost the user a deliberate act. Slice 2E.7 renders the two-call flow; nothing calls either RPC yet.

## ADR-048 — The creation-undo collision is closed by one shared predicate; the candidate-slot collision was withdrawn as unreachable

- **Date:** 2026-07-27
- **Status:** Accepted **as amended**; recorded in Slice 2E.5 on branch `codex/phase-2e-natural-language-task-updates`. Its second half — problem (b) below, `2E_CANDIDATE_REMATERIALIZED`, `private.task_candidate_slot_taken` and the `unique_violation` traps — was **withdrawn on evidence before the slice was accepted**, and the withdrawal is recorded here rather than by deleting the reasoning, because the reasoning is what a future reader needs in order not to repeat it. Everything about the creation-undo collision stands.
- **WITHDRAWN, and why:** problem (b) claimed that a confirmed candidate leaves no `entry_task_candidate_resolutions` row, so cancelling a task frees its candidate slot under `202607220040`'s partial indexes. **That is true of the RPC and false of the system.** `public.record_entry_task_candidate_confirmation` (`202607220041:299-364`) is an `after insert or update` trigger on `public.tasks` that writes exactly that row for every active task carrying candidate provenance — which is precisely *why* `confirm_entry_task_candidates_v6` only writes rows for non-`confirmed` dispositions, and why `undo_confirm_entry_tasks` deletes by `task_id = any(entity_ids)` as well as by `undo_operation_id`. The row is keyed `unique (user_id, interpretation_id, candidate_index)`, it survives the task's cancellation, and the `2C_TERMINAL_DISPOSITION` gate reads it: the duplicate that would take the freed slot can never be created. The only path that *does* free the slot is a creation-undo, which deletes those rows — and that path is already refused by `2E_CREATION_UNDONE` at step 15b, before the row is even locked. So the guard was subsumed by one that runs earlier, and its token was a declared member of a closed vocabulary no reachable state can provoke: the defect ADR-049, written in this same slice, codifies. Four of five review lenses found it independently. In its place, the migration and the pgTAP suite now assert that `tasks_record_candidate_confirmation` still exists — because that trigger is the load-bearing reason no guard is needed, and nothing else in the repository would notice if it were dropped.
- **Context:** PRD 2E-DESTRUCTIVE-008 requires the cancel/creation-undo collision to be handled in **both** orderings, with a task whose creation operation is itself `undone` "treated as deleted", refused with `55P03` and a declared detail code; 2E-DESTRUCTIVE-009 requires "the same guard" on every other door — `restore_task` and the recovery affordance.
- **Problem:** Two distinct states make returning a task from `cancelled` to an active status illegitimate, and only one of them was named by the PRD. (a) `private.undo_confirm_entry_tasks` compensates a creation by *cancelling*, with `and status <> 'cancelled'` (`202607250052:310-314`), so on an already-cancelled task it changes nothing — the ten scalars still equal the `applied_state` the cancel recorded, the ten-column undo guard passes, and the cancel-undo puts a deleted task back. (b) `202607220040:13-19` made candidate identity unique only over non-cancelled rows, and `confirm_entry_task_candidates_v6` records a resolution row only for a disposition **other than** `'confirmed'` (`202607220044:1357-1358`) — so a confirmed candidate leaves no ledger entry, the `2C_TERMINAL_DISPOSITION` gate never fires for it, and cancelling frees the slot for a duplicate the entry surface immediately re-offers. Restoring afterwards is a bare `23505`, which `apply.ts` maps to `undeclared_failure` with `retryable: true`.
- **Alternatives considered:** *One token for both* (rejected: different causes with different remedies — a creation-undone task is permanently deleted, a slot-taken task is blocked by a duplicate the user can still cancel — and telling a user their task was deleted when it is merely blocked is a lie the copy would have to carry). *Guard every field-undo rather than the cancel-undo* (rejected: unnecessary, and it would refuse legitimate compensations; the exhaustiveness argument is proven instead). *Let the `23505` surface and add a mapper case* (rejected: 2E-UPDATE-017 makes the vocabulary a closed list of `2E_*` DETAIL tokens, and a raw SQLSTATE is not a member of it). *Exclude slot-taken tasks from the listing too* (rejected: hiding the row hides the only place the situation is legible).
- **Decision:** (1) Two `private` predicates, `task_creation_undone` and `task_candidate_slot_taken`, each defined **once** and read by every door. (2) `2E_CREATION_UNDONE` (`55P03`) closes the cancel-undo and `restore_task`; the candidate listing **excludes** such tasks through the same predicate, by a body-only `create or replace` of `list_task_command_candidates`. (3) `2E_CANDIDATE_REMATERIALIZED` (`55P03`) closes the same two doors for the slot collision, backed by a `unique_violation` trap on both status writes for the concurrent case; the listing does **not** exclude those tasks. (4) `task_candidate_slot_taken` mirrors both partial indexes exactly, **including their absence of an owner column**. (5) The creation-family rows are locked `for update` **before** `public.tasks`, everywhere they are read under a write.
- **Reason:** The cancel-undo is the only field-undo that can pass the ten-column guard on a creation-undone task, because that guard compares `status` against the status the forward action *left*, a creation-undo forces the row to `cancelled`, and `cancel_task` is the sole action in §11.2 whose target status is `cancelled` — `set_status` is bounded to the six non-terminal precisely so it cannot be a second route. That is an argument about the other fourteen actions, so the pgTAP suite proves it with a rename rather than asserting it. Owner-scoping the occupant of `task_candidate_slot_taken` would make the predicate **laxer** than the constraint it anticipates, which is the one direction that lets a `23505` through; cross-owner occupancy is unrepresentable anyway, so the difference is theoretical while being at least as strict as the index is not. The lock order is forced: `public.undo_operation` takes the operation row `for update` and only then calls a handler that writes `public.tasks` (`202607250052:654-657`), so acquiring the task first would give the two paths opposite orders and a deadlock. The lock covers the family regardless of `status` while the refusal reads only `undone` rows, because locking only the `undone` ones would leave an `available` row free to become one underneath.
- **Consequences:** A deleted task is a candidate for **nothing** — not `restore_task`, not `rename_task`, not the recovery listing — which is stricter than §13.6 asks and is the correct reading of "treated as deleted". The comment at `taxonomy.ts:301-305` claiming re-confirmation was gated by the resolution ledger was **false** and is corrected in the same change. The `unique_violation` trap opens one subtransaction per status command; that cost is accepted against never surfacing an undeclared SQLSTATE that a mapper would call retryable. The concurrent path the trap exists for is not provoked by pgTAP — it needs two sessions — and is recorded as owed with the remote smoke.

## ADR-049 — A declared failure code is retired when nothing can raise it

- **Date:** 2026-07-27
- **Status:** Accepted; recorded in Slice 2E.5 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** `2E_ACTION_NOT_ENABLED` was declared by Slice 2E.4 to refuse `cancel_task` and `restore_task` until confirmation evidence existed. With both enabled and all fifteen actions resolved from the taxonomy `case`, its `else` terminator is unreachable while the closed enum and that `case` list the same members.
- **Problem:** Keep a declared, localized, pgTAP-asserted code whose raise no state can reach, or retire it.
- **Alternatives considered:** *Keep it as the terminator's token* (rejected — see Reason). *Delete the terminator too* (rejected: an action added to the enum and forgotten in the taxonomy would fall through with null policy arrays and be validated against nothing).
- **Decision:** The token is removed from `TASK_COMMAND_ERROR_DETAILS`, from `copy.ts`, from the pgTAP catalog arrays and from every function body. The `else` survives, raising the bare `22023 'Invalid task command action'` that step 2 already gives an unknown action. A post-deploy guard greps every shipped body for the retired token and fails the deployment if one still names it — which is why the migration's own prose must not mention it inside a function.
- **Reason:** This phase has twice rejected a guard that no reachable state can provoke — the two tautological reminder checks of `202607260058` — on the grounds that for a declared member of a closed error vocabulary it is the same defect as a missing raise. Applying that standard to a *guard* but not to a *code* would be inconsistent. The replacement refusal is provokable through step 2, so the terminator remains meaningful without adding an unreachable declaration.
- **Consequences:** `TASK_COMMAND_ERROR_DETAILS` goes 9 → 11 rather than 9 → 12. The retirement is enforced at deploy rather than by convention. A future action added to the enum without a taxonomy branch is refused as an invalid action rather than as an unavailable one, which is truthful: it has no policy, so it is not an action this contract knows.

## ADR-050 — A multi-step command continues by re-derivation from a pinned clock

- **Date:** 2026-07-28
- **Status:** Accepted; recorded in Slice 2E.7 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** Phase 2E's flow is several round trips — parse, maybe disambiguate, preview, maybe confirm, apply — and every step after the first needs the command the first step produced. PRD §11.1 forbids the obvious shortcut by name: "No state is stored in the client as the source of truth. A preview is recomputed server-side and re-fingerprinted on every render."
- **Problem:** Something has to survive the round trip, and the three candidates each break a different guarantee.
- **Alternatives considered:** *Re-parse the command text on every step* (rejected: a second billed call that may legitimately return a **different** command than the one previewed, so the user applies something they never saw — and 2E-COMMAND-013 makes a re-parse failure mid-flow an outcome with nowhere to go). *Carry the computed preview* (rejected by PRD §11.1 directly). *Persist the session server-side* (rejected: a new table, a new lifecycle, a new expiry vocabulary and a new cleanup job, for state whose entire purpose is to be reconstructible).
- **Decision:** The client round-trips a validated envelope carrying the model's **normalized proposal** and the instant the session was issued at. Every step re-runs `validateTaskCommand`, `loadTaskCandidates` and `rankTaskCandidates` against that same instant. The envelope also carries the explicit selection and a staleness witness `{taskId, updatedAt}` from the preview that was actually rendered; a writing path requires the witness and refuses without it.
- **Reason:** **Pinning `issuedAt` is the whole mechanism, not a detail.** `loadTaskCandidates` derives `p_observed_before` from the instant it is given (`candidates.ts:231`) and the RPC echoes it onto every row, from where `buildTaskCommandPreview` carries it into `preview.observedBefore` and `buildApplyPayload` hashes it. Minting a fresh instant per step would therefore change the fingerprint on every step of one operation key, and three things break at once: 2E-IDEMPOTENCY-004's replay returns `2E_IDEMPOTENCY_MISMATCH` instead of the original outcome, a double-submit is refused rather than replayed, and a destructive retry after a `2E_TRANSITION_INTEGRITY` can **never** succeed, because the surviving confirmation row is bound to the first attempt's digest. A first draft of this design justified *not* pinning it on the claim that `observedBefore` "is what the twelve-column staleness gate compares against"; that is false — the gate at `202607260058:1121-1136` compares twelve `locked_task` columns against values derived from `p_pre_state`, and `p_observed_before` is only format-validated. Staleness lives in `expected` and `p_pre_state`; the pinned instant carries determinism and request identity.
- **Consequences:** The envelope is untrusted input and is parsed by a schema like any other boundary, with a version literal so an envelope minted by an older deployment is refused rather than best-effort-read. Tampering buys nothing — the tampered command is re-validated, re-previewed and re-rendered, so the user still sees what they are about to apply, and every authorization decision is the database's against `auth.uid()`. What tampering must not be able to do is *skip* a check, which is why the staleness witness is **required** on writing paths: an envelope that reached one without a witness is an envelope no server render produced, and honouring it would make 2E-PREVIEW-006 structurally unreachable. `clarificationUsed` is likewise derived from the envelope carrying an answer rather than carried as a boolean, so the bounded-once guarantee of 2E-NOMATCH-008 is a property of the shape. A command whose session is abandoned costs nothing: no row was written.

## ADR-051 — The destructive confirmation is issued by the render, and the dialog is hand-rolled

- **Date:** 2026-07-28
- **Status:** Accepted; recorded in Slice 2E.7 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** ADR-047 established that the confirmation is a server-minted row bound to a fingerprint the RPC derives itself. Slice 2E.7 has to decide *when* that row is minted, and what the confirmation step looks like. 2E-A11Y-004 requires "an appropriate dialog role with an accessible name and description".
- **Problem:** (a) A first design issued the confirmation inside the Confirm action, immediately before consuming it. (b) A native `<dialog>` with `showModal()` is the obvious way to satisfy 2E-A11Y-004.
- **Alternatives considered:** *Issue at Confirm time* (rejected — see Reason). *Native `<dialog>` + `showModal()`* (rejected on executed evidence). *An inline confirm-and-apply control with no dialog* (rejected: 2E-A11Y-004 asks for a dialog role, and a destructive action that shares its visual weight with an ordinary Apply is exactly the accident 2E-DESTRUCTIVE-001 exists to prevent).
- **Decision:** (1) The confirmation is issued by the round that **renders** the preview, never by the one that consumes it. (2) The dialog is a hand-rolled `role="dialog" aria-modal="true"` with its own focus management. The same placement rule applies to the creation confirmation of 2E-NOMATCH-005.
- **Reason:** (a) Issuing and consuming in one action binds the token to whatever the envelope says **at Confirm time**, which is not necessarily the preview the user saw. The draft's own stated defence — "editing the patch after issuance fails `2E_CONFIRMATION_REQUIRED`" — was unreachable in its own flow, because there was no issuance to be *before*. That is a security defect rather than a style point: 2E-DESTRUCTIVE-003 says "a changed proposal invalidates prior confirmation", and there is no prior confirmation to invalidate if it is minted last. (b) **jsdom 29.1.1 — the version this repository runs — has no `showModal`, `show` or `close` on `HTMLDialogElement.prototype`; `showModal()` throws `TypeError`.** Verified by executing jsdom, not by reading the version number. Vitest with jsdom is the only accessibility gate CI runs, so a native dialog would leave 2E-A11Y-004 asserted by nobody and shipping on a manual read of the source.
- **Consequences:** Every render of a destructive preview mints a confirmation, so an abandoned flow leaves an unspent row — which ADR-047 already accepts, and which a single subsequent edit to the task makes unappliable. The three behaviours `showModal()` would have supplied (initial focus, a Tab cycle, Escape-restores-focus) are implemented and each has a test. That decision paid for itself immediately: the focus-trap test found that `input:not([disabled])` matches `type="hidden"` fields, so "the first focusable element" resolved to a hidden form field, `.focus()` on it was a silent no-op, and the dialog opened with focus still on the page behind it. The selector now excludes hidden inputs. Background inerting uses the focus cycle rather than the `inert` attribute, which jsdom does not reflect either.

## ADR-052 — `task_command` is its own analytics surface, and the remote smoke reads the vocabulary rather than restating it

- **Date:** 2026-07-28
- **Status:** Accepted; recorded in Slice 2E.7 on branch `codex/phase-2e-natural-language-task-updates`.
- **Context:** 2E-ANALYTICS-005 requires the command surface value in all three allowlists "in the same migration and commit as the first emitting code". 2E-ANALYTICS-006 requires `scripts/remote-product-events-smoke.mjs` to import the vocabulary from the contracts module "so a TypeScript addition cannot drift from the smoke". PRD §3.4 already records that the smoke's hard-coded list had fallen behind.

The `policyVersion` property is validated as a *shape* (`YYYY-MM-DD.N`) rather than against today's literal, because PRD §10.4 requires that version to be bumped whenever a weight or threshold changes, and a pinned literal would make every legitimate bump reject live events. Band, outcome and evidence literals **are** pinned exactly, because those vocabularies are closed and a CHECK literal is permanent.

## ADR-053 — `2E-COMMAND-012` is reclassified to Phase 2F rather than satisfied by a signature change in a closeout slice

- **Date:** 2026-07-28

- **Context:** 2E-COMMAND-012 requires that "prompt and strategy versions of a command proposal are recorded on the resulting operation, since `ai_usage_events` has no column for them". 2E-PROVENANCE-001 restates the substance. Slice 2E.7 left the choice to Slice 2E.8 in explicit terms: add the column, or record a reclassification in the PRD.

Against that, the cost is a drop-and-recreate of a production-critical shared function during convergence-and-closeout, whose entire purpose is to stop changing things and verify what exists. A closeout slice that ships its riskiest schema change last has misunderstood what closeout is for.
- **Consequences:** Attributing a bad command to the prompt that produced it requires joining `ai_usage_events.created_at` to the deploy history rather than reading a column — weaker than the requirement intends, which is why this is recorded as deferred rather than absorbed. The residual risk is stated in identical terms in the PRD, `PHASE_2E_FINAL_REPORT.md` §7.1, `PHASE_2E_TRACEABILITY_MATRIX.md` and `TODO.md`, so no reader of any one of them can conclude the requirement was met. ## ADR-055 - The semantic-retrieval evidence standard: two tiers, named exclusions, and a 90-day expiry

- **Date:** 2026-07-29
- **Status:** Accepted; recorded in Phase 2F Slice 2F.1 (PRD 2F-DECISION-002, 2F-MEASURE-002..006).
- **Context:** `PHASE_2E_PRD.md` SS22 defers semantic task retrieval to "should the measured baseline later justify" it, without defining "justify". The Phase 2F gate package (Gate 5 / F10) specified a measurable standard; the PRD encodes it; this ADR is its durable record.
- **Problem:** An undefined evidence gate is decided by taste. A threshold computable two ways is decided twice. A gate nothing fires is the same as no gate.
- **Alternatives considered:** *Build embeddings now* (rejected: zero real commands typed at decision time - the largest investment against the weakest evidence). *A single high threshold* (rejected: it would forbid the cheap experiment that answers the question sooner). *No expiry* (rejected: a permanently pending gate blocks nothing and decides nothing).
- **Decision:** Two tiers, measured over **qualifying commands** only (a model-parsed proposal for a real user; smoke-created users, disposable-fixture users and fixture-targeted commands excluded by construction - `product_events.user_id references auth.users(id) on delete cascade` plus fail-closed smoke cleanup plus the reader's own owner-scoping; `outcomeCategory = 'unsupported'` excluded from the qualifying denominator):
  1. **Spike tier - 50 qualifying commands / 10 distinct active days / a 14-day window** authorizes only a time-boxed (<=3 days) offline replay spike: replay recorded failed-match commands against an offline embedding index and measure whether outcomes would have changed. Never infrastructure - no pipeline, no job type, no backfill, no `source_type` widening, no index.
  2. **Planning tier - 150 qualifying commands / 20 distinct active days / a 30-day window / >=2 distinct real users**, with `no_match` rate >= 20% or no-match-to-creation rate >= 15%, may authorize *planning* a later semantic-retrieval phase. `no_match` means a qualifying command whose final outcome is `still_unmatched` or `creation_offered` (`src/features/task-commands/outcomes.ts:37-40`; no outcome member is literally named `no_match`). No-match-to-creation is computed from `task_command_applied.applyRoute = 'created'`. The distinct-user count is out of an owner-scoped reader's range and is verified by a privileged read at evaluation time. At one user, this tier authorizes nothing beyond the spike.
- **Reason:** The spike answers the better question ("would embeddings have helped *these* commands?") at the cost of a script; the planning tier guards the expensive commitment behind statistics a 14-scenario corpus cannot supply.
- **Consequences:** **Permanently non-authorizing, alone or together:** unsupported-command refusal volume, adoption/command volume, one-step rate, ambiguity rate, latency. **Expiry:** at 90 days without a met threshold, an ADR removes semantic retrieval from the active roadmap until a new demand signal appears. Because nothing in this repository fires on a date and Phase 2F ends before day 90, this ADR creates the dated expiry entry in `docs/TODO.md` - its date computed from the 2F.5 reader's go-live, placeholder until then - and 2F-OPERATIONS-006 verifies that entry exists at closeout.

## ADR-058 - The command-funnel reader excludes `is_synthetic` rows as a fourth mechanism, and that mechanism is hygiene rather than a trust boundary

- **Date:** 2026-07-29
- **Status:** Accepted; recorded in Phase 2F Slice 2F.5 before implementation, because it amends a merged requirement (PRD 2F-MEASURE-002). Supplements ADR-055; does not change either evidence tier.
- **Context:** 2F-MEASURE-002 states that "qualifying command" exclusion "works by construction through **three** real mechanisms, not email-pattern heuristics": the `product_events.user_id` cascade to `auth.users`, the smoke cleanup, and the reader's own owner-scoping. The requirement was written from the migration's ownership model. It did not account for a column the same migration already carries.

- **Date:** 2026-07-29

It seeds disposable fixture tasks with the **service-role** client - the pattern `scripts/remote-phase-2e-smoke.mjs:154-158` already uses, untouched by Slice 2F.4's revocation, which revoked from `authenticated` only - then resolves each corpus command through the real `loadTaskCandidates` against the deployed `list_task_command_candidates` and scores the returned rows with the real `rankTaskCandidates`. Seeding is fixture setup, not the contract under measurement. Fixtures are deleted in a `finally` with the deletion asserted before the process may exit 0.
- **Reason:** The measurement that discharges the caveat has to use the production loader and the production scorer, or it measures a copy. An opt-in lane is the smallest mechanism that reaches them from a credentialed run without putting credentials in CI or a transpiler in the dependency tree.
- **Consequences:** A second Vitest configuration exists; a Vitest case asserts that the default configuration excludes the remote pattern, so a future config edit that would drag credentialed tests into CI fails in CI. Both baselines are published side by side with their scope labels, and cross-scope comparison stays prohibited wherever either number is quoted.

The distinction in (f) is load-bearing rather than pedantic: a guard keyed on appearance would red the build on the two owner-authorized sentences that carry the ADR-053/ADR-057 and 2E-MATCH-018 traceability chains, and the predictable repair would be to delete truthful cross-phase references.

The four earlier generators are **not** retrofitted: their phases are closed, their matrices are historical records, and rewriting them would change accepted artifacts to satisfy a standard adopted after them. **Date:** 2026-07-31. **Context:** UX-12 (Slice G5), owner decision DEC-7, and 2F-REMINDER-004.

The Phase 2F closeout says so in an executable assertion — `src/lib/closeout/phase-2f-census.test.ts:152`, *"never fire; no reactivation path exists"* — and measured the bucket at zero rows against the deployed project.

**Consequences.** Snooze and reschedule perform the same physical write. They remain separate product actions, distinguished by command name, accepted input shape (bounded relative preset from `now()` versus an explicit absolute instant), validation, audit `action_type` and UI affordance — which is the shape DEC-7 requires. ## ADR-067 — A phase-start guard measures governing artifacts, not filenames

- **Date:** 2026-07-31
- **Status:** Accepted; owner-authorized as a correction to the guard's proxy, explicitly **not** a relaxation of the invariant.
- **Context:** `phase-2f-documentation.test.ts`'s A13 case asserted that no file in `docs/` or `docs/reports/` may be named to match `/PHASE_2G/i`. The owner then commissioned a definition study — a document whose purpose is to decide whether a phase should exist, which declares no requirement and plans no work — and the guard reddened the `application` job.
- **Problem:** The invariant A13 protects is *"the next phase must not be started before it is authorized."* A filename is a weak proxy for that. It is simultaneously **too strict** (it forbids recording an evaluation) and **too weak** (a declared requirement family in a file called `ROADMAP_NOTES.md` would have passed). The guard's own comment already drew the correct distinction — "a mention as future work is a record; a declared requirement would be a start" — and its companion assertion enforced it; only the filename half was wrong.
- **Alternatives considered:** *Rename the study* (rejected: it hides a real document behind a name chosen to dodge a test, which this repository's review culture would flag later, and it leaves the too-weak half unfixed). *Delete or withhold the study* (rejected: the owner commissioned it and it is the record of a decision). *Delete A13* (rejected: it is the only mechanical thing preventing a silent phase start).
- **Decision:** A phase is started by an **implementation-governing artifact**, not by a filename. Four signals, any one of which fails the build: a governing artifact **by role** (`/^PHASE_2G_.*(PRD|IMPLEMENTATION_PLAN|REQUIREMENTS)/i`, whatever else it is called); a **declared** requirement family in this repository's declaration shape (`- **2G-XXXX-000:**`); an **accepted** ADR whose heading names the phase; and a migration or source file marked as that phase's implementation. Permitted explicitly: definition studies, future-work mentions, candidate labels such as `2G-1`…`2G-4`, and append-only amendments stating the phase remains unauthorized.
- **Reason:** It measures the property rather than a symptom, and it is strictly stronger in the direction that matters — the declaration scan is now content-based and file-name-independent, so an innocuous filename can no longer hide a phase start.
- **Consequences:** Eight executed mutation cases prove each signal fires and that the permitted set passes; a guard whose failure modes are asserted is the only kind worth keeping, and A13's previous form had none. The declaration shape is deliberately identical to the one `phase-2f-traceability.test.ts`'s attribution guard uses, so the intentional `2G-READINESS-001` negative-control fixture stays a non-match and does not become a false positive. No other Phase 2F closeout assertion was touched: the same file's C1-re-raise case, the parity case, the funnel cases and the cross-scope-comparison case are unchanged, and all 142 tests across the five closeout suites pass.

- **Alternatives considered:** *Operational Readiness first* (rejected: its items are each keyed to a trigger — public signup, first pilot, deployment — and none had occurred; a rate limiter cannot be validated against a surface nobody can reach). *Conversational Creation first* (rejected by the owner in favour of building it against the final credential contract rather than a project-key design that BYOK would immediately replace). *Deferring the entity work* (rejected on evidence: the Person surface is not truthful without it).

- **Reason:** Entity Graph Completion is deterministic, independent, and needs zero migrations and zero privileged boundaries. BYOK establishes the credential contract before any new AI surface consumes it. Signup hardening is what actually makes signup safe — BYOK addresses **one** of its fourteen controls.
- **Consequences:** C1's spend-cap recommendation changes meaning rather than being deferred a third time: under per-user credentials the owner is not the payer, so the protective control becomes an infrastructure quota owned by signup hardening, not a USD ceiling owned by a product phase. Three prerequisites for the first non-owner account do not exist and are named rather than assumed: **account deletion**, **admin suspension**, and **terms and privacy policy**. Hosted signup was closed on 2026-07-31 and verified (G-0.5); **BYOK is explicitly not a mitigation for an open signup path**, and no initiative may be cited as one.

## ADR-069 — BYOK's pre-code gates bind to what depends on them, not to the whole initiative

- **Date:** 2026-08-01
- **Status:** Accepted; owner decision, recorded as an append-only amendment to `BYOK_IMPLEMENTATION_PLAN.md` §0 (Amendment A-1). Explicitly **not** an implementer relaxing a gate.
- **Context:** The plan's §0 declares five pre-code gates and one absolute rule: *"No slice may start until every artifact below is in the repository."* G-0.1, G-0.2 and the G-0.3 procedure were executed and committed on `codex/byok-precode`. Two artifacts remained: G-0.3's provisioned keys for four environments, and G-0.4's dedicated low-limit OpenAI validation key.
- **Problem:** Read absolutely, the rule stops everything. G-0.4's artifact is consumed by exactly one lane — BYOK.3's live credential validation — yet it would block BYOK.1's tables and BYOK.2's resolvers, neither of which reaches a provider. G-0.3's *preview and production* values are likewise consumed only by a deployment that BYOK.1 and BYOK.2 do not perform. The absolute reading therefore blocks work on the availability of an artifact that work cannot use, while the implementer's own inference to the contrary was correctly refused as unilateral: this repository does not renegotiate a governing document's invariant inside a branch.
- **Alternatives considered:** *Hold the absolute reading* (rejected by the owner: it stalls two slices of schema, crypto and RPC work on a paid external vendor commitment they never touch, and it does so to protect nothing). *Let the implementer proceed on its own reading* (rejected: the plan is a governing document, and softening it is the owner's act, not the implementer's — the implementer stopped, which was correct). *Delete or rewrite §0* (rejected: it would erase the record of what the plan originally required, and the stricter reading was not wrong, only overbroad). *Generate preview and production keys now* (rejected: it needs administrative controls the implementer cannot reach without extracting or exposing credentials, and nothing yet deploys).
- **Decision:** Each gate binds to what actually depends on its artifact. G-0.1, G-0.2 and G-0.5 gate all BYOK implementation. G-0.3's **written procedure** gates BYOK.1. G-0.3's **local/test provisioning** gates execution of crypto integration tests needing persistent environment secrets. G-0.3's **preview/production provisioning** gates deployment to those environments. **G-0.4 gates BYOK.3's live validation lane and BYOK.3's closeout** — BYOK.3 may not be accepted or merged without it, and the lane may never ship marked "passed" while unexercised.
- **Reason:** A gate exists to stop work that would be dishonest or unsafe without its artifact. Testing an AES-256-GCM envelope needs a key, not a *provisioned production* key; a resolver that returns ciphertext needs no provider at all. Binding each gate to its dependents keeps every gate's protective force exactly where the artifact is consumed, and it makes the one gate that genuinely blocks — G-0.4 — legible instead of hidden inside a blanket rule that had already been over-applied four times.
- **Consequences:** BYOK.1 and BYOK.2 are authorized and proceed on local and test keys the implementer generates (four values, pairwise distinct, 32 bytes, base64, in git-ignored files, never displayed or recorded beyond presence/validity/length/distinctness). Preview and production provisioning becomes an explicit **stop with exact owner-facing commands** at the first deployment that needs it, with both the Next.js and Edge Function runtimes required to receive the same environment-specific pair. G-0.4's key acquires named constraints that BYOK.3 must honour in code — dedicated project and key, restricted permissions, USD 2 monthly budget **alert** documented as a soft alert and not a hard cap, lowest practical rate limits, opt-in lane only, `maxRetries: 0`, short timeout, a hard application-side daily attempt ceiling, and revocation after acceptance. The implementer stops before BYOK.3 while G-0.4 is unprovisioned rather than shipping a validation lane it did not exercise.

## ADR-070 — The per-IP throttle gets a column and a third secret, and G-0.4 closes with one thing still unreachable

- **Date:** 2026-08-01
- **Status:** Accepted; owner decision, recorded as append-only Amendment P-1 in `BYOK_PRD.md` and Amendment A-2 in `BYOK_IMPLEMENTATION_PLAN.md`.
- **Context:** BYOK.1 shipped `credential_validation_attempts` with exactly the three columns `BYOK-SCHEMA-007` declares, and **raised a conflict rather than resolving it**: `BYOK-VALIDATE-004` and plan task 3.8 require throttling per user *and per IP* over that table, and BYOK.3's migration budget was zero. Separately, G-0.4 — the dedicated low-limit OpenAI validation key — was the last outstanding pre-code gate, and `ADR-069` had made it gate BYOK.3's acceptance and merge rather than only its lane.
- **Problem:** Three governing statements could not all hold: a fixed three-column shape, a per-IP throttle stored in that shape, and a zero-migration slice. Any implementer resolution would have been an implementer expanding a governing document's schema inside a branch — the move `ADR-069` exists because the *owner* is entitled to make. Meanwhile a per-IP throttle stores something the product has never stored before: a signal about where a user connects from.
- **Alternatives considered:** *Per-user ceiling only* (rejected: it leaves the T-16 control — the product as an oracle for testing stolen OpenAI keys — mitigated only for a single account, and the whole point of the control is the attacker who is not limited to one). *Throttle per IP outside the table*, at an edge or in a separate store (rejected: it adds an infrastructure dependency this repository does not have, and puts the abuse evidence somewhere the residue verifier and the retention rule cannot see it). *Store the raw IP* (rejected: it is the most identifying value the product would hold, for a purpose that needs only equality). *Derive the HMAC key from `BYOK_MASTER_KEY` or the fingerprint pepper* (rejected for the reason `BYOK-FINGERPRINT-001` already gives: one compromise must not yield two capabilities — and a rate-limit pepper is the most widely-handled of the three, so coupling it to decryption is the worst pairing available).
- **Decision:** `credential_validation_attempts` gains **one** column, `ip_hash`, in a BYOK.3 migration; the initiative budget rises from **four to five**. `ip_hash` is `HMAC-SHA256` over a **canonicalized** IP under a **third independent secret**, `BYOK_RATE_LIMIT_PEPPER` — never the master key, never the fingerprint pepper, subject to `BYOK-MASTER-001…005` independently. The raw IP is never stored, logged or returned. `ip_hash` is used only for throttling and abuse control. Retention is bounded and enforced. Indexing supports concurrency-safe daily ceilings per user and per IP and nothing more. Requirements: `BYOK-SCHEMA-010…015`. **G-0.4 is satisfied** — a dedicated project and key exist as `BYOK_VALIDATION_OPENAI_API_KEY` with a USD 2 budget, restricted models, lowest practical limits and acceptance-lane-only use — so **BYOK.3 is authorized to begin**.
- **Reason:** Equality is the only property a throttle needs from an address, and a keyed hash gives equality without giving the address. Canonicalization is part of the contract rather than an implementation detail, because an un-canonicalized hash silently mints a fresh bucket per spelling and defeats the ceiling it exists to enforce. The third secret costs one more value to provision and removes the case where a rate-limit leak assists decryption. Raising the budget by one and saying so is cheaper than a slice quietly spending a migration it was not allocated — which is exactly what BYOK.1 refused to do.
- **Consequences:** Six secrets now exist per environment rather than four; local and test values for the new pepper are generated with the same evidence rule as the others (presence, base64 validity, 32 bytes, pairwise distinctness, and nothing else recorded), and preview/production follow Amendment A-1.2's point-of-use ordering. `credential_validation_attempts` acquires the initiative's first retention obligation, which BYOK.6's residue verifier must then account for. **One gap is recorded rather than discovered later:** measured at `0b62a5b`, no repository Actions secret named `BYOK_VALIDATION_OPENAI_API_KEY` exists and the name is absent from `.env.local` and `.env.test.local`, while `ADR-059` runs the opt-in lane locally and deliberately keeps credentials out of CI. The lane can therefore be **written but not executed** until the value is readable by a local run, and `ADR-069` forbids BYOK.3 closing with it unexercised — so this gates BYOK.3's **closeout**, not its start.

## ADR-071 — BYOK.4's second migration carries a second function, and "consumes no retry" is stated narrowly

- **Date:** 2026-08-01
- **Status:** Accepted; implementer decision inside an approved budget, recorded because the *content* of an approved migration changed even though the *count* did not.
- **Context:** `BYOK_IMPLEMENTATION_PLAN.md` allocates BYOK.4 exactly two migrations and names them: the `entries.status` literal, and the `claim_next_entry_interpretation_job` `create or replace`. `BYOK-JOBS-003` separately requires that a job reaching execution with no active credential move to a **declared terminal state** and **not consume a retry**.
- **Problem:** The existing `fail_job` cannot express that. Its terminality is `attempts >= max_attempts` and nothing else, so a credential failure on attempt 1 of 5 is rescheduled for four more attempts that will fail identically — spending backoff, lease churn and the retry budget a *fixable* failure will need later. Two migrations were approved; neither, as described, contains a way to satisfy the requirement.
- **Alternatives considered:** *Add a `p_terminal` argument to `fail_job`* (rejected: PostgreSQL cannot extend an argument list with `create or replace` — `ADR-057` records this codebase learning that the expensive way — so it would mean `drop function` plus recreate, changing a signature four callers and a pgTAP suite depend on, for a boolean). *Teach `fail_job` to read `p_error` and infer terminality from the code* (rejected: it overloads an error-message parameter with control-flow meaning, which is the implicit coupling this repository files rather than ships, and it makes every future caller's retry policy a function of a string they may not know is load-bearing). *Stop and ask for a third migration* (rejected: the file budget is not exceeded, and stopping on a change that stays inside the approved count would be ceremony rather than governance — but it is recorded here rather than folded silently into "the claim replacement").
- **Decision:** `202608010069` contains both `claim_next_entry_interpretation_job` and a new, separately named `fail_job_terminal(uuid, text, text)` — `service_role` only, `SECURITY DEFINER`, empty `search_path`, same lease check as `fail_job`, sets `exhausted` immediately and schedules nothing. Its `p_error` is **restricted by the database** to the closed terminal vocabulary, so a future handler that reverts to `error.message` fails loudly rather than writing a provider message into a column the Jobs page renders verbatim. **Two migration files; the head moves by exactly two.**
- **Reason:** A second named function costs one more object and touches no existing signature. The retry policy becomes visible at the call site — `fail_job` versus `fail_job_terminal` — rather than hidden in a parameter's contents, and the closed vocabulary gains a second enforcement point in the layer that actually stores the value.
- **Consequences:** `jobs.error` now has two writers with different guarantees, and the difference is stated rather than glossed: `fail_job_terminal` accepts only declared codes; `fail_job` still accepts free text at the database level, and is safe today only because `_shared/job-failure.ts` is its sole caller and passes a code. A third writer exists and predates BYOK — `reap_expired_jobs` writes the fixed literal `'Worker lease expired'`, which carries no secret and no provider text but is not a member of the vocabulary either. Both are recorded as residual risks in `docs/reports/BYOK_SLICE_04_ACCEPTANCE.md` rather than described as closed. **Separately, "does not consume a retry" is narrowed to what it can mean:** `jobs.attempts` is incremented by the *claim*, so by the time any handler runs the attempt is already spent and no failure path can return it. What `fail_job_terminal` guarantees is that **no further attempt is scheduled**. The migration header says so in those words, so the requirement is not read as a promise the implementation cannot keep.

## ADR-072 — The project key's name leaves the environment contract, and the allowlist widens by two to hold the check that replaces it

- **Date:** 2026-08-02
- **Status:** Accepted; implementer decision, taken against an exact census and recorded because it both **removes** a documented contract and **widens** a security allowlist in the same change.
- **Context:** `ADR-068`'s cutover completed on the platform side on 2026-08-02: the three BYOK secrets exist in the Supabase Edge Function store, migrations `202608010065`…`202608010069` are applied, `process-jobs` is deployed, and `OPENAI_API_KEY` is unset from the deployed function secrets. `CHANGELOG.md` had recorded one question as deliberately open — after the cutover `OPENAI_API_KEY` has no reader anywhere, and this repository removes consumer-less contracts rather than keeping them — and handed it to BYOK's convergence audit. Separately, the first deployment produced a defect no test could have caught: the Node runtime that saved the owner's credential held a **different** `BYOK_MASTER_KEY` from the deployed worker, so the credential is sealed under a key nothing available can open.
- **Problem:** Two things had to happen together and neither is free. **First**, the census: a comment-stripped scan over `src`, `supabase/functions`, `scripts`, `e2e` and `.github` finds `OPENAI_API_KEY` in exactly three files, and none of them is a runtime consumer — `.env.example` carries the name with an empty value, and the other two are the guards that assert the absence. So the name survives only in the place a person looks at 3am. **Second**, the mismatch: nothing in the product may report *which* of key, tag or AAD failed (`BYOK-CRYPTO-005`), so a runtime-key mismatch is structurally invisible from inside the product and must be checked from outside it. A check that reads the deployed secret listing has to **name** `OPENAI_API_KEY` to assert it is gone — and `BYOK-GUARD-006` pins the allowlist and requires an ADR to widen it.
- **Alternatives considered:** *Keep `OPENAI_API_KEY` in `.env.example`* (rejected: the census proves it is a contract nothing honours, and `.env.example`'s own comment already described the 3am failure mode it was creating). *Write the verifier without naming the key* — assembling the string at runtime, or checking only master-key parity (rejected: the first is evasion of a guard rather than compliance with it, and this repository does not ship code shaped to slip past its own controls; the second drops the one deployment-level check nothing else automates). *Put the verifier's logic in `src/` so it inherits the existing test classification* (rejected: it would then be TypeScript inside the app's own tree, which is a worse reachability posture than a `scripts/*.mjs` that `next build` never compiles). *Leave the mismatch to documentation* (rejected: the defect had already happened once, silently, to the person who wrote the documentation).
- **Decision:** `OPENAI_API_KEY` is **removed** from `.env.example` and from `README.md`, and `project-key-guard.test.ts` gains an assertion that neither file offers the name again. `scripts/byok-verify-runtime-parity.mjs` and `src/lib/byok/runtime-parity.test.ts` are **added** to `PROJECT_KEY_ALLOWLIST` under a new classification, `operator-verification-script`, whose reachability proof is stronger than the test classification's: not TypeScript, under `scripts/`, and imported by no module outside a test. The allowlist is pinned at **four**, still compared in both directions, and a further assertion pins the set of *scripts* that may name the key to exactly the verifier and confirms it never reads the name from the environment. `.env.example` also drops `OPENAI_CHAT_MODEL` and `OPENAI_REASONING_MODEL`, which the same census found unread, and gains `OPENAI_FILE_MODEL`, which the deployed attachment handler does read.
- **Reason:** The allowlist's purpose is that every surviving reference is a place the key legitimately *cannot* be used, and every entry is now a place that names it in order to assert its absence — a stricter composition than before, not a looser one, even though the count rose. Removing the name from the two files a person actually copies removes the only reachable invitation. And the verifier earns its entry: it is the sole automated check standing between a silent key mismatch and a user's credential being sealed under a key no runtime holds, a failure whose only remedy is asking every affected user to type their key again.
- **Consequences:** `npm run byok:verify-runtime` exists and **must be run before configuring any credential in any environment**; it refuses to return a verdict at all unless it can first reproduce a known digest, so it can never report "different values" when it means "different hash function". `.env.example` and `README.md` no longer tell a new developer to set a project OpenAI key, because there is none to set. The allowlist is four entries and its classification map has two classes; a fifth entry needs its own ADR, as before. **The removal is deliberately *not* evidence that the cutover succeeded** — it is evidence that no code path wants the name. The cutover itself failed on the master-key mismatch and is recorded as failed in `docs/reports/BYOK_DEPLOYED_ACCEPTANCE.md`.

## ADR-073 — Signup Hardening is planned as one initiative with tiered pre-code gates, and its requirements never use a phase prefix

- **Date:** 2026-08-02
- **Status:** **Accepted 2026-08-04** — owner approval recorded in `ADR-077`. Proposed 2026-08-02; recorded when the Signup Hardening planning artifacts were opened. Governs `docs/SIGNUP_HARDENING_PRD.md` and `docs/SIGNUP_HARDENING_IMPLEMENTATION_PLAN.md`. **No implementation was authorized by this ADR while Proposed** — the plan's per-slice pre-code gates do that, and they began operating at SH.0 only after `ADR-077`.
- **Context:** `ADR-068` ordered Signup Hardening after BYOK's close and named its three absent prerequisites — account deletion, admin suspension, terms and privacy policy — while stating that BYOK addresses only one of signup's fourteen controls. BYOK closed on 2026-08-02 (`b007ffa`), authorizing this initiative. A four-agent repository census (`docs/reports/SIGNUP_HARDENING_FINDINGS.md`) measured the surface before scope was declared, per the prompt's instruction to inspect repository truth rather than assume the preliminary scope.
- **Problem:** Two governance hazards had to be settled before any requirement was written. **First**, the requirement ID namespace: `ADR-067`'s phase-start guard fails the build on a declared requirement family in the shape `- **2G-XXXX-000:**`, so a Signup Hardening requirement using a `2G-` (or any phase) prefix would trip a guard that exists to prevent a silent phase start. **Second**, the gate structure: `ADR-069` recorded that BYOK's earlier mistake was reading one absolute pre-code rule so broadly that an unrelated external dependency blocked every slice; Signup Hardening has several external dependencies (a CAPTCHA vendor, hosted Auth config, SMTP, a hosting platform) and must not repeat that.
- **Alternatives considered:** *Number requirements under a phase prefix* (rejected: trips `ADR-067`, and Signup Hardening is an initiative like BYOK/EGC, not a numbered phase — BYOK used `BYOK-*`, EGC used `EGC-*`). *One absolute pre-code gate* (rejected by the very lesson `ADR-069` records — it would let the CAPTCHA-vendor decision block the deletion work). *Fold operator tooling in because the admin boundary is adjacent* (rejected: the prompt explicitly forbids silently absorbing an operator dashboard, and `ADR-068`'s reasoning against "nearby, so fold it in" applies).

Its pre-code gates are split into three tiers (`SIGNUP_HARDENING_IMPLEMENTATION_PLAN.md` §0): gates that block **all** implementation (census complete, the deletion-cascade drill green in CI, the privileged-boundary inventory, the owner-signed quota/retention value sheet), gates that block **deployment** of a slice (hosted-config readback, backup verified, disposable-account strategy, hosting/SMTP decision recorded), and gates that block **public signup** only (the rollout gate, which is the initiative's output, not a blocker on any slice). The administrative boundary is built here; operator *surfaces* (dashboard, alerting, credential/account-health) are explicitly out of scope and recommended to a Phase 2H-aligned Operations initiative.
- **Reason:** Binding each gate to what depends on it is exactly `ADR-069`'s ruling, applied preventively rather than after a stall. The `SH-*` namespace keeps the phase-start guard meaningful. Measuring before scoping caught that the row-level cascade is already complete (so deletion's hard part is storage and the untested composite-FK path, not the tables) and that no lifecycle state exists at all (so suspension and deletion share one foundation) — neither of which the preliminary scope list stated.
- **Consequences:** The single load-bearing all-implementation gate is the cascade drill (`SH-DELETE-001`): it is fail-closed against a user-owned table added after the census, and it must be green before deletion is designed because the census found the cascade has never been executed against a row-complete account (43 composite `NO ACTION` FKs sit in the path, untested). Eight migrations are budgeted across seven slices; deletion, suspension and rollout never share a PR. The `SH-*` families and their owners are fixed in the PRD; a new family is an amendment, not an edit.

## ADR-074 — The account-deletion executor is a self-only Edge Function, and deletion is a resumable state machine that stops rather than forces

- **Date:** 2026-08-02
- **Status:** **Accepted 2026-08-04** — owner approval recorded in `ADR-077`. Proposed 2026-08-02. Governs Signup Hardening slice SH.2.
- **Context:** No deletion path exists in product code, and two guards actively assert `deleteUser`'s absence from `src/` (`phase-2f-cleanup.test.ts:274`, `egc-operations.test.ts:248`). Deletion needs a capability no `authenticated` role holds; the repository forbids a `service_role` client in product code; row-level cascade from `auth.users` is complete but storage objects do not cascade (six live orphans prove it), and the cascade is untested against a row-complete account.
- **Problem:** Where does the executor live, and how does it avoid the two failure modes that make deletion dangerous — deleting the wrong account's data, and leaving a half-deleted zombie? A Server Action cannot hold the capability without importing a service-role client into `src/`. A single `auth.admin.deleteUser` call assumes the cascade is complete and storage is empty — the census proves the second false and leaves the first untested.
- **Alternatives considered:** *A Server Action with a service-role client* (rejected: puts an admin credential in product code, defeating the guards and the trust model). *One `deleteUser` call* (rejected: leaves storage orphans, and forces rather than stops on unknown residue). *A generic admin deletion endpoint taking a target user id* (rejected: T-01 — the exact over-broad-endpoint hazard; the executor must be authorized only for the requesting user's own account). *Delete storage by name heuristic* (rejected: the `codex.cost` misclassification, STATE.md:232 — deletion must be by structural ownership, prefix = uid).
- **Decision:** The executor is an Edge Function outside `src/`, authenticated as the requesting user (Bearer validated server-side), authorized only for that user's own account, accepting no target parameter. It is a resumable state machine: verify `deleting` status → enumerate and delete the `user-files/<uid>/` prefix → verify zero objects remain → delete the `auth.users` row → write a de-identified `account_deletion_log` record. It **stops rather than forces** on any unknown residue (a `user_id` table not covered by the cascade census, or an unclassifiable object), leaving the account in `deleting` with writes already blocked, and records the reason. Storage deletion is exact-prefix-match plus a cross-owner reference check, with a colliding-name negative control.
- **Reason:** Self-only authorization removes the way T-01 could happen. A resumable machine turns a crash into a re-run rather than a zombie (T-08). Stop-on-unknown is the deletion analogue of the fail-closed decryption BYOK relies on: when the system meets something it cannot classify, the safe act is to halt with the account still non-functional, not to force a destructive step. Deleting by prefix-equals-uid, verified against `auth.users` and `attachments`, is the only classification that the `codex.cost` incident proves a name heuristic cannot match.
- **Consequences:** The deletion log is de-identified by construction — opaque event id, hashed session under the rate-limit pepper, per-table and per-object counts, no email/name/user_id — so retention of the log does not contradict the privacy claim that the account is gone (T-31), and the Privacy Policy states exactly the log's enumerated fields (`SH-LEGAL-014`). The six 2026-07-16 orphans are resolved by the same scanner: manifested first, then deleted as a separate owner-authorized irreversible step. A new guard pins the executor as the only deletion-capability site; the two existing `deleteUser`-absence guards stay green because the executor is not in `src/`.

## ADR-075 — The administrative boundary is an operator CLI over service_role SQL, with no product admin UI and no service-role HTTP endpoint

- **Date:** 2026-08-02
- **Status:** **Accepted 2026-08-04** — owner approval recorded in `ADR-077`. Proposed 2026-08-02. Governs Signup Hardening slice SH.3.
- **Context:** There is exactly one operator, no hosting platform, no admin role concept in the schema, and an established operator-script pattern (`byok-rotate-master-key.mjs`, `byok-verify-runtime-parity.mjs`). Suspension and reactivation need a trusted boundary that normal users cannot reach.
- **Problem:** How is a privileged, audited administrative capability exposed without creating a `service_role` route that a normal user might reach (T-10), and without building a product admin UI that presupposes a role system the schema does not have?
- **Alternatives considered:** *A product admin UI behind a role check* (rejected: needs an admin role concept that does not exist, and puts a high-value capability behind app-layer authorization rather than the database boundary the repository trusts). *A `service_role` HTTP endpoint* (rejected: T-10 — the over-broad service-role endpoint the threat model calls out; an endpoint is reachable, a grant is not). *Direct SQL by the operator without a wrapper* (rejected: a raw `update account_lifecycle` would bypass the audit write and the transition-legality check).
- **Decision:** Administrative transitions are `service_role`-only `SECURITY DEFINER` SQL functions (`suspend_account`, `reactivate_account`, `begin_account_deletion_admin`) with empty `search_path`, a closed reason vocabulary, and an unconditional `audit_logs` write — callable by no client role. The operator surface is a `scripts/` CLI in the BYOK-script family: named account, explicit verb, `--reason` from the closed set, a dry-run default and explicit `--apply`, before/after status readback, never printing user content. The provider-side sign-in ban is a recorded runbook step with the admin API key, outside product code.
- **Reason:** A grant, not a route, is the boundary — and `service_role` SQL functions callable by no client role cannot be reached by a normal user by construction, which an HTTP endpoint's authorization must instead be trusted to enforce on every request. Making the audit write unconditional in the function body means admin-action-without-audit (T-12) is structurally impossible, not procedurally forbidden. The CLI reuses a pattern the repository already operates and tests.
- **Consequences:** Admin action without audit cannot happen; suspension takes effect within one proxy round-trip because the app-shell lifecycle read is per-request, with the ≤1 h JWT residual closed by the recorded provider-side ban rather than hidden. No admin role is added to the schema; the "one operator" reality is matched by a CLI, and a future multi-operator need is a later decision, not prejudged. A both-directions allowlist test pins the admin scripts as the only `service_role` lifecycle callers.

## ADR-076 — CAPTCHA is enforced by the provider, not the UI, and the vendor is chosen before integration

- **Date:** 2026-08-02
- **Status:** **Accepted 2026-08-04** — owner approval recorded in `ADR-077`. Proposed 2026-08-02. Governs Signup Hardening slice SH.5 (vendor decision gates only that slice, per `ADR-073`'s tiering).
- **Context:** No CAPTCHA exists anywhere (0 matches across `src/`, `e2e/`, `scripts/`); GoTrue's `security.captcha` block is commented out in `config.toml`. GoTrue natively supports hCaptcha and Cloudflare Turnstile. Signup, recovery and resend are the abuse surfaces.
- **Problem:** A CAPTCHA enforced only in the browser is bypassed by a raw API call (T-18), which is the most common way CAPTCHA is misapplied. And picking a vendor is an external dependency that, read as an absolute pre-code gate, would block unrelated deletion and suspension work — the `ADR-069` hazard.
- **Alternatives considered:** *UI-only widget validation* (rejected: T-18 — bypassable, proves nothing). *hCaptcha* (viable; heavier privacy footprint and a more intrusive challenge UX). *No CAPTCHA, throttles only* (rejected: the rollout gate marks CAPTCHA `required` before public signup, and throttles alone do not stop distributed low-rate signup floods). *Making the vendor decision an all-implementation gate* (rejected per `ADR-073`/`ADR-069`: it gates only SH.5).
- **Decision:** CAPTCHA is enforced by GoTrue (`security.captcha`), so a signup/recovery/resend call with a missing or invalid token fails at the provider regardless of the client — verified behaviorally against the deployed project, not by config read alone. The recommended vendor is Cloudflare Turnstile (GoTrue-native, privacy-friendly, low-friction), confirmed by accepted ADR before any integration code. The forms carry the widget and pass `captchaToken` through the existing Server Actions; local dev and CI run with CAPTCHA disabled by a documented config divergence, so a green CI never claims the hosted control.
- **Reason:** Provider enforcement makes UI-only bypass structurally impossible — the property the threat model requires. Deciding the vendor by ADR before integration keeps the choice reviewable and stops a half-integrated switch later. Confining the decision's gate to SH.5 is the tiering `ADR-069` established.
- **Consequences:** The widget's script origin is the only new external origin the auth pages load, and it is asserted absent from every authenticated product route (a CSP and privacy consideration). The deployed missing-token/invalid-token probe is the acceptance evidence; CI green is never cited as proving the hosted control. A vendor change later is a new ADR, not a silent swap.

## ADR-078 — SH.3's migration grows the reason vocabulary and replaces the heartbeat a second time, and a deferred job is not a failed one

- **Date:** 2026-08-04
- **Status:** Accepted — recorded under the `ADR-071` precedent, which established that **migration *content* gets an ADR even when the migration *count* does not**. SH.3 spends exactly the one migration the plan §1 allocates (`202608040073`); this records the two pieces of its content that stretch the plan's one-line description, and one design decision inside it that is not obvious.
- **Context:** The plan describes SH.3's migration as "admin transition functions (`suspend_account`, `reactivate_account`, `begin_account_deletion_admin`) + suspension worker/heartbeat predicate finalization". Three things inside that description turned out to need a decision rather than an implementation.
- **Decision 1 — the reason vocabulary grows by two.** `202608040070`'s CHECK carried one suspension reason, `operator_suspension`, and its own comment reserved vocabulary growth for "the owning slice". SH-COPY-002 requires the suspended surface to show *"the closed reason's public label"* — and a vocabulary of one has no label worth showing. `operator_suspension_abuse` and `operator_suspension_security` join it; `operator_suspension` stays as the generic "under review". Each has a public label in `src/features/shell/lifecycle-copy.ts` in both locales, and a unit test compares the label set to the migration's own text in **both directions**, so a code the database accepts can never reach the surface without a label and a label can never exist for a code the database refuses. **Alternatives:** *keep one reason* (rejected: makes `--reason` degenerate and SH-COPY-002 vacuous); *free-text reason with a length bound* (rejected outright: SH-SUSPEND-007 requires the database to refuse free text, and a free-text reason on a suspended surface is an operator note rendered to the person it is about).
- **Decision 2 — `run_user_heartbeat` is replaced a second time, and the no-burst rule is a predicate rather than a state change.** SH-SUSPEND-005 requires that reminders which came due during a suspension do not fire as a burst on reactivation. The obvious implementations both change the user's data: marking them `cancelled` destroys a scheduled intent the user still holds, and adding a `missed` status changes a CHECK, the generated types and the reminders UI for one edge case. **Decided instead:** the heartbeat reads the lifecycle row it already reads and, *only when the account's current reason code is `operator_reactivation` or `deletion_reverted`*, withholds reminders whose `remind_at` precedes `changed_at` — the reactivation instant. The reminder rows are untouched, stay `scheduled`, and stay visible in the user's list; what is withheld is the notification, and the suspended surface says so in both locales before it happens. Gating on the reason code is what keeps this a no-op for every account that was never suspended, **including every account the SH.1 backfill seeded**, whose `changed_at` is the migration's own run time — an ungated predicate would have silently swallowed those accounts' genuinely-overdue reminders at deploy.
- **Decision 3 — a job whose owner stopped being active is deferred, not failed.** `SH-WORKER-001` asks for "a declared, non-terminal outcome that returns the job to the queue". The available mechanism was `fail_job`, and using it would have been wrong in three ways at once: `jobs.error` is rendered verbatim on the Jobs page, `failed` is a state the user is shown, and neither is true of *"your account was suspended between two milliseconds"*. `defer_job_for_inactive_owner` returns the row to `pending` with its lease cleared, writes an `audit_logs` row (`job_deferred_inactive_owner`) so the automatic move is auditable, and **refuses when the owner is active** so it can never become a generic put-this-back primitive. `attempts` is left exactly as the claim set it — the requirement's "no retry burned beyond the claim's own", and safe because the claim predicate stops the *next* claim, so the race can happen once per suspension rather than once per tick. The code `owner_not_active` is deliberately **not** a member of `JOB_FAILURE_CODES`, and a test asserts that: the three refusal vocabularies of SH-SUSPEND-009 share nothing.
- **Consequences:** The migration count is unchanged at one, four of the initiative's eight spent. The heartbeat's replaced body is byte-identical to `202608040071`'s except for the lifecycle read (now `select … into` rather than `exists`) and the one reminder predicate. A future slice that adds a suspension reason must add its public label in the same change or the label-parity test fails by name. The drain's summary gains a `deferred` column rather than folding deferrals into `failed`, because a summary that called a suspension a failure is how an operator ends up investigating a healthy queue.

## ADR-079 — The current policy version is stated in SQL as well as in TypeScript, and bumping it is a migration

- **Date:** 2026-08-04
- **Status:** Accepted — recorded under the `ADR-071` precedent (migration *content* gets an ADR even when the migration *count* does not). SH.4 spends exactly the one migration the plan §1 allocates (`202608040074`); this records the design decision inside it that a reader would otherwise have to reverse-engineer, and the consequence it carries.
- **Context:** `SH-LEGAL-004` makes the current version of each document **a single repository constant** that rendering, acceptance and enforcement all read — `src/features/legal/versions.ts`. `SH-LEGAL-005` separately requires that `authenticated` may INSERT its own row into `policy_acceptances`. Those two requirements together open a door: PostgREST exposes that INSERT, and a constant only TypeScript knows is a constant PostgREST does not enforce.
- **Problem:** A client could insert `{"document":"terms","version":"9999-12-31"}` and **pre-accept every future policy it has never been shown** — after which no version bump would ever re-interpose it (T-30 in reverse). Server Action validation cannot close this, because the Server Action is not the only door. Equally, a client could record a superseded version to look compliant (T-28).
- **Alternatives considered:** *Validate only in the Server Action* (rejected: leaves the direct INSERT open, which is the actual attack surface, and would make SH-LEGAL-006 a claim about one caller rather than about the data). *Revoke the client INSERT and expose only the RPC* (rejected: SH-LEGAL-005 states the client INSERT grant in those words, and narrowing a requirement to make a guard easier is the wrong direction — the guard should hold at the boundary the requirement leaves open). *Store the current version in a `policy_versions` table an operator updates* (rejected: adds a table and a write path for a value that changes perhaps once a year, and makes the most legally consequential value in the system editable without review). *A monotonic guard — refuse a version older than one already accepted* (rejected: it stops the stale case and completely misses the pre-accept-the-future case, which is the more dangerous one).
- **Decision:** The version is stated in **both** places. `private.current_policy_version(text)` holds the literals in SQL, executable by no role; a `BEFORE INSERT` trigger refuses any version that is not current, so the direct INSERT and the RPC are guarded by the same rule; and `src/features/legal/version-parity.test.ts` compares the two literal sets **in both directions**, the `extraction-parity.test.ts` pattern. The RPC `record_policy_acceptance(document, surface)` takes **no version parameter at all** — a caller that cannot name a version cannot name a wrong one, so the whole class of forged-version bugs is absent from the app boundary rather than defended against there.
- **Consequence, stated rather than discovered: bumping a policy version is a migration plus the constant change in the same commit.** This is not a cost being absorbed reluctantly. A version bump re-interposes consent for every existing account on their next session; it is a deliberate legal event, and making it a reviewed schema change is the right weight for it. The alternative — a value one person can edit in a constants file and ship — is exactly the shape of change that should not be quiet.
- **Related consequences:** `policy_acceptances` joins the SH.0 cascade drill (its populator arm reads the current version through the same function rather than hard-coding it, so a bump does not fail the drill for an unrelated reason) and the SH.6 grant matrix. The `signup` member of the acceptance-surface vocabulary is declared but **not yet written by anything**: SH-LEGAL-008 requires acceptance rows to be written at the first authenticated session rather than trusted from the pre-session form, so today every row carries `interposition`. The member stays because the PRD declares it and a closed set that has to grow later is worse than one that starts complete.

## ADR-080 — The auth throttle is reachable by `anon`, blinded by a pepper the database does not hold, and takes its ceilings as required parameters

- **Date:** 2026-08-04
- **Status:** Accepted — recorded under the `ADR-071` precedent (migration *content* gets an ADR even when the migration *count* does not). SH.5 spends exactly the one migration the plan §1 allocates (`202608040075`); this records three decisions inside it that the plan leaves open and that a reader would otherwise have to reverse-engineer from grants.
- **Context:** `SH-THROTTLE-002` names `claim_credential_validation_slot` (`202608010067`) as the pattern to follow. That function authenticates its caller — `auth.uid()` is its first act, and `authenticated` is the only role that may execute it. **Every event this table exists to throttle happens before authentication.** A signup, a recovery request, a resend and a failed sign-in all arrive with no session, so the pattern's identity source and its grant are both unavailable, and the plan does not say what replaces them.
- **Problem:** The Server Actions run server-side but hold no privileged credential — `src/lib/supabase/` has exactly two factories, both session-scoped, and **no service-role client exists anywhere in the application**. So the throttle is reachable only by `anon`, or the application must grow a service-role client to reach it.
- **Decision 1 — `anon` may execute the claim; no role may touch the table.** `claim_auth_event_slot` and `finalize_auth_event_attempt` are granted to `anon` and `authenticated`; `auth_event_attempts` itself grants SELECT/INSERT/UPDATE/DELETE to nobody, keeps forced RLS with no permissive policy, and the two `SECURITY DEFINER` functions are its only write path. **Alternative rejected — a service-role client in the Next.js runtime:** it removes an anonymous INSERT path and installs, in the web tier, a credential that bypasses RLS on *every* table in the database. Trading a bounded, hash-blinded, single-shape insert for a universal RLS-bypass key in the most exposed process is the wrong direction, and it would have made the throttle's availability depend on a new production secret — so a missing variable would break recovery a second time, which is the exact failure `SH-ORIGIN-001` had just finished repairing.
- **Why the anonymous path is bounded, stated rather than assumed:** the identifier and IP hashes are `HMAC-SHA256` under a pepper that lives in the application environment and **not in this database** (`BYOK-SCHEMA-010`'s contract, with a domain tag added — see Decision 3). A direct caller therefore *cannot compute the hash of an address they want to attack*, so identifier-stuffing cannot lock a victim out; this is what makes `SH-THROTTLE-006` hold against the anonymous surface rather than only against the UI. A direct caller can burn buckets they invent, which harms only themselves, and can grow the table with junk rows — bounded per bucket by Decision 2's hard cap, bounded in time by the 30-day sweep, and no cheaper for them than hammering GoTrue's own public endpoints, which are capped at 30 per 5 minutes per IP. **Residual, recorded not waved away:** an anonymous caller can create unboundedly many *distinct* buckets. That is a storage-growth nuisance shared by every anonymous endpoint, it is swept within 30 days, and it grants nothing — a claimed slot sends no mail, creates no account and authenticates nobody, because the protection is applied by the Server Action passing the *correct* ceiling before it calls the provider, never by the row itself.
- **Decision 2 — ceilings are required parameters with no defaults, clamped to a hard cap declared in SQL.** `SH-THROTTLE-002` requires ceilings "changeable without migration", and the binding provider ceiling for resend (`rate_limit_email_sent = 2/hour`) is a **default-SMTP artefact** that changes the day Resend lands. A default in the signature would freeze a provider-dependent value into DDL. Requiring the parameter keeps every number in application code; a `1 … 100` bound inside the function stops a direct caller from passing `2^31` to farm one bucket, while sitting far above any real operating ceiling, so the cap is a safety bound and not the pending SMTP number. **The argument list is fixed on the first attempt on purpose:** Postgres cannot extend a function's parameters via `create or replace` (`ADR-057`, `2E-COMMAND-012`), so a signature that would need widening later is a signature that needs a second migration this initiative has not budgeted.
- **Decision 3 — the auth hashes are domain-separated from BYOK's.** Both reuse `BYOK_RATE_LIMIT_PEPPER` and `canonicalizeIp`, so no new production secret and no second canonicalization rule appear; but the HMAC input carries a domain tag (`auth:ip:` / `auth:identifier:`) so that an auth attempt's `ip_hash` never equals the `ip_hash` the BYOK ledger holds for the same address. Without the tag, anyone reading both tables could correlate a named BYOK user with an anonymous auth attempt — a join the pepper was supposed to prevent, reintroduced by reusing it.
- **Consequences:** The migration count is unchanged at one; **six of the initiative's eight are spent, two remain.** `anon` gains its first EXECUTE grant in this database. *(Corrected after CI: this ADR first said the SH.6 grant-matrix census "must treat these two functions as a declared exception". That was wrong about **when** — `signup_hardening_grant_census.sql` already runs every CI cycle and failed on this change within minutes, along with SH.0's `service_role` revoke carve-out and BYOK-SCHEMA-013's "`ip_hash` on exactly one table". All three are declared-set assertions whose own comments require a new member to "join the expected list by name in its own slice", and all three were widened **in this slice, with this ADR as the citation** — not loosened, and not deferred. The right reading is that a census which only ran at SH.6 would have let three declared invariants drift for two slices; the one that runs continuously turned them into a five-minute conversation.)* On BYOK-SCHEMA-013 specifically, the widening is defensible on the requirement's own terms: its stated concern is "a second retention surface and a second thing to forget to prune", and `auth_event_attempts` is swept on the same 30-day window by its own scheduler-only function — while Decision 3's domain tag means the two columns are not even the same value for the same address. The `resend` ceiling ships as a constant marked provisional at its definition and is **pending the post-SMTP hosted readback**; `SH-THROTTLE-005` is satisfied for the stable limits now and re-checked for the email limit then. Because the pepper is what blinds the table, losing or rotating it silently converts every existing bucket into a fresh one — the ceilings reset rather than fail, which is the safe direction, and it is why the pepper is a deployment secret and not a repository constant.

## ADR-081 — The `authenticated` INSERT on `audit_logs` is retained by decision, and the `service_role` grant on the BYOK tables is replaced by three named functions rather than kept

- **Date:** 2026-08-05
- **Status:** Accepted — recorded under the `ADR-071` precedent (migration *content* gets an ADR even when the migration *count* does not). SH.6 spends exactly the two migrations the plan §1 allocates (`202608050076` quotas and fairness, `202608050077` retention and the exposure closures); this records two decisions inside the second one that the plan deliberately left open, and one thing the PRD asserted that turned out not to be true of the repository.
- **Context:** `SH-EXPOSURE-003` requires the direct `authenticated` INSERT on `audit_logs` to be "dispositioned by decision, not silence: either revoked (with every in-app direct writer moved behind an RPC in the same slice) or retained with the writer inventory recorded". `SH-EXPOSURE-001` requires `service_role` to lose table DML on `user_ai_credentials` and `credential_validation_attempts`, on the stated basis that "the resolvers and throttle RPCs are DEFINER and keep working".

### Decision 1 — `audit_logs` INSERT is retained, with the writer surface guarded

- **What is actually exposed.** `authenticated` holds INSERT and SELECT and nothing else: UPDATE and DELETE were revoked in `202607170016`, so append-only holds regardless of this decision, and RLS confines every insert to the writer's own rows. The residual capability is that a user can write a true-looking audit row **about their own account**. It reaches nobody else's history, and it cannot forge an undo, because `undo_operations` grants `authenticated` no INSERT at all (`202607170028`).
- **What revoking would have cost.** Eighteen direct inserts across five modules, behind an RPC that would have to accept an open-vocabulary `action_type` — `audit_logs.action_type` has no CHECK constraint. That is a large, regression-prone change to production write paths, inside a slice whose subject is quotas and retention, and the resulting RPC would either validate nothing (achieving little) or need a closed action vocabulary that nothing has enumerated.
- **Decision:** retain, and make the retention checkable. `src/lib/closeout/audit-log-writers.test.ts` pins the **writer surface** — which modules may write directly — rather than a count. A nineteenth insert inside an already-listed module is ordinary work; the same insert in a new module is the exposure growing, which is the only thing a decision to retain has to keep bounded. The same file asserts that no Edge Function and no operator script writes audit rows directly, because there a direct insert would be an unaudited actor writing audit history.
- **Alternative rejected — defer to a later initiative:** the requirement's own words forbid silence, and "we will look at it later" recorded nowhere is the state it exists to prevent. Retained-with-an-inventory is one of the two exits it names; taking it explicitly is not the same as not deciding.

### Decision 2 — the `service_role` grant is replaced by three named functions, not simply removed

- **The PRD said nothing used the grant. The repository said otherwise.** `SH-EXPOSURE-001` was written expecting the DEFINER resolvers and throttle to be the only paths. Two real callers are not: `supabase/functions/delete-account/executor.ts` selects `status` to prove a credential was erased before the cascade runs, and `scripts/byok-rotate-master-key.mjs` selects ciphertext, iv and key_version and writes them back re-sealed.
- **Master-key rotation cannot exist without reading ciphertext.** The key lives in the operator's environment and never in this database (`BYOK-MASTER-005`), so the envelope must leave the database to be rewrapped. There is no design in which rotation runs and no privileged caller ever sees an envelope.
- **Decision:** revoke the table grants and route both callers through the narrowest function each needs — `admin_credential_status(uuid)` returning one column and never key material, `admin_list_credential_envelopes(integer, integer)` paged over active rows, and `admin_rewrap_credential_envelope(...)` writing as a compare-and-set on `key_version` so a concurrent rotation is a skip rather than a corruption. All three refuse a caller that is not `service_role`, and none is reachable by `anon` or `authenticated`.
- **What this closes, and what it honestly does not.** It closes generic table access: a leaked service key no longer reads every envelope with one `select *`, and no future code can casually reach for the table, because the table is not there for it. It does **not** eliminate T-26. `admin_list_credential_envelopes` still returns ciphertext to a service-role caller. What changed is that the capability is one named function with a stated purpose — greppable, separately revocable, impossible to use by accident — instead of an ambient property of a grant. Recording that residual is the point; a closure claimed as total would be worse than the grant, because it would stop anyone looking.
- **Alternative rejected — weaken the closure to keep the callers working:** the standing instruction is the opposite, and correctly so. A grant retained because something depends on it is a grant nobody will ever be able to remove.
- **Consequences:** The `service_role` revoke carve-out in `signup_hardening_grant_census.sql` grows from four tables to six, by name. `byok-rotate-master-key.mjs` now pages rather than reading every row at once, so a rotation no longer depends on how many accounts exist. The BYOK incident/rotation runbook's mechanics change even though its steps do not, and the residual above belongs in `SECURITY.md` rather than in a closed-issue list.

## ADR-082 — A migration that schedules a destructive sweep has already authorized it, so SH.6's sweeps are deployed unscheduled

- **Date:** 2026-08-05
- **Status:** Accepted — recorded after the fact, because the decision was forced by a defect found during deployment rather than taken at design time. No migration is spent; the correction is an operator script and a removed schedule.
- **Context:** `SH-RETENTION-008` requires a dry-run transcript to be recorded **before** the first live sweep against production, and PRD amendment `P-1` says in as many words that approving the retention schedule was not authorization to execute a purge. Migration `202608050077` nevertheless ends with a `cron.schedule(...)` block covering all seven sweeps, following the shape `202608040075` established for the auth-attempt prune.
- **The defect, stated plainly.** Applying that migration to the hosted project scheduled every destructive sweep, five of which had never run against production and none of which the owner had authorized. The first live purge would have executed at 04:11 UTC the following morning. The dry-run transcript — the artifact whose entire purpose is to inform a decision that has not yet been made — would have been produced *after* the deletion, describing something that had already happened. The gate was not bypassed by anybody; it was removed by the same migration that documented it.
- **Why nothing was lost, and why that is not the point.** The dry-run measured **zero** eligible rows in all seven classes, so the run would have deleted nothing. That is a fact about how young this project is, not about the design: the oldest `heartbeat_runs` row crosses its 30-day line within a fortnight. A control that happens to be harmless this week is not a control.
- **A second, smaller fault in the same block:** it scheduled `prune_credential_validation_attempts` under a new job name while BYOK's `byok-prune-validation-attempts` already scheduled the same function, so one sweep was queued twice nightly. Harmless — the delete is idempotent — but it is a duplicate nobody decided on.
- **Alternatives considered.** *Leave the schedules and rely on the zero counts* (rejected: it makes the authorization gate a coincidence, and the counts stop being zero on a known date). *Spend a migration to drop the schedules* (rejected: the eight-migration budget is fully spent, and an unscheduling is data, not schema — `cron.unschedule` needs no DDL). *Revoke EXECUTE from the scheduler* (rejected: there is no role to revoke from; the sweeps are already executable by nobody, and pg_cron runs them as the scheduler's own identity, which is exactly why scheduling IS the authorization).
- **Decision:** the five SH.6 sweeps were unscheduled on the hosted project on 2026-08-05, along with the duplicate, leaving `byok-prune-validation-attempts` and `sh-prune-auth-event-attempts` exactly as SH.5 and BYOK left them. `scripts/sh6-retention-schedule.mjs` becomes the gate the migration removed: `--status` reads the posture, `--enable` schedules the five, and **enabling is the authorization of the first live purge**, which the script says before it acts.
- **Consequence for the retention flags.** `sweepActive` in `src/features/legal/retention.ts` stays `false`, and the Privacy Policy keeps its honest-notice warning. Deployed is not enforced: a window whose sweep is not scheduled is not being applied to anyone, and a flag claiming otherwise would be T-31 in its purest form — a policy sentence false about the very database it describes. The flags flip when the schedule is enabled, not when the migration lands.
- **The general rule this establishes:** a migration may create a destructive mechanism, and may not schedule one. Scheduling is an operational act with an owner behind it, and it belongs in a script that can be read, run and reversed on its own — not in a file whose only observable effect at review time is that CI stayed green.
